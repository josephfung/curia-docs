Curia is not a single AI assistant — it is a team. A Coordinator agent serves as the unified face of that team, handling every message you or anyone else sends. Behind the scenes, specialist agents (research, expense tracking, scheduling, and more) do focused work and hand their results back to the Coordinator, which synthesizes everything into a single coherent reply. The people who email or message you never know multiple agents were involved.

## The Coordinator agent

Every inbound message — across every channel — routes to the Coordinator first, without exception. The Coordinator has a persona you configure: a display name, a tone & style (a few lines on how it sounds, set in **Settings → Personality**), and an email signature. To the outside world, that persona is the only identity they see.

The Coordinator decides how to handle each message:

- **Handle directly** — small talk, acknowledgments, simple questions the Coordinator can answer from memory
- **Delegate to a specialist** — complex or domain-specific tasks go to the right specialist agent, which returns results to the Coordinator
- **Synthesize and respond** — the Coordinator assembles the specialist's work into a reply in its own voice

The Coordinator's `role: coordinator` field in its YAML tells the dispatch layer to route all messages here. There is exactly one Coordinator per deployment.

```yaml
# agents/coordinator.yaml
name: coordinator
role: coordinator
description: Central coordinator — routes all messages, delegates to specialists, maintains the unified persona
model:
  tier: standard
system_prompt: |
  You are Alex, executive assistant to the CEO.
  You are the single point of contact for all communications.
  You have a team of specialists you can delegate to, but you always
  respond in your own voice. The sender should never know multiple
  agents were involved.
pinned_skills:
  - entity-context
  - delegate
  - contact-lookup
  - email-send
  - email-reply
  - calendar-list-events
  - get-autonomy
  - set-autonomy
allow_discovery: true
```

## Specialist agents

Specialist agents like `research-analyst` work entirely inside the system. They receive delegated tasks from the Coordinator via the Bullpen or a direct `agent.response` event, do their work using their own pinned skills, and return results. They never communicate with the outside world directly — their internal handles (such as `@research-analyst`) appear only in the audit log and Bullpen threads, never in outbound messages.

```yaml
# agents/research-analyst.yaml
name: research-analyst
role: specialist
description: Conducts web research, summarizes findings, and provides analysis
model:
  tier: fast
system_prompt: |
  You are a research analyst working as part of an executive assistant team.
  Conduct thorough research and provide clear, actionable summaries.
  Your findings will be reviewed and presented by the team coordinator.
pinned_skills:
  - web-fetch
  - web-search
  - scheduler-create
  - scheduler-list
  - scheduler-cancel
allow_discovery: false
```

## Agent definition in YAML

You define agents in YAML files in the `agents/` directory. No code is required for most agents. The full schema includes:

```yaml
name: expense-tracker
description: Tracks and categorizes expenses from receipts and emails

model:
  tier: standard

system_prompt: |
  You are an expense tracking assistant for a CEO.
  Extract amounts, vendors, categories, and dates from receipts.

pinned_skills:
  - email-list
  - email-get
  - file-parse

allow_discovery: true

pinned_context:
  docs: /shared/expenses/rules.md
  configs: expenses/currency

schedule:
  - cron: "0 9 * * 1"
    task: "Generate weekly expense summary"

error_budget:
  max_turns: 20
  max_cost_usd: 1.00
```

### Key fields

| Field | Description |
|---|---|
| `model.tier` | Capability tier: `fast`, `standard`, or `powerful` — mapped to a concrete model by the operator in config |
| `pinned_skills` | Tools and skills always available to this agent in every task |
| `allow_discovery` | When `true`, the agent can search the tool registry for capabilities not in its pinned list |
| `pinned_context` | Shared documents and settings shown to the agent on every turn — see [Pinned context](#pinned-context) |
| `schedule` | Cron expressions for recurring tasks the agent runs automatically |
| `error_budget.max_turns` | Maximum LLM round-trips per task execution — hard cap |
| `error_budget.max_cost_usd` | Maximum dollar spend per task execution — hard cap |

### Model tiers

Each agent declares a capability tier rather than a specific model. The operator maps tiers to concrete models in `config/local.yaml`, so the same agent YAML works across deployments with different model choices.

```yaml
model:
  tier: standard   # fast | standard | powerful
```

| Tier | Default model | Use for |
|---|---|---|
| `fast` | Claude Haiku | High-frequency specialist agents — structured lookups, calendar ops, contact work |
| `standard` | Claude Sonnet | General-purpose agents — coordinator, inbox, meeting debrief |
| `powerful` | Claude Opus | Agents requiring maximum reasoning depth (rarely needed) |

The tier-to-model mapping is controlled in `config/local.yaml` under `model_routing.tiers`. See the [configuration reference](/references/configuration) for details.

### Error budgets

Every agent task has hard caps that prevent runaway behavior — infinite loops, surprise LLM bills, or agents that spin forever on a stuck task.

- `max_turns` — the maximum number of LLM round-trips for a single task execution. When exceeded, the task stops and reports an error.
- `max_cost_usd` — the maximum estimated dollar spend for a single task. Tracked across every LLM call in the task; exceeded tasks are halted immediately.

These budgets are tracked cumulatively across bursts for long-running persistent tasks.

### Skill discovery

When `allow_discovery: true` is set, the agent receives the built-in `tool-registry` tool in addition to its pinned skills. If the LLM determines it needs a capability not in its pinned list, it queries the registry:

```text
tool-registry({ query: "send SMS" })
```

The registry returns matching skill names and descriptions. Curia then appends the full tool schemas to the agent's working tool list for that task, so discovered skills are immediately callable.

<Note>
Tools tagged `sensitivity: elevated` — such as payment processing or bulk deletion — require human approval the first time an agent attempts to use them. Normal-sensitivity tools discovered via the registry are auto-approved.
</Note>

### Pinned context

Some agents work from standing instructions: an inbox agent's email rules, a scheduling agent's preferences, a list of your current priorities. `pinned_context` declares them, and Curia puts their current contents into the agent's instructions on every turn. The agent never has to remember to look them up, and an edit you make takes effect on its next turn.

```yaml
pinned_context:
  docs:                                   # shared documents: one path, or a list
    - /shared/inbox/rules.md
    - path: /shared/priorities.md
      description: The principal's highest priorities, learned by asking them.
  configs:                                # single config-store keys: one, or a list
    - ceo_inbox/decision_tagging
    - key: ceo_inbox/watermark
      description: ID of the last message processed. If missing, start from the newest.
```

- **`docs`** are documents under `/shared/` in the document workspace. They have no length limit, the agent can edit them one `##` section at a time, and you can read and edit them in the console under **Memory → Documents**. Use one when a setting is long or changes a piece at a time, such as a list of rules.
- **`configs`** are single `config-store` keys, written `<namespace>/<key>`. Use them for short values.
- **`description`** is optional. It tells the agent what the item is for and what it means when it is missing, and it is shown even before the item exists.

How each item appears to the agent:

| State | What the agent sees |
|---|---|
| Exists | Its full contents (documents also show their version) |
| Not created yet | "Not yet created" or "Not set yet", so the agent knows to create it on first write |
| Blank | That it exists but is empty |
| Archived in the console | That you archived it. The agent won't recreate it, so you can restore it |
| Couldn't be read | "Unavailable this turn". The agent is told not to overwrite it. The failure is logged and never silently skipped |

A shared document can be changed only by the agents that declare it, plus you in the console. Several agents can declare the same document to share it, and simultaneous edits are protected by version checks. Shared documents are durable: they are never tied to a task and never archived when a project completes. Each shared document should describe its own format at the top, so every agent that uses it follows the same format.

<Note>
Everything in `pinned_context` is sent on every turn. Keep it to what the agent needs most of the time; anything rarer can still be read on demand with `doc-read` or `config-store`. Curia logs a warning when a pinned item grows past `documentWorkspace.pinnedContextWarnChars` (16,000 characters by default), but it still sends the item in full.
</Note>

## TypeScript handlers

For agents that need custom logic beyond what YAML configuration supports, you can add a TypeScript handler as an escape hatch. The YAML configuration stays exactly the same; you add a `handler` field pointing to your TypeScript file.

```yaml
name: research-analyst
handler: ./research-analyst.handler.ts
# ... all other YAML fields apply normally
```

The handler exports lifecycle hooks:

```typescript
export const onTask = async (task, ctx) => { /* before the agent starts */ };
export const onToolResult = async (tool, result, ctx) => { /* after each tool call */ };
export const beforeRespond = async (response, ctx) => { /* before the final reply */ };
```

Use handlers for things like custom memory loading, domain-specific validation of tool results, or pre-processing inputs before they reach the LLM.

## The Bullpen

When specialist agents need to coordinate, they do so in the Bullpen — a structured, threaded discussion space that functions like an internal team channel. Any agent can open a thread addressed to other agents. The Coordinator checks for pending Bullpen threads on every task, ensuring nothing gets missed even if an agent only activates on inbound messages.

Every Bullpen exchange is:

- **Logged** — every message is written to the audit log with full causal tracing
- **Visible** — you can observe all threads via the dashboard or HTTP API SSE stream
- **Interruptible** — you can send a message to any thread via any channel to redirect, clarify, or stop a discussion

Think of it as overhearing your staff coordinate at their desks — with the ability to step in at any moment.

## Agent lifecycle

When a message arrives, here is what happens inside Curia:

<Steps>
  <Step title="Message received">
    The channel adapter publishes a normalized `inbound.message` event to the bus. The dispatch layer receives it and routes it to the Coordinator.
  </Step>
  <Step title="Context loaded">
    The Coordinator loads its system prompt, the current contents of anything in its `pinned_context`, relevant entity memory and knowledge graph context, and any pending Bullpen threads. Conversation history for this `conversation_id` is loaded from working memory.
  </Step>
  <Step title="LLM called">
    The Coordinator calls its configured LLM. If the LLM decides to invoke a tool or delegate to a specialist, those requests are dispatched via the bus.
  </Step>
  <Step title="Tools and delegation">
    Tool results flow back through the execution layer (sanitized and validated). Specialist agents complete their work and return results to the Coordinator.
  </Step>
  <Step title="Response published">
    The Coordinator formulates a reply and publishes an `agent.response` event. The dispatch layer routes the outbound message back to the originating channel, and the outbound gateway adds the persona's email signature to email — every email Curia sends or drafts, except system alerts, notes for the principal, and mail from the principal's own mailbox.
  </Step>
</Steps>
