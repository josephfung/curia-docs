Curia ships with a Coordinator agent that handles all incoming messages and a research analyst that can dig into topics on demand. When your workflow calls for domain-specific expertise — expense tracking, contract review, investor relations — you create a specialist agent that owns that domain and lets the Coordinator delegate to it.

## When to create a specialist vs. using the Coordinator directly

The Coordinator can handle many tasks on its own using its pinned skills. Create a specialist agent when:

- The task requires a **focused, auditable skill set** distinct from the Coordinator's (e.g., an expense tracker with its own parsing and spreadsheet skills)
- You want a **focused system prompt** that won't bloat the Coordinator's context
- The task has a **recurring schedule** of its own (e.g., generate a weekly summary every Monday)
- You want **separate error budgets** — caps on LLM turns and spend that are independent of the Coordinator's limits

## Choosing built-in skills

Curia ships with more than 90 built-in skills. The [built-in skills reference](/skills/built-in-skills) is the catalog to shop from — each skill lists its `action_risk` level — and [how skills work](/skills/how-skills-work) explains the execution model. A few rules of thumb when deciding what to give an agent:

- **Pin the narrowest set that does the job.** List only the skills the agent actually needs in `pinned_skills`. A calendar agent doesn't need `email-send`; an expense tracker doesn't need `calendar-delete-event`. Smaller skill sets keep the agent focused and shrink the blast radius if a prompt goes wrong.
- **Mind `action_risk`.** Higher-risk skills (`medium`, `high`, `critical`) trigger the [approval workflow](/security/approval-workflow) whenever the current [autonomy score](/core-concepts/autonomy) is below their floor. Pinning a skill doesn't bypass that gate — it only makes the skill available.
- **Pin explicitly, or allow discovery.** `pinned_skills` are always available. `allow_discovery: true` lets the agent search the registry for anything else at runtime; leave it off (the default) for agents that should only ever touch their declared skills.
- **Use capability bundles instead of long lists.** Some skill families are pinned as a set by a single flag rather than named one by one. `enable_task_management: true` auto-pins the full `task-*` backlog family (`task-create`, `task-list`, `task-update`, `task-complete`) *and* the `doc-*` document-workspace family (`doc-list`, `doc-read`, `doc-search`, `doc-write`), giving the agent a task backlog and durable working memory in one line.

## Simple agent — YAML only

Most agents need nothing more than a YAML file. Create a file in the `agents/` directory:

```yaml
# agents/expense-tracker.yaml
name: expense-tracker
description: Tracks and categorizes expenses from receipts and bank notifications

model:
  tier: standard

system_prompt: |
  You are an expense tracking assistant for a CEO.
  Extract amounts, vendors, categories, and dates from receipts and notifications.
  Maintain running totals by category and flag anything unusual.

pinned_skills:
  - email-list
  - email-get
  - file-parse

allow_discovery: true

schedule:
  - cron: "0 9 * * 1"
    task: "Generate weekly expense summary and email it to the CEO"

error_budget:
  max_turns: 20
  max_cost_usd: 1.00
```

Restart Curia after adding the file — agents are loaded at startup.

## Required fields

| Field | Description |
|---|---|
| `name` | Unique identifier used in the Bullpen, audit log, and the `delegate` skill |
| `description` | One-sentence summary; the Coordinator reads this to decide when to delegate |
| `model` | Capability tier — set `tier` to `fast`, `standard`, or `powerful` |
| `system_prompt` | The agent's instructions |

## Optional fields

<AccordionGroup>
  <Accordion title="model — capability tier">
    Agents declare a capability tier rather than a specific model. The operator maps tiers to concrete models in `config/local.yaml`, so the same agent YAML works across deployments:

    ```yaml
    model:
      tier: standard   # fast | standard | powerful
    ```

    | Tier | Default model | Use for |
    |---|---|---|
    | `fast` | Claude Haiku | High-frequency structured agents (calendar, contacts) |
    | `standard` | Claude Sonnet | General-purpose agents (coordinator, inbox) |
    | `powerful` | Claude Opus | Agents needing maximum reasoning depth |

    See the [configuration reference](/references/configuration) for how to remap tiers to models in `config/local.yaml`.
  </Accordion>

  <Accordion title="pinned_skills and allow_discovery">
    `pinned_skills` lists skills that are always available to this agent. `allow_discovery: true` lets the agent search the skill registry for capabilities beyond the pinned list:

    ```yaml
    pinned_skills:
      - email-list
      - email-get
      - file-parse

    allow_discovery: true
    ```

    Set `allow_discovery: false` (the default) for agents that should only ever use their declared skills. See [choosing built-in skills](#choosing-built-in-skills) for how to pick the set.
  </Accordion>

  <Accordion title="enable_task_management — backlog and working memory">
    Set `enable_task_management: true` to auto-pin two skill families as a bundle rather than naming their eight skills by hand: the `task-*` backlog skills (`task-create`, `task-list`, `task-update`, `task-complete`) and the `doc-*` document-workspace skills (`doc-list`, `doc-read`, `doc-search`, `doc-write`). It also marks the agent heartbeat-eligible so its scheduled wake-ups fire.

    ```yaml
    enable_task_management: true
    ```

    The Coordinator, `ceo-inbox`, and `contacts` agents enable it. See [choosing built-in skills](#choosing-built-in-skills).
  </Accordion>

  <Accordion title="memory — access">
    Agents do not declare memory scopes. Every agent reads and writes a single shared knowledge graph, so a specialist can build on facts other agents recorded (contact preferences, prior research, entity relationships). Whether an agent can touch memory at all is decided by the memory skills you pin to it (e.g. `memory-query`, `memory-store`), not by a per-agent namespace.
  </Accordion>

  <Accordion title="schedule — cron jobs at startup">
    Schedule tasks that run automatically on a cron expression:

    ```yaml
    schedule:
      - cron: "0 9 * * 1"
        task: "Generate weekly expense summary"
      - cron: "0 */4 * * *"
        task: "Check inbox for new receipts"
    ```

    Cron expressions run in Curia's configured timezone (set via `TIMEZONE` in `.env`). These jobs are created in the scheduler database at startup. If the job already exists from a previous run, it is updated, not duplicated.
  </Accordion>

  <Accordion title="error_budget — max turns and cost">
    Every agent task has hard caps. When either limit is exceeded, the task stops immediately — no infinite loops, no surprise bills:

    ```yaml
    error_budget:
      max_turns: 20      # maximum LLM round-trips per task execution
      max_cost_usd: 1.00 # maximum spend per task execution
    ```

    Error budgets apply per task execution — a recurring scheduled task gets a fresh budget on each run.
  </Accordion>
</AccordionGroup>

## Reaching the principal

Agents that need to send messages to, look up calendars for, or otherwise act on behalf of the principal (the CEO / operator the deployment serves) MUST reference `${principal_contact_id}` in their system prompt. The runtime injects this placeholder at bootstrap from the contact designated as the principal.

```yaml
system_prompt: |
  You are an executive assistant.

  The CEO's contact ID is `${principal_contact_id}` — it is injected at bootstrap.
  Call `entity-context` on `${principal_contact_id}` to discover their verified
  email addresses, Signal number, calendar IDs, and timezone whenever you need
  to reach them.
```

Why this matters:

- **Don't hardcode addresses or phone numbers** in agent prompts. They go stale and create a confidentiality risk if the wrong value is baked in.
- **Don't call `contact-lookup` by role for the principal.** The platform already resolved the principal's contact ID once at bootstrap; re-doing the lookup on every cron tick wastes a skill call on an immutable value, and an LLM doing the resolution mid-prompt can pick the wrong contact when role names overlap.
- The placeholder is **opt-in** — only agents that reference it pay the prompt-bytes cost. Specialist agents that should report through the coordinator (research-analyst, expense-tracker, etc.) shouldn't need it.

The same convention applies to `${agent_contact_id}` (the agent's own identity), which is also opt-in and bootstrap-resolved. See the [agent manifest schema](/references/agent-manifest-schema) for the full template-variable list.

## Full example — investor relations specialist

```yaml
# agents/investor-relations.yaml
name: investor-relations
description: Tracks investor communications, prepares updates, and monitors cap table events

model:
  tier: standard

system_prompt: |
  You are an investor relations specialist for a CEO.
  You track communications with investors, monitor for cap table events,
  and help prepare board updates and investor briefings.

  Always surface relevant past context when investors reach out.
  Flag any unusual requests or requests that may require legal review.

pinned_skills:
  - email-list
  - email-get
  - email-draft-save
  - contact-lookup

allow_discovery: true

schedule:
  - cron: "0 8 * * 1"
    task: "Summarize investor email activity from the past week"

error_budget:
  max_turns: 30
  max_cost_usd: 2.00
```

## Complex agents — TypeScript handler

If you need custom logic that goes beyond what a system prompt can express, add a TypeScript handler alongside your YAML:

```yaml
# agents/research-analyst.yaml
name: research-analyst
handler: ./research-analyst.handler.ts
description: Conducts web research and provides analysis

model:
  tier: fast

system_prompt: |
  You are a research analyst. When given a topic, conduct thorough research
  and return a clear, actionable summary with sources.

pinned_skills:
  - web-fetch
  - web-search
  - web-browser
```

Your handler exports lifecycle hooks:

```typescript
// agents/research-analyst.handler.ts

export const handler = {
  async onTask(ctx) {
    // Called when the agent receives a new task.
    // Modify ctx.messages or ctx.tools before the LLM call.
  },

  async onSkillResult(ctx, skill, result) {
    // Called after each skill invocation.
    // Inspect or transform the result before it returns to the LLM.
  },

  async beforeRespond(ctx, response) {
    // Called before the agent's response is sent.
    // Return a modified response string, or undefined to use the original.
    return response;
  },
};
```

## Delegating to your agent

Once your agent is running, the Coordinator can delegate to it using the `delegate` skill. The Coordinator reads each agent's `description` field to decide when to route tasks. Write descriptions clearly — they function as the Coordinator's routing table.

You can also test delegation directly from the CLI:

```
> Ask the investor-relations agent to summarize this week's investor emails.
```

Curia routes the task to your agent, runs it, and synthesizes the result into the Coordinator's response.
