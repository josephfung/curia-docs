Curia keeps every credential — LLM API keys, Nylas, Signal, Tavily, the HTTP API token, the console login secret, your website passwords and saved cards — in an encrypted vault rather than in plaintext `.env` files. The vault is the single source of truth for secrets; tools read from it through a scoped accessor, and the LLM never sees a value.

## How it works

Secrets are encrypted with **AES-256-GCM** and stored in a `secrets` table in Postgres. Each row holds the ciphertext and its initialization vector, never the plaintext. The key that encrypts and decrypts them — `SECRET_ENCRYPTION_KEY` — is the one secret that has to live outside the vault, in `.env`.

At runtime a tool calls `ctx.secret("tavily_api_key")`; the execution layer checks that the tool declared that key, decrypts the value, and hands it to the handler. Every access is audit-logged (which tool, which task, and when), but the value itself is never written to a log.

## What stays in `.env`

Only the four values needed to reach and unlock the vault, plus non-secret deployment config:

| Variable | Purpose |
|---|---|
| `DB_USER` | PostgreSQL user. |
| `DB_PASSWORD` | PostgreSQL password. |
| `DATABASE_URL` | Postgres connection string (where the vault lives). |
| `SECRET_ENCRYPTION_KEY` | Base64-encoded 32-byte AES-256 master key that decrypts the vault. |

`pnpm run setup` generates the database password and the master key, writes them to `.env`, and seeds the core credentials (`anthropic_api_key`, `api_token`, `web_app_bootstrap_secret`) into the vault automatically.

<Warning>
  **Back up `SECRET_ENCRYPTION_KEY`.** It is the only thing that can decrypt the vault. If you lose it, every stored secret becomes permanently unrecoverable and you have to re-seed from scratch. Keep a copy somewhere independent of the server — a password manager or a secrets store.
</Warning>

## The Secrets page

In the console, **Memory → Secrets** lists every secret Curia holds in one searchable table. Values are never shown, not even to you: the page reads names and details only, and its forms write values without reading them back.

Each row has a **Kind**:

| Kind | What it is | What you can do |
|---|---|---|
| **Personal** | Your website logins, PINs and saved cards (`user.*` keys) | Add, edit, replace and remove |
| **System** | Keys that tools, channels and MCP servers declare, such as `tavily_api_key` or `channel.email.nylas_api_key` | Set, replace and remove |
| **Platform** | Keys Curia reads directly at startup: LLM provider keys, embeddings, the HTTP API token, the console sign-in and web push keys | View only. The page shows **Managed by deployment**; change them on the server |

Search by name, site or username, and narrow the list by kind, status (**Configured**, **Expired**, **From env**, **Missing**, **Not set**, **Not declared**) and whether something requires the key. The **Used for** column shows the sign-in site, the card, or what declares the key, and **Last used** shows when Curia last read it.

Open a row to see its details, what declares it and its **Recent uses**. From there:

- **Set value** or **Edit** writes a new value. Leave a password field blank to keep the current one.
- **Remove** deletes the key. If something enabled still needs it, the console names what would stop working and asks you to confirm again.
- **+ New secret** adds a personal secret: a **Website login**, a **Card**, or **Other** (a labelled value, such as a bank PIN). The drawer shows the key name it will save under, and warns you before replacing one that exists.

A row marked **Not declared** is left over from an uninstalled tool or channel. You can remove it, but not set it.

## Adding vault secrets

Core credentials are seeded by `pnpm run setup`. Channel credentials are managed from **Settings → Channels** in the Curia console — each channel's settings page has a field for its credential (Nylas API key, Signal phone number, etc.). Tool credentials, such as the optional Tavily key, are under **Settings → Tools**. Any declared key can also be set from **Memory → Secrets**.

Keys Curia reads at startup, including channel credentials, take effect after a restart. On the Secrets page, their **Recent uses** says **Read when Curia starts**. Restart Curia after adding or updating one:

```bash
docker compose restart curia
```

A tool's own key, such as `tavily_api_key`, is read each time the tool runs, so it needs no restart.

### Vault key names

| Vault key | Set by |
|---|---|
| `anthropic_api_key` | `pnpm run setup` (prompted) |
| `openai_api_key` | `pnpm run seed-vault` (see [OpenAI embeddings](/integrations/openai-embeddings)) |
| `embedding_api_key` | `pnpm run seed-vault`, only when your [embedding server](/integrations/embeddings-endpoint) checks a key |
| `openrouter_api_key` | `pnpm run seed-vault`, only if you route a tier to [OpenRouter](/references/configuration#model-routing) |
| `aws_access_key_id`, `aws_secret_access_key` | `pnpm run seed-vault`, only if you opt in to AWS Bedrock |
| `api_token` | `pnpm run setup` (generated) |
| `web_app_bootstrap_secret` | `pnpm run setup` (generated, shown once) |
| `channel.email.nylas_api_key` | Settings → Channels → Email |
| `channel.email.<name>.nylas_grant_id` | Settings → Channels → Email → Email accounts |
| `principal.mailbox.<id>.nylas_grant_id` | Settings → Behaviour → Email & Calendar |
| `channel.signal.phone_number` | Settings → Channels → Signal |
| `tavily_api_key` | Optional. Settings → Tools → `web-search` → Optional secrets, or the setup assistant's link. Used from the next search, no restart. |

Channel credentials managed through the [channel registry](/references/channel-config-schema) are stored under namespaced keys following the convention `channel.<name>.<field>` (e.g. `channel.email.nylas_api_key`).

## Rotating the master key

Rotating `SECRET_ENCRYPTION_KEY` re-encrypts every stored secret under a new key. Supply both the old and new keys and the database connection:

```bash
SECRET_ENCRYPTION_KEY_OLD=<old-base64> \
SECRET_ENCRYPTION_KEY_NEW=<new-base64> \
DATABASE_URL=<url> \
pnpm exec tsx scripts/rotate-secret-key.ts
```

Generate a new key with `openssl rand -base64 32`. After rotation, replace `SECRET_ENCRYPTION_KEY` in `.env` with the new value and recreate the container. Keep the old key until you have confirmed the instance comes up cleanly with the new one.

## Required and optional tool secrets

A tool can declare that a secret must be present before it can be used. Declaring a vault key in the tool manifest's `install.requires_secrets` makes the [registry](/core-concepts/registry) refuse to install or enable the tool until that key is in the vault. No bundled tool uses this today.

A tool can instead list a key in `install.optional_secrets`, with a note on what it adds. Optional secrets never block install or enable. The console shows them under **Optional secrets** on the tool's page, marked "not set" until you add one. The bundled `web-search` tool declares `tavily_api_key` this way: it works without a key, and a key raises its limits.

## Personal secrets (`user.*`)

Secrets you hand Curia during a conversation — a website password, an account PIN — are stored under the `user.*` namespace, separate from system and channel credentials. Curia sends you a one-time link, valid for 30 minutes, to type the value into; the value goes straight to the vault and the agent never sees it. You can also add one yourself with **+ New secret** on the Secrets page.

A website login keeps its **sign-in page URL** and **username** next to the password. Neither is secret, so Curia can see them and knows which saved login belongs to which site. Its key is named from the site, so the same login isn't saved twice under different names.

Curia can **list the names** of these keys and their sign-in details (never the values, and never system or channel keys), and checks that list before asking you for a secret. Without it, the same password gets captured under three near-identical names over three conversations and none of them can be found again. Reading a `user.*` value at runtime is a separate, narrower permission held only by the browser tool, which uses it to fill a form without the secret ever entering the model's context.

If a site asks for a sign-in code, Curia asks you for it, or picks up an emailed code from your inbox, and types it only into that site's waiting sign-in page. Anywhere else, such as its notes, memory and messages, the code is replaced with `[sign-in code]`.

## Saved cards

You can save payment cards so Curia can pay for things you ask it to buy. Curia fills the card at checkout without ever seeing the number, and only after you approve that purchase.

### Save a card

Either:

- **Ask Curia** to save a card. It sends you a one-time link to a form where you type the card in.
- **Add it yourself** under **Memory → Secrets → + New secret → Card**.

The form asks for a **Label** (such as "Personal"), the **Card number**, **Expiry month** and **Expiry year**, the **Security code (CVV)**, the **Name on card** and, optionally, the **Billing postal code**. Afterwards the Secrets page shows only the brand, the last four digits and the expiry, and marks a card **Expired** once its expiry month has passed.

When a card is renewed, edit it on the Secrets page: change the label, expiry, name or postal code, type a new security code, or choose **Replace card** to swap in a whole new card. Curia can also send you a link for just the new expiry and security code.

### Pay with a card

Before every purchase, Curia asks you first. The request names the card (brand and last four), the site, the amount as the checkout page shows it, and what is being bought. Answer it the way you answer any approval: reply, react, or use the console. An unanswered request expires after 30 minutes.

Your yes covers one card, one site and the conversation it came from, for 30 minutes. Within that window Curia can fill the card number and security code at most twice, so it can retry once if the form rejects the first attempt. A second purchase asks again. No autonomy score, instruction or approval of anything else lets Curia skip this step.

<Warning>
  The amount in the request is what Curia read from the page, and Curia doesn't check that the checkout finished. Once you approve a site, any part of its checkout page can receive the card, including frames from other domains, because payment processors host the card fields in their own frames.
</Warning>

Each request and your answer appear in the card's **Recent uses** and in the audit log, with the brand, last four, site and amount, never the number.
