## What this is for

Curia often hands work over as a document: a briefing, a draft plan, a research summary. This step gives Curia a Google account of its own with access to Google Drive, Docs and Sheets. Curia creates files there and shares them with your principal, who always gets edit access.

This is **Curia's** Google account, not your principal's. Curia only sees your principal's files if they share them with it.

On the [Setup page](/get-started/check-your-setup) this is the **Google Workspace** step, under **Business Apps** after **Email & calendar**. It's **required**: in your principal's first conversation Curia delivers its drafts as Google Docs, so Start onboarding waits until Curia is signed in.

## What you'll need

- **A Google account for Curia.** If Curia's mailbox from [Curia's own email](/get-started/curia-email) is on Gmail or Google Workspace, use that account.
- **A Google account of your own** to set up Google Cloud. Use your account, not Curia's. You can reuse the Google Cloud project from Curia's email, and its **Web application** OAuth client (you'll add a second secret to it for Curia; see step 3).
- **Curia on its public https:// address** (`APP_ORIGIN`). Google sends the sign-in back there.

**Time:** about 20 minutes.

**Cost:** nothing beyond Curia's Google account itself.

## Steps

<Steps>
  <Step title="Open or create a Google Cloud project">
    Sign in to [console.cloud.google.com](https://console.cloud.google.com) with **your own** account. Open the project you made for Curia's email, or create one, for example `curia-workspace`.

    Under **APIs & Services → Library**, enable:

    - Google Drive API
    - Google Docs API
    - Google Sheets API

    This step doesn't need the Calendar or Gmail APIs: Curia reaches mail and calendar through Nylas. A project reused from Curia's email already has them on, which is fine.
  </Step>

  <Step title="Set up the consent screen and publish it">
    Under **APIs & Services → OAuth consent screen**:

    - **If Curia's account is in a Google Workspace organisation you manage,** create the project inside that organisation and choose **Internal**. Only accounts in your organisation can sign in, and there's no review.
    - **Otherwise,** choose **External**. Add the Drive, Docs and Sheets scopes, then **publish the app** so its status reads **In production**. Publishing doesn't list your app anywhere. Google may show an "unverified app" warning when Curia's account signs in; you can continue past it.

    <Warning>
      Don't leave an External app in **Testing**. Google expires Testing sign-ins after 7 days, and Curia loses access to Drive every week.
    </Warning>
  </Step>

  <Step title="Add Curia's callback to a Web application OAuth client">
    Under **APIs & Services → Credentials**, open the **Web application** OAuth client you use for Curia's email, or choose **Create credentials → OAuth client ID** with the application type **Web application**.

    Under **Authorized redirect URIs**, add the **Callback URL** shown in the Google Workspace step. It's your Curia address followed by `/api/google-workspace/callback`, for example `https://curia.example.com/api/google-workspace/callback`. Keep any Nylas redirect URI that's already there.

    Copy the **client ID**. For the secret:

    - **A client you just created:** copy the **client secret** now. Google shows it only once.
    - **The client from Curia's email:** its secret can't be viewed again. Choose **Add secret**, copy the new secret, and leave the original one enabled: Nylas still uses it.

    <Note>
      A **Desktop app** client can't be used here: Google lets it return only to `localhost`.
    </Note>
  </Step>

  <Step title="Enter the details in the Google Workspace step">
    On the Setup page, open **Google Workspace** under **Business Apps** and fill in:

    | Field | Value |
    |---|---|
    | Curia's Google address | Curia's Google address, such as `curia@example.com` |
    | OAuth client ID | The client ID from step 3 |
    | OAuth client secret | The client secret from step 3 |

    Click **Save** (or go straight to the next step: **Sign in as Curia** turns on once all three are filled in, and saves them first). Saved fields show **Saved**. The values are stored in the encrypted [vault](/get-started/secrets-vault).
  </Step>

  <Step title="Sign in as Curia">
    Click **Sign in as Curia**. Google opens in the same tab. Sign in as **Curia's** Google account, not your own, and leave every permission ticked.

    Google sends you back to a page that says how it went. On success, Curia saves the sign-in, turns its Google Workspace tools on, and restarts once; the page waits for it and then links back to Setup. The step then reads **Signed in as Curia**.

    If the page says **Wrong Google account** or **Permissions missing**, nothing was saved: go back and sign in again.
  </Step>
</Steps>

After Setup, the same **Sign in as Curia** panel is under **Settings → MCP Skills → google-workspace**, with the three values.

### Signing in by hand (fallback)

If Curia isn't on a public address yet, you can still sign it in from a computer with a browser and copy the token across. This uses Google's `localhost` redirect, so it needs a **Desktop app** client (or `http://localhost:8000/oauth2callback` on a Web client). You need `git` and [`uv`](https://docs.astral.sh/uv/) on that computer:

```bash
git clone https://github.com/josephfung/curia.git
cd curia
GOOGLE_OAUTH_CLIENT_ID=<client ID> \
GOOGLE_OAUTH_CLIENT_SECRET=<client secret> \
CURIA_GOOGLE_EMAIL=<Curia's Google address> \
  uv run --with mcp scripts/gdrive-auth.py
```

Copy the token file to the server, then, from the directory you installed Curia into, write it into Curia's token volume and restart:

```bash
docker compose exec -T curia sh -c \
  'mkdir -p /tmp/.google_workspace_mcp/credentials; cat > "/tmp/.google_workspace_mcp/credentials/<Curia's Google address>.json"' \
  < "<Curia's Google address>.json"
docker compose restart curia
```

The Google Workspace step reads **Signed in** once Google accepts that token; no need to sign in again from the console.

## Check it works

1. In the logs (`docker compose logs curia`), look for `MCP server tools registered` with `"server":"google-workspace"` and a `registered` count above zero. A count of zero means the sign-in token is missing: sign in as Curia again.
2. Open `/api/health` on your Curia address. `checks.mcp.google_workspace` should read `ok`.
3. In the console chat, ask Curia to create a Google Doc called "Curia test". It should reply with a link that opens.

If Drive calls fail with `403`, the file isn't shared with Curia's account. If they fail with `401`, the token was revoked or expired: the Google Workspace step reads **token rejected**. Sign in as Curia again.

## What your principal will notice

- Curia sends them links to Google Docs, Sheets and Drive files it has made. The files live in Curia's Drive, and your principal always gets edit access.
- Shares come from Curia's Google address, so that's the name they'll see in Google's sharing emails.
- To let Curia read or work on one of their own files or folders, they share it with Curia's Google address as an **Editor**, the same way they'd share with a colleague.
