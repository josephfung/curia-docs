## What this is for

This page gets Curia running on a server you control. `install.sh` pulls the published container image, generates your secrets, starts the database and app in Docker and runs migrations. Nothing is built from source, so you don't need Node, pnpm or a checkout of the code.

When you're done, Curia is running and you can sign in to its console. It can't reach anyone yet: you connect its email, a way to message your principal and its voice on the next pages.

<Note>
  Want to change Curia's code, not just run it? [Build from source](/get-started/development) instead.
</Note>

## What you'll need

- **A host with Docker and the Compose plugin.** Docker 20.10 or later: [Docker Desktop](https://www.docker.com/products/docker-desktop/) or the standalone CLI.
- **curl**, to download the installer.
- **An Anthropic API key** (it starts with `sk-ant-`). The installer asks for it and won't continue without one. Get one at [console.anthropic.com](https://console.anthropic.com); usage is billed by Anthropic. OpenRouter and Amazon Bedrock also work, but only with configuration changes after install (see the [configuration reference](/references/configuration)).
- **A domain pointing at the host,** with ports 80 and 443 open. Create a DNS A record for it before you start. If you already terminate TLS at your own proxy or load balancer, you can use that instead.

You don't need Node, pnpm or openssl on the host. Migrations, secret generation and vault seeding all run inside the image.

**Time:** a few minutes once the host and DNS record are ready. Connecting everything else takes an hour or two, at your own pace. See [What to expect](/get-started/what-to-expect).

### Why HTTPS by default

Run Curia on its own domain with HTTPS unless you're only trying it out:

- Browsers only allow microphone access on HTTPS (or on `localhost`), so voice calls from the console need it.
- SMS needs a public HTTPS address for the Telnyx webhook.
- The phone app and your principal's email sign-in will need it too. Both are coming soon.

A local install on `http://localhost:3000` is fine for a try-out on your own machine. It isn't a setup you can hand to a principal.

## Steps

<Steps>
  <Step title="Download the installer">
    ```bash
    curl -fsSL https://github.com/josephfung/curia/releases/latest/download/install.sh -o install.sh
    ```

    <Warning>
      Download the script first, then run it. Don't pipe curl into bash (`curl … | bash`): the installer asks questions and needs a real terminal. It also gives you a chance to read the script first.
    </Warning>

    <Note>
      By default the installer uses the **latest release**, for both the config files and the container image. Set `CURIA_VERSION` to choose a different one; it pins the config and the image together:

      - `CURIA_VERSION=v0.40.1 bash install.sh` pins a specific release.
      - `CURIA_VERSION=edge bash install.sh` tracks the newest `main` build (for testing).

      The Postgres image is versioned separately, by its major version (`CURIA_POSTGRES_TAG=pg16`). On a re-run of an existing install, `CURIA_VERSION` doesn't change the image tag: edit `CURIA_IMAGE_TAG` in `.env` and run `docker compose pull` to upgrade.
    </Note>
  </Step>

  <Step title="Run it">
    ```bash
    bash install.sh
    ```

    The installer:

    - checks that Docker, the Compose plugin and curl are available;
    - fetches the compose files and the `.env` template next to the script;
    - generates the database password and the vault master key (`SECRET_ENCRYPTION_KEY`) and writes them to `.env`;
    - asks for your Anthropic API key;
    - asks how you'll reach Curia (next step);
    - pulls the image, starts Postgres, runs migrations and seeds the encrypted vault;
    - starts Curia and waits for it to report healthy.

    Secrets go into the [encrypted vault](/get-started/secrets-vault). Only the four bootstrap values needed to reach and unlock it stay in `.env`.
  </Step>

  <Step title="Choose how you'll reach Curia">
    The installer offers three options. Its default is **1**, but for a real setup choose **2**:

    - **2 — Public domain + HTTPS.** Recommended. A bundled Caddy proxy gets a Let's Encrypt certificate automatically. Enter your domain when asked.
    - **3 — Public IP / my own proxy.** Plain HTTP on port 3000, for when your own proxy or load balancer handles TLS.
    - **1 — Local / evaluation.** `http://localhost:3000`, no TLS. For a try-out on your own machine only.

    Re-running the installer won't ask this again. To change topology later, see [Deployment and self-hosting](/get-started/deployment).
  </Step>

  <Step title="Save your bootstrap secret">
    When the installer finishes, it prints your console address and a **bootstrap secret**:

    ```
    ╔══════════════════════════════════════════════════════════════════════╗
    ║   Curia is running.                                                    ║
    ║   Open:    https://curia.example.com                                   ║
    ║   Bootstrap secret (save this to a password manager):                  ║
    ║   a1b2c3d4...                                                          ║
    ╚══════════════════════════════════════════════════════════════════════╝
    ```

    Save the bootstrap secret in a password manager now. It's how you sign in, and the installer won't show it again.
  </Step>

  <Step title="Sign in and fill in the setup form">
    Open the address from the summary and paste the bootstrap secret into the **Access key** field.

    Curia opens its setup form at `/setup`. It has six steps:

    1. **About you:** a name.
    2. **Your details:** timezone, email, preferred name, title and working hours.
    3. **Assistant identity:** Curia's name, title and email signature.
    4. **Tone & style:** how Curia sounds, started from a template, plus a detail level.
    5. **Autonomy & preferences:** how independently Curia acts, and any standing preferences.
    6. **Review:** check everything, then **Confirm & save**.

    The form speaks to "you" as the executive Curia works for: the name, email and timezone are your principal's. If you're setting Curia up for someone else, enter their details.

    When you save, Curia restarts if it needs to bring channels online ("Setting up channels…"), then opens the chat view at `/chat`.
  </Step>

  <Step title="Meet the setup agent">
    At `/chat`, the setup agent greets you. It starts with a few quick wins that need no credentials: Curia's persona, a scheduled debrief, how Curia refers to your principal, and a tour of what's ready. Then it helps you connect the rest, one item at a time. You can stop at any point and pick up in a later session.

    <Warning>
      Add an embedding source soon after you install. Without one, Curia's memory is off and the setup agent can't check what you've already set up. See [Search and memory](/get-started/search-and-memory).
    </Warning>
  </Step>
</Steps>

<Accordion title="Running the installer again">
  `install.sh` is safe to re-run. After a fresh install completes, it writes a `SETUP_COMPLETE` marker to `.env`, and every later run takes an **upgrade/restart** path:

  - **No secrets are regenerated.** Your database credentials and vault master key are kept, so existing encrypted secrets stay readable.
  - **Migrations are re-applied safely.** Already-applied migrations are skipped.
  - **The vault is checked, not re-seeded.** The installer confirms the required secrets are present and fails loudly if any are missing, rather than overwriting them.

  Re-running is the normal way to upgrade or restart the stack.
</Accordion>

## Check it works

- The installer ends with **Curia is running.**
- You can sign in at your domain over HTTPS, and the browser shows a valid certificate.
- The health endpoint answers. From any machine:

  ```bash
  curl https://curia.example.com/api/health
  ```

  `"status"` should be `"ok"`. Channel checks such as `email`, `signal` and `sms` read `"skipped"` until you connect them. That's expected. See [Health monitoring](/get-started/health-monitoring) for every field.
- The setup form saved and you're in `/chat` with the setup agent.

## What your principal will notice

Nothing yet. Curia has no email, messaging or voice connected, so it can't contact anyone. Your principal first hears from Curia once you've connected a channel to reach them.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Re-running the installer on an existing install">
    This is expected and safe. Once the first install completes, `install.sh` finds the `SETUP_COMPLETE` marker in `.env` and switches to upgrade/restart mode: it never regenerates secrets, re-applies migrations safely, and checks (rather than re-seeds) the vault. If the vault check fails because required secrets are missing, run a fresh install from a clean directory.
  </Accordion>

  <Accordion title="Postgres connection refused">
    Confirm the container is running:

    ```bash
    docker compose ps
    ```

    The database password is generated during install and passed to the container through `.env`, so the credentials match by default. If you've edited `.env` by hand, check that `DATABASE_URL` still matches `DB_USER` and `DB_PASSWORD`.
  </Accordion>

  <Accordion title="Let's Encrypt certificate isn't issued (HTTPS option)">
    Caddy requests a certificate on first start. It needs a DNS A record for your domain pointing at the host, ports 80 and 443 reachable from the internet, and the right `DOMAIN` value in `.env`. Check the proxy logs for the result:

    ```bash
    docker compose logs caddy
    ```
  </Accordion>
</AccordionGroup>

## Updating Curia

Curia applies pending database migrations automatically on every startup and skips ones already applied. Updating is pulling the new images and restarting. There's no manual SQL step.

<Warning>
  Back up your database before updating. A fresh dump makes an interrupted migration much easier to recover from.
</Warning>

<Steps>
  <Step title="Back up the database">
    ```bash
    docker compose exec -T postgres pg_dump -U curia -Fc curia > curia-backup-$(date +%Y%m%d).dump
    ```

    This writes a compressed dump you can restore with `pg_restore`. Keep it until you've confirmed the update is healthy.
  </Step>

  <Step title="Pull and restart">
    ```bash
    docker compose pull
    docker compose up -d
    ```

    On startup Curia runs any pending migrations before serving traffic. Watch the logs (`docker compose logs -f curia`) until `/api/health` reports `"ok"`.
  </Step>

  <Step title="Roll back if needed">
    If an update misbehaves, restore the backup. Stop Curia so nothing is writing, restore (`--clean --if-exists` drops and recreates objects), then start the stack again:

    ```bash
    docker compose stop curia
    docker compose exec -T postgres pg_restore -U curia -d curia --clean --if-exists < curia-backup-YYYYMMDD.dump
    docker compose up -d
    ```

    Replace `YYYYMMDD` with your dump's date.
  </Step>
</Steps>
