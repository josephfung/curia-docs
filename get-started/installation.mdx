---
title: "Install Curia"
description: "Run Curia from the published container image with a single script — no source checkout, no toolchain, just Docker."
---

Getting Curia running takes one script and about five minutes. `install.sh` pulls the published container image, generates your secrets, starts the database and app in Docker, and runs migrations — the only thing you provide is an Anthropic API key. Nothing is built from source, so you don't need Node, pnpm, or a checkout of the code. Once it's running, you finish configuration inside the app and add optional capabilities (email, search, Signal) whenever you need them.

<Note>
  Want to modify Curia, not just run it? The [build from source](/get-started/development) path clones the repo and hot-reloads your changes. This page is the fastest route to a running instance.
</Note>

## Prerequisites

The image-based install runs everything inside the container, so the host needs very little:

- **Docker with the Compose plugin** — Postgres and the app both run in Docker; install [Docker Desktop](https://www.docker.com/products/docker-desktop/) or the standalone CLI (Docker 20.10+)
- **curl** — used once to download the installer and the compose files

<Note>
  You do **not** need Node, pnpm, or openssl on the host. Migrations, secret generation, and vault seeding all run inside the pulled image.
</Note>

## Quick start

<Steps>
  <Step title="Download the installer">
    ```bash
    curl -fsSL https://github.com/josephfung/curia/releases/latest/download/install.sh -o install.sh
    ```

    <Warning>
      Download the script first, then run it — do **not** pipe curl straight into bash (`curl … | bash`). The installer uses interactive prompts that need a real terminal, and piped input has no TTY. Reviewing the script before running it is also just good practice.
    </Warning>

    <Note>
      By default the installer uses the **latest release** — both the config files and the container image come from it. Set `CURIA_VERSION` to choose a different one; it pins the config *and* the image together:

      - `CURIA_VERSION=v0.40.1 bash install.sh` — pin a specific release.
      - `CURIA_VERSION=edge bash install.sh` — track the newest `main` build (advanced / testing).

      The Postgres image is a separate axis, versioned by its major (`CURIA_POSTGRES_TAG=pg16`) rather than the Curia release. On a re-run of an existing install, `CURIA_VERSION` does not change the image tag — edit `CURIA_IMAGE_TAG` in `.env` and `docker compose pull` to upgrade.
    </Note>
  </Step>

  <Step title="Run it">
    ```bash
    bash install.sh
    ```

    The installer does everything needed to get Curia running, without a source checkout:

    - Checks that Docker, the Compose plugin, and curl are available
    - Fetches the compose files and the `.env` template next to the script
    - Generates the database password and the vault master key (`SECRET_ENCRYPTION_KEY`) and writes them to `.env`
    - Prompts you for an Anthropic API key — get one at [console.anthropic.com](https://console.anthropic.com)
    - Asks how you'll reach Curia (the deployment topology step below)
    - Pulls the published image, starts Postgres, runs database migrations **inside the image**, and seeds the encrypted vault
    - Brings the full Curia stack up and waits for it to become healthy

    The Anthropic key is the only value you supply. Everything else is generated for you. Secrets land in the [encrypted vault](/get-started/secrets-vault); only the four bootstrap values needed to reach and unlock it stay in `.env`.
  </Step>

  <Step title="Choose your deployment topology">
    The installer asks how you plan to reach the instance and configures the stack accordingly:

    - **Local / evaluation** — `http://localhost:3000`, no TLS. The right choice for a laptop or a quick trial.
    - **Public domain + HTTPS** — automatic Let's Encrypt certificates via a bundled Caddy reverse proxy. You supply a domain (with a DNS A record pointing at the host and ports 80/443 open).
    - **Public IP / my own proxy** — plain HTTP on `:3000`, for when you terminate TLS at an upstream load balancer or proxy.

    You can change this later by editing `.env` and re-running the installer.
  </Step>

  <Step title="Save your bootstrap secret">
    When the installer finishes, it prints a summary box with your login URL and a **bootstrap secret**:

    ```
    ╔══════════════════════════════════════════════════════════════════════╗
    ║   Curia is running.                                                    ║
    ║   Open:    http://localhost:3000                                       ║
    ║   Bootstrap secret (save this to a password manager):                  ║
    ║   a1b2c3d4...                                                          ║
    ╚══════════════════════════════════════════════════════════════════════╝
    ```

    Save the bootstrap secret to a password manager now. You'll use it to log in, and it won't be shown again.
  </Step>

  <Step title="Log in and finish in the app">
    Open your instance (`http://localhost:3000` for a local install, or your domain) and enter your bootstrap secret to create your account.

    Once you're in, the **setup wizard** at `/setup` runs automatically. It's a six-step form: your name (the CEO Curia works for), your operational details (timezone, email, working hours), the assistant's identity, baseline tone, decision-making posture, and a review screen. Submitting the last step writes everything through, restarts external channels if needed, and drops you directly into the chat view at `/chat`.

    At `/chat`, the **setup-wizard specialist agent** greets you and takes an outcome-backward approach: it surfaces what's already done, asks what you most want Curia to do for you, and walks you to the shortest path to that first working integration. Remaining tasks can be deferred and picked up in any future session. The whole thing takes a few minutes and makes every subsequent interaction noticeably more useful.

    <Note>
      Checkpoint: Curia is running on Anthropic and Postgres. Agents are live, the web app is working, and the assistant knows enough about you to be useful. Add email, semantic search, or Signal below whenever you need them.
    </Note>
  </Step>
</Steps>

<Accordion title="Running the installer again">
  `install.sh` is safe to re-run. Once a fresh install completes, it writes a `SETUP_COMPLETE` marker to `.env`, and every subsequent run takes a non-rotating **upgrade/restart** path:

  - **No secrets are regenerated** — your database credentials and vault master key are preserved, so existing encrypted secrets stay readable.
  - **Migrations are re-applied idempotently** — already-applied migrations are skipped, so this is safe on every run and is how you pick up a new image version.
  - **The vault is verified, not re-seeded** — the installer confirms the required secrets are present and fails loudly if any are missing, rather than overwriting them.

  Because secrets are never silently regenerated, re-running is the normal way to upgrade or restart the stack.
</Accordion>

## Full setup

The quick start gives you a running instance on Anthropic and Postgres. The capabilities below are optional and independent — add them in any order, only when you need them.

Each one follows the same pattern: add the credential to the [encrypted vault](/get-started/secrets-vault) via the Curia console (Settings → Channels for channel credentials), then recreate the Curia container to pick up the change:

```bash
docker compose up -d --force-recreate curia
```

### Email (Nylas)

Curia uses [Nylas](https://nylas.com) as its email layer — a unified API that handles IMAP and SMTP complexity and provides a consistent interface across Gmail, Outlook, and other providers.

<Steps>
  <Step title="Create a Nylas account">
    Sign up at [app.nylas.com](https://app.nylas.com). The free tier is sufficient for development.
  </Step>

  <Step title="Create an application">
    In the Nylas dashboard, create a new application and choose **Email** as the product. Once created, copy your **API key** (stored as `nylas_api_key` in the vault).
  </Step>

  <Step title="Add credentials via the console">
    In the Curia console, go to **Settings → Channels → Email** and enter your Nylas API key. Then go to **Email accounts** and add an account — paste the Nylas Grant ID for that mailbox. The console stores these in the vault automatically.

    <Warning>
      Use a dedicated email account rather than your primary inbox for development. Curia reads and processes all incoming messages.
    </Warning>
  </Step>

  <Step title="Apply the change">
    ```bash
    docker compose up -d --force-recreate curia
    ```

    The email channel activates automatically when all three vault keys (`nylas_api_key`, `nylas_grant_id`, `nylas_self_email`) are present.
  </Step>
</Steps>

### Semantic search and entity memory (OpenAI)

OpenAI's `text-embedding-3-small` model powers entity memory and semantic search in the knowledge graph. Without it, knowledge graph lookups are exact-match only.

Get an API key from [platform.openai.com](https://platform.openai.com) and add it to the vault as `openai_api_key` via the Curia console (Settings → Channels). Then recreate the container to apply it:

```bash
docker compose up -d --force-recreate curia
```

### Web research (Tavily)

Tavily powers the `web-search` tool, which lets agents research topics and look up current information during tasks.

<Steps>
  <Step title="Get a Tavily API key">
    Sign up at [tavily.com](https://tavily.com) and copy your API key from the dashboard.
  </Step>

  <Step title="Add the key to the vault">
    In the Curia console, go to **Settings → Channels → Web search** and enter the key (stored as `tavily_api_key`).
  </Step>

  <Step title="Enable the web-search tool">
    `web-search` declares `tavily_api_key` in its `install.requires_secrets`, so it stays disabled until the key is in the vault. Once added, enable the tool from the Settings registry in the console, then recreate the container:

    ```bash
    docker compose up -d --force-recreate curia
    ```

    See [Managing skills, agents, and channels](/core-concepts/registry) for the registry workflow.
  </Step>
</Steps>

### Signal messaging

Signal messaging runs via [signal-cli](https://github.com/AsamK/signal-cli). Docker Compose manages the socket path automatically — the only thing you need to provide is your phone number.

<Steps>
  <Step title="Bootstrap signal-cli">
    Signal requires registering a phone number with signal-cli and seeding the `signal-data` Docker volume with the resulting credentials. Refer to your deployment documentation for the bootstrap procedure.
  </Step>

  <Step title="Add your phone number to the vault">
    In the Curia console, go to **Settings → Channels → Signal** and enter the E.164 number you registered (e.g. `+12223334444`). It is stored under the vault key `channel.signal.phone_number`. Do not configure `SIGNAL_SOCKET_PATH` — the deployment layer manages this automatically.
  </Step>

  <Step title="Apply the change">
    ```bash
    docker compose up -d --force-recreate curia
    ```

    The Signal channel activates when `channel.signal.phone_number` is in the vault and the `signal-data` volume is populated.
  </Step>
</Steps>

## Updating Curia

Curia applies pending database migrations automatically on every startup, under an
advisory lock, and skips migrations that are already applied. Updating is therefore
just pulling the new images and restarting; a schema-changing version bump migrates
unattended, and re-running when you're already up to date is a safe no-op. There is
no manual SQL step.

<Warning>
  Always back up your database before updating. Migrations move your schema forward,
  and a bad interruption mid-migration is far easier to recover from with a fresh dump
  in hand.
</Warning>

<Steps>
  <Step title="Back up the database">
    ```bash
    docker compose exec -T postgres pg_dump -U curia -Fc curia > curia-backup-$(date +%Y%m%d).dump
    ```

    This writes a compressed, custom-format dump you can restore with `pg_restore`.
    Keep it until you've confirmed the update is healthy.
  </Step>

  <Step title="Pull and restart">
    ```bash
    docker compose pull
    docker compose up -d
    ```

    On startup the app runs any pending migrations before serving traffic. Watch the
    logs (`docker compose logs -f curia`) — a successful boot ends with the health
    check passing at `http://localhost:3000/api/health`.
  </Step>

  <Step title="Roll back if needed">
    If an update misbehaves, restore the backup in place. Stop the app so nothing
    is writing, restore (`--clean --if-exists` drops and recreates objects), then
    bring the stack back up:

    ```bash
    docker compose stop curia
    docker compose exec -T postgres pg_restore -U curia -d curia --clean --if-exists < curia-backup-YYYYMMDD.dump
    docker compose up -d
    ```

    Replace `YYYYMMDD` with your dump's date.
  </Step>
</Steps>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Re-running the installer on an existing install">
    This is expected and safe. Once the first install completes, `install.sh` detects the `SETUP_COMPLETE` marker in `.env` and switches to upgrade/restart mode: it never regenerates secrets, re-applies migrations idempotently, and verifies (rather than re-seeds) the vault. If the vault verification fails because required secrets are missing, run a fresh install from a clean directory.
  </Accordion>

  <Accordion title="Postgres connection refused">
    Confirm the container is running:

    ```bash
    docker compose ps
    ```

    The database password is generated during install and shared with the container automatically through `.env`, so the credentials match by default. If you've edited `.env` by hand, make sure `DATABASE_URL` is still consistent with `DB_USER` and `DB_PASSWORD`.
  </Accordion>

  <Accordion title="Email channel not activating">
    All three Nylas secrets must be in the vault: `nylas_api_key`, `nylas_grant_id`, and `nylas_self_email`. If any is missing, the channel disables itself at startup. Confirm they are all present via Settings → Channels → Email in the console, then check the startup logs for a "email channel disabled" or "email adapter disabled" message.

    Remember to recreate the container after adding secrets: `docker compose up -d --force-recreate curia`.
  </Accordion>

  <Accordion title="Let's Encrypt certificate isn't issued (HTTPS topology)">
    Caddy requests a certificate on first start and needs three things in place: a DNS A record for your domain pointing at the host, ports 80 and 443 reachable from the internet, and the `DOMAIN` value set correctly in `.env`. Check the proxy logs for the ACME challenge result:

    ```bash
    docker compose logs caddy
    ```
  </Accordion>
</AccordionGroup>
