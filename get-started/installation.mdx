## What this is for

This page gets Curia running on a server you control. `install.sh` pulls the published container image, generates your secrets, starts the database and app in Docker and runs migrations. Nothing is built from source, so you don't need Node, pnpm or a checkout of the code.

When you're done, Curia is running and you can sign in to its console. It can't reach anyone yet: you connect its email, a way to message your principal and its voice on the next pages.

<Note>
  Want to change Curia's code, not just run it? [Build from source](/get-started/development) instead.
</Note>

## What you'll need

- **A host with Docker and the Compose plugin.** Docker 20.10 or later: [Docker Desktop](https://www.docker.com/products/docker-desktop/) or the standalone CLI. Check the [system requirements](/get-started/system-requirements) for the machine to run Curia on.
- **curl**, to download the installer.
- **An Anthropic API key** (it starts with `sk-ant-`). The installer asks for it and won't continue without one. Get one at [console.anthropic.com](https://console.anthropic.com); usage is billed by Anthropic. OpenRouter and Amazon Bedrock also work, but only with configuration changes after install (see the [configuration reference](/references/configuration)).
- **A domain pointing at the host,** with ports 80 and 443 open. Create a DNS A record for it before you start. If you already run HTTPS on the host (nginx, Traefik, Cloudflare Tunnel or similar), Curia can sit behind it instead.
- **Two more ports for calls,** `7881/tcp` and `7882/udp`, open on the host. Voice comes with every install, and call audio can't go through a proxy. See [Ports to open](/get-started/deployment#ports-to-open).

You don't need Node, pnpm or openssl on the host. Migrations, secret generation and vault seeding all run inside the image.

You don't need an embedding key either. Curia's memory runs on an embedding model bundled in the image, so the knowledge graph works from the first boot. See [Embedding models](/integrations/embeddings-endpoint) to use a different one. (The bundled model is newer than v0.45.0; on that release, memory needs an OpenAI key or your own embedding server, as [Search and memory](/get-started/search-and-memory) explains.)

**Time:** a few minutes once the host and DNS record are ready. Connecting everything else takes an hour or two, at your own pace. See [What to expect](/get-started/what-to-expect).

### Why HTTPS by default

Run Curia on its own domain with HTTPS unless you're only trying it out:

- Browsers only allow microphone access on HTTPS (or on `localhost`), so voice calls from the console need it.
- SMS needs a public HTTPS address for the Telnyx webhook.
- The [phone app](/channels/phone-app) installs on a home screen and sends notifications only from an HTTPS address.

A local install on `http://localhost:3000` is fine for a try-out on your own machine. It has no phone app, so onboarding then needs Signal or SMS. It isn't a setup you can hand to a principal.

## Steps

<Steps>
  <Step title="Download the installer">
    ```bash
    curl -fsSL https://github.com/josephfung/curia/releases/latest/download/install.sh -o install.sh
    ```

    <Warning>
      Download the script first, then run it. Don't pipe curl into bash (`curl … | bash`): the installer asks questions and needs a real terminal. It also gives you a chance to read the script first.
    </Warning>

    <Note>
      By default the installer uses the **latest release**, for both the config files and the container image. Set `CURIA_VERSION` to choose a different one; it pins the config and the image together:

      - `CURIA_VERSION=v0.40.1 bash install.sh` pins a specific release.
      - `CURIA_VERSION=edge bash install.sh` tracks the newest `main` build (for testing).

      The Postgres image is versioned separately, by its major version (`CURIA_POSTGRES_TAG=pg16`). On a re-run of an existing install, `CURIA_VERSION` doesn't change the image tag: edit `CURIA_IMAGE_TAG` in `.env` and run `docker compose pull` to upgrade.
    </Note>
  </Step>

  <Step title="Run it">
    ```bash
    bash install.sh
    ```

    The installer:

    - checks that Docker, the Compose plugin and curl are available;
    - fetches the compose files, the `.env` template, the Caddyfile, the browser container's seccomp profile (`docker/seccomp-chrome.json`) and LiveKit's configs (`docker/livekit.yaml` and `docker/livekit.local.yaml`) next to the script;
    - generates the database password and the vault master key (`SECRET_ENCRYPTION_KEY`) and writes them to `.env`;
    - asks for your Anthropic API key;
    - asks how you'll reach Curia (next step);
    - generates a key and secret for LiveKit, the server that carries call audio, and turns it on in `.env`;
    - pulls the images, starts Postgres, runs migrations and seeds the encrypted vault, including LiveKit's address and keys;
    - starts Curia, its [browser container](/integrations/web-browser) and LiveKit, and waits for Curia to report healthy.

    Secrets go into the [encrypted vault](/get-started/secrets-vault). Only the four bootstrap values needed to reach and unlock it stay in `.env`, plus LiveKit's own key pair, which LiveKit reads from there. You never enter LiveKit's settings yourself: see [Voice](/get-started/voice).
  </Step>

  <Step title="Choose how you'll reach Curia">
    The installer asks **How will people reach Curia?** and offers three options. If you're not sure, choose **1**, the default (press Enter):

    - **1 — My domain, with HTTPS set up for me (recommended).** Curia gets its own certificate from Let's Encrypt, through a bundled Caddy proxy. Enter your domain when asked. It needs the domain pointing at the server and ports 80 and 443 open. If something on the server already uses port 80 or 443, the installer warns you and suggests option 2.
    - **2 — My domain, behind HTTPS I already run.** For servers that already have nginx, Traefik, Cloudflare Tunnel or similar in front. Curia listens on port 3000 behind it. The installer asks for the public address your proxy serves Curia on, such as `https://curia.example.com`; press Enter to keep `localhost` for testing. An `http://` address works, with a warning, but the phone app needs `https`. Your proxy then needs two forwarding rules: see [How people reach it](/get-started/deployment#how-people-reach-it).
    - **3 — Just this computer, to try it out.** `http://localhost:3000`. No phone app, so onboarding then needs Signal or SMS.

    Re-running the installer won't ask this again. For what each option sets up, or to change it later, see [Deployment](/get-started/deployment#how-people-reach-it).
  </Step>

  <Step title="Save your bootstrap secret">
    When the installer finishes, it prints the address of the Setup page and a **bootstrap secret**:

    ```
    ╔══════════════════════════════════════════════════════════════════════╗
    ║   Curia is running.                                                    ║
    ║   Open:    https://curia.example.com/setup                             ║
    ║   Bootstrap secret (save this to a password manager):                  ║
    ║   a1b2c3d4...                                                          ║
    ║   Enter it on the login page to create your account.                   ║
    ║   You won't be shown it again here.                                    ║
    ╚══════════════════════════════════════════════════════════════════════╝
    Finish setting up Curia in your browser at the address above.
    Guide: https://docs.meetcuria.com/get-started/check-your-setup
    When every step is done, choose Start onboarding.

    Open these ports for calls: 7881/tcp, 7882/udp
    ```

    Save the bootstrap secret in a password manager now. It's how you sign in, and the installer won't show it again.

    On option 3 the address is `http://localhost:3000/setup`, and there are no ports to open. On option 2 with a public address, the installer also prints what your proxy must forward.
  </Step>

  <Step title="Sign in and open the Setup page">
    Open the address from the summary and paste the bootstrap secret into the **Access key** field.

    The console opens on the **Setup page** at `/setup`. It walks you through every step, from who Curia is for to **Start onboarding**, and takes every key on the step itself. The setup guide, Curia's own chat, opens beside it the first time, to answer questions as you go.

    See [The Setup page](/get-started/check-your-setup) for the steps and what each needs.

    <Note>
      Curia's memory, which the setup guide uses, works out of the box on the bundled embedding model. To build memory from conversations, turn on fact extraction later: see [Search and memory](/get-started/search-and-memory).
    </Note>
  </Step>
</Steps>

<Accordion title="Running the installer again">
  `install.sh` is safe to re-run. After a fresh install completes, it writes a `SETUP_COMPLETE` marker to `.env`, and every later run takes an **upgrade/restart** path:

  - **No secrets are regenerated.** Your database credentials and vault master key are kept, so existing encrypted secrets stay readable.
  - **Migrations are re-applied safely.** Already-applied migrations are skipped.
  - **The vault is checked, not re-seeded.** The installer confirms the required secrets are present and fails loudly if any are missing, rather than overwriting them.
  - **Voice is left as it is.** LiveKit's settings in `.env` and its values in the vault are never changed. If voice is off, as on installs made before LiveKit came with Curia, the installer says so: see [Turn voice on for an existing install](/channels/voice-setup#turn-voice-on-for-an-existing-install).

  Re-running is the normal way to upgrade or restart the stack.
</Accordion>

## Check it works

- The installer ends with **Curia is running.**
- You can sign in at your domain over HTTPS, and the browser shows a valid certificate.
- The health endpoint answers. From any machine:

  ```bash
  curl https://curia.example.com/api/health
  ```

  `"status"` should be `"ok"`, and `"knowledge_graph"` should read `"ok"` (Curia's memory is on). Channel checks such as `email`, `signal` and `sms` read `"skipped"` until you connect them. That's expected. See [Health monitoring](/get-started/health-monitoring) for every field.
- You're signed in and the console shows the Setup page.

## What your principal will notice

Nothing yet. Curia has no email, messaging or voice connected, so it can't contact anyone. Your principal first hears from Curia once you've connected a channel to reach them.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Re-running the installer on an existing install">
    This is expected and safe. Once the first install completes, `install.sh` finds the `SETUP_COMPLETE` marker in `.env` and switches to upgrade/restart mode: it never regenerates secrets, re-applies migrations safely, and checks (rather than re-seeds) the vault. If the vault check fails because required secrets are missing, run a fresh install from a clean directory.
  </Accordion>

  <Accordion title="Postgres connection refused">
    Confirm the container is running:

    ```bash
    docker compose ps
    ```

    The database password is generated during install and passed to the container through `.env`, so the credentials match by default. If you've edited `.env` by hand, check that `DATABASE_URL` still matches `DB_USER` and `DB_PASSWORD`.
  </Accordion>

  <Accordion title="Let's Encrypt certificate isn't issued (HTTPS option)">
    Caddy requests a certificate on first start. It needs a DNS A record for your domain pointing at the host, ports 80 and 443 reachable from the internet and free for Caddy, and the right `DOMAIN` value in `.env`. If the installer warned that something already uses port 80 or 443, another web server is in the way: stop it, or put Curia behind it as in [How people reach it](/get-started/deployment#how-people-reach-it). Check the proxy logs for the result:

    ```bash
    docker compose logs caddy
    ```
  </Accordion>
</AccordionGroup>

## Updating Curia

Curia applies pending database migrations automatically on every startup and skips ones already applied. Updating is pulling the new images and restarting. There's no manual SQL step.

Some releases also need a change to your `docker-compose.yml` or `.env`, which an update never makes for you. Read the [upgrade notes](/references/releases#upgrade-notes) before you update from an earlier release.

<Warning>
  Back up your database before updating. A fresh dump makes an interrupted migration much easier to recover from.
</Warning>

<Steps>
  <Step title="Back up the database">
    ```bash
    docker compose exec -T postgres pg_dump -U curia -Fc curia > curia-backup-$(date +%Y%m%d).dump
    ```

    This writes a compressed dump you can restore with `pg_restore`. Keep it until you've confirmed the update is healthy.
  </Step>

  <Step title="Pull and restart">
    ```bash
    docker compose pull
    docker compose up -d
    ```

    On startup Curia runs any pending migrations before serving traffic. Watch the logs (`docker compose logs -f curia`) until `/api/health` reports `"ok"`.
  </Step>

  <Step title="Roll back if needed">
    If an update misbehaves, restore the backup. Stop Curia so nothing is writing, restore (`--clean --if-exists` drops and recreates objects), then start the stack again:

    ```bash
    docker compose stop curia
    docker compose exec -T postgres pg_restore -U curia -d curia --clean --if-exists < curia-backup-YYYYMMDD.dump
    docker compose up -d
    ```

    Replace `YYYYMMDD` with your dump's date.
  </Step>
</Steps>
