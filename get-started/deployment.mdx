<Note>
  This page describes the install as of **v0.46**, which adds local speech and turns voice on by default. Earlier releases have no `speech` container and need only 4 GB of RAM.
</Note>

Curia is single-tenant and self-hosted: one instance per principal, on a server you control. The [installer](/get-started/installation) sets it up as a Docker Compose stack. Most of that stack isn't Curia's own code: Curia ships open-source pieces alongside its runtime, including a database, a browser, a call server, speech models and an MCP server. This page shows every piece, where it comes from and what it can reach.

[Architecture](/core-concepts/architecture) describes how Curia works inside its own process. This page describes what runs on the server.

## The containers

| Container | Image | What runs in it | Reaches |
|---|---|---|---|
| **caddy** | `caddy` (upstream) | Caddy, terminating HTTPS with a Let's Encrypt certificate | curia, and livekit for call signaling (`/rtc*`) |
| **curia** | `curia` | Curia's runtime (agents, channels, scheduler), the console and phone app, **workspace-mcp** (the Google Workspace MCP server, run as a subprocess) and the **all-MiniLM-L6-v2** embedding model, run in-process | Every other container, and every outside service |
| **postgres** | `curia-postgres` | PostgreSQL 16 with pgvector and pgAudit. Holds memory, the encrypted vault and the audit log | Nothing |
| **speech** | `curia-speech` | Curia's speech service, running Parakeet (speech to text), Pocket TTS (text to speech) and Silero (detecting when someone is speaking) | Nothing: it has no internet access |
| **browser** | `curia-browser` | Chromium, run headful on Xvfb, behind Curia's egress guard, which refuses private and local addresses | The open web only |
| **livekit** | `livekit-server` (upstream) | LiveKit, the real-time server that carries call audio. The installer starts it with keys it generates | Curia's voice agent |

Images named `curia-*` are built and published with each Curia release, from the same commit and under the same tag. Updating Curia updates them. `caddy` and `livekit-server` come from their projects unchanged. The Curia image runs as a non-root `curia` user; see the [security overview](/security/overview) for the container security model.

### What can read your secrets

Only the **curia** container. It holds `SECRET_ENCRYPTION_KEY`, the key that decrypts the [vault](/get-started/secrets-vault), and the vault itself lives encrypted in Postgres. The browser runs page code from the open web, so it is kept apart on purpose:

- It gets no environment file.
- It joins its own network, shared only with curia, so it has no route to Postgres.
- Its DevTools port isn't published.

The speech container has no internet access once its models are downloaded.

## How people reach it

The installer asks once, on a fresh install, **How will people reach Curia?** Your answer decides who provides HTTPS, and where calls connect. Every option starts LiveKit for calls.

| Option | What the installer sets up | Use it when |
|---|---|---|
| **1. My domain, with HTTPS set up for me** (recommended, the default) | The bundled Caddy on ports 80 and 443, with a Let's Encrypt certificate it renews itself. Caddy sends call signaling (`/rtc*`) to LiveKit and everything else to Curia. It sets `DOMAIN`, adds `docker-compose.tls.yml` to `COMPOSE_FILE` and sets `APP_ORIGIN=https://<your-domain>` in `.env`. Calls connect to `wss://<your-domain>`. | Curia runs on a server with a domain. You need a DNS A record pointing at the host, and ports 80 and 443 open, before you start. The installer warns if something already uses port 80 or 443. |
| **2. My domain, behind HTTPS I already run** | No Caddy. Curia serves plain HTTP on port `3000` for your proxy. The installer asks for the public address your proxy serves Curia on, sets `APP_ORIGIN` to it, and points calls at the same host (`wss://<host>`). Press Enter instead to keep `localhost`, for testing. | nginx, Traefik, Cloudflare Tunnel or similar already handles HTTPS in front of the host. |
| **3. Just this computer, to try it out** | No Caddy, at `http://localhost:3000`. Calls connect to `ws://localhost:7880`. | A try-out on your own machine. There's no phone app, so onboarding then needs Signal or SMS. |

On option 2, your proxy must forward:

- `/` to port `3000` on the Curia host;
- `/rtc*` to `127.0.0.1:7880` on the Curia host, for call signaling. A proxy on another machine can't reach that address: set `LIVEKIT_HTTP_BIND` in `.env` so LiveKit listens on an interface it can reach.

An `http://` address is accepted with a warning: the browser works, but the phone app needs `https`.

To move an existing install to option 1, set `DOMAIN=<your domain>`, `COMPOSE_FILE=docker-compose.yml:docker-compose.tls.yml` and `APP_ORIGIN=https://<your domain>` in `.env`, then run `docker compose up -d`. Behind your own proxy, set `APP_ORIGIN` to the address people use to reach Curia and add the forwarding rules above. Either way, change the LiveKit URL under **Settings → Channels → Voice** to match (see [Voice credentials](/channels/voice-setup#credentials)), and if the install was made for just this computer, set `LIVEKIT_COMMAND="--config /etc/livekit.yaml"` in `.env` so LiveKit advertises the server's public address. Re-running the installer on a finished install doesn't ask the question again.

With `APP_ORIGIN` set to an `https://` address, session cookies are marked `Secure` and the API accepts browser requests from that origin alone. Open the console at `https://<your-domain>`, not `http://<server>:3000`.

## Ports to open

| Port | Container | Why |
|---|---|---|
| `80`, `443` | caddy | The console, the phone app, call signaling and SMS webhooks from Telnyx, over HTTPS. Behind your own proxy, that proxy holds these instead |
| `7881/tcp`, `7882/udp` | livekit | Call audio over WebRTC, on options 1 and 2. Without these, calls connect with no sound |

Docker's published ports bypass host firewalls such as UFW, so open these in your cloud provider's firewall. Nothing else is published on a public interface:

- **Postgres listens on `127.0.0.1:5432`.** Curia reaches it over the compose network, and the installer runs migrations inside the container. For remote access, prefer an SSH tunnel (`ssh -L 15432:127.0.0.1:5432 <server>`, then connect to `localhost:15432`). Publishing it is an explicit opt-in: set `POSTGRES_BIND` in `.env` to `0.0.0.0`, `::` or an interface address.
- **Port `3000` follows your network setup.** On the HTTPS and local options, the installer sets `HTTP_BIND=127.0.0.1`, so `3000` is reachable only from the server and Caddy reaches Curia over the compose network. Anything that used `<server>:3000` directly, such as an uptime probe, should use `https://<your-domain>`. On the own-proxy option, `HTTP_BIND` is empty and `3000` is published on every interface, so allow it only from your proxy.

<Warning>
  `install.sh` never overwrites an existing `docker-compose.yml`, so an update keeps your old one, hand-edits included. Compose files from before v0.45 publish Postgres on **every** network interface. Edit the postgres `ports:` entry to read `- "${POSTGRES_BIND:-127.0.0.1}:${POSTGRES_PORT:-5432}:5432"`, then run `docker compose up -d postgres` so the container is recreated; editing the file alone changes nothing. On an HTTPS install, also change the curia entry to `- "${HTTP_BIND:-}:${HTTP_PORT:-3000}:3000"`.

  `install.sh` checks what Docker actually published, stops and asks while Postgres is exposed, and warns when port 3000 ignores `HTTP_BIND`. To check by hand, run `ss -tlnp | grep 5432`: it should show `127.0.0.1:5432`.
</Warning>

### How channels reach Curia

Most channels don't need an open port: Curia connects out to them. Turning one on doesn't change your firewall, except SMS.

| Channel | How it connects | Open port |
|---|---|---|
| Console, phone app | The person's browser or phone connects in | `443`, plus LiveKit's ports for calls |
| SMS (Telnyx) | Telnyx posts each message to Curia as a webhook | `443` |
| Email (Nylas) | Curia checks Nylas for new mail | None |
| Slack | Curia holds an outbound connection to Slack (Socket Mode) | None |
| Signal | Curia talks to signal-cli on the same host, which connects out to Signal | None |

## Volumes and backups

| Volume | Holds | If you lose it |
|---|---|---|
| `pgdata` | Memory, the vault, the audit log, everything Curia knows | **Gone.** Back this up |
| speech models | Speech model weights | Re-downloaded |
| `browser_profile` | The browser's sign-ins and cookies | Sign in to those sites again |
| `google_workspace_tokens` | Curia's Google Workspace sign-in | Sign Curia in to Google again |
| `caddy-data` | Caddy's certificates | Caddy requests new ones |

Back up `pgdata` together with `.env`, and keep `.env` out of version control. `.env` holds only bootstrap values (`DB_USER`, `DB_PASSWORD`, `DATABASE_URL` and `SECRET_ENCRYPTION_KEY`) and LiveKit's own key pair (`LIVEKIT_KEYS`); every other credential is in the vault. Keep a separate copy of `SECRET_ENCRYPTION_KEY` somewhere off the server, such as a password manager. Without it the vault can't be decrypted, and every stored secret has to be entered again.

## Outside services

| Service | Used for | Needed? |
|---|---|---|
| AI model provider (Anthropic, OpenRouter and others) | Every agent's reasoning | Yes |
| Nylas | Curia's mailbox, and the principal's mail and calendar | For email and calendar |
| Google Workspace | Docs, Sheets and Drive, through workspace-mcp | For Google Docs |
| Slack | The Slack channel | For Slack |
| Telnyx | The SMS channel | For SMS |
| Tavily | Web search. Works without a key; a key raises the limits | Built in |
| Web Push (the phone's push service) | Notifications to the phone app | For the phone app |
| Let's Encrypt | Caddy's HTTPS certificate | For the HTTPS install |
| Deepgram, Cartesia | Cloud speech, instead of the local speech container | Optional |

The installer also downloads the speech models from Hugging Face once, at install time.

## Running it

- **It restarts on its own.** Every service uses `restart: unless-stopped`, so the stack comes back after a reboot or a crash.
- **Applying changes.** A vault secret saved in the console needs only a restart: **Settings → System → About → Restart** ([Console](/core-concepts/console#restarting-curia)) or `docker compose restart curia`. A changed `.env` value needs `docker compose up -d curia`, so the container is recreated with the new environment. If you changed both, `docker compose up -d --force-recreate curia` applies either. See [Initial configuration](/get-started/configuration).
- **Updating.** See [Updating Curia](/get-started/installation#updating-curia), and read the release's [upgrade notes](/references/releases#upgrade-notes) first: some releases need a change to your compose file or `.env` that an update never makes for you.
- **Watching it.** See [Health monitoring](/get-started/health-monitoring) for uptime checks on `/api/health`.

## What the installer doesn't deploy

Some things are up to you:

- **signal-cli.** The Signal channel needs a signal-cli daemon you run on the same host. Curia connects to its socket. See [Signal](/channels/signal-setup).
- **Your own agents and skills.** The image ships the built-in ones. Yours live in your own config and code. See [Building custom agents](/agents/building-custom-agents) and [Building tools](/tools-and-skills/building).
- **Backups.** Nothing backs up `pgdata` for you.

Some additions are worth considering on a server:

- **A VPN or proxy for the browser's traffic.** Set `BROWSER_PROXY` to send the browser out through another IP, for sites that block cloud servers. See [Web browser](/integrations/web-browser).
- **Single sign-on in front of the console.** An identity-aware proxy, in front of Caddy or in place of it, adds your organisation's sign-in on top of Curia's own.

## Sizing

The stack is sized for **4 vCPU and 8 GB of RAM**. The speech container holds about 2.6 GB of models in memory, and that sets the minimum. See [System requirements](/get-started/system-requirements) for CPU, memory, disk and network.
