Curia is single-tenant and self-hosted: one instance per principal, running on infrastructure you control. On a server, the [image-based install](/get-started/installation) is the right path — it needs only Docker and curl, pulls the published container image, and requires no source checkout or toolchain on the box. The install steps are in [Install Curia](/get-started/installation). This page covers the choices and upkeep specific to running it on a server.

## Topology

The installer asks once, on a fresh install, how you'll reach Curia. Your answer decides whether Curia gets HTTPS.

| Option | What the installer sets up | Use it when |
|---|---|---|
| **Public domain + HTTPS** (recommended) | A bundled [Caddy](https://caddyserver.com) reverse proxy on ports 80 and 443 that gets and renews a Let's Encrypt certificate. It sets `DOMAIN`, adds `docker-compose.tls.yml` to `COMPOSE_FILE` and sets `APP_ORIGIN=https://<your-domain>` in `.env`. | Curia runs on a server with a domain. You need a DNS A record pointing at the host, and ports 80 and 443 open, before you start. |
| **Public IP / my own proxy** | Curia only, serving plain HTTP on port `3000`. | You already terminate TLS at a load balancer or reverse proxy in front of the host. |
| **Local / evaluation** | The same as above: plain HTTP at `http://localhost:3000`. | A try-out on your own machine. Browsers only allow the microphone on HTTPS or `localhost`, so voice calls from other devices won't work. |

To move an existing install to the domain option, set `DOMAIN=<your domain>`, `COMPOSE_FILE=docker-compose.yml:docker-compose.tls.yml` and `APP_ORIGIN=https://<your domain>` in `.env`, then run `docker compose up -d`. Behind your own proxy, set `APP_ORIGIN` to the URL people use to reach Curia. Re-running the installer on a finished install doesn't ask the question again.

The bundled Caddy proxies only Curia. If you add voice, LiveKit needs its own route and ports: see [Run LiveKit on a server](/channels/voice-setup#run-livekit-on-a-server).

## Production considerations

<Note>
  The Docker image runs as a non-root `curia` user as part of its security hardening. See the [security overview](/security/overview) for the full container security model.
</Note>

- **The stack restarts automatically.** Both the `postgres` and `curia` services use `restart: unless-stopped`, so the instance comes back after a server reboot or a crash without manual intervention.
- **Secrets live in the encrypted vault.** Application credentials are stored in the [vault](/get-started/secrets-vault), not in `.env`. Only four bootstrap values stay in `.env`: `DB_USER`, `DB_PASSWORD`, `DATABASE_URL`, and `SECRET_ENCRYPTION_KEY`. Treat `.env` as sensitive — back it up securely and keep it out of version control.
- **Back up `SECRET_ENCRYPTION_KEY` separately and keep it safe.** It is the master key that decrypts the vault. If you lose it, every stored secret becomes unrecoverable and you have to re-seed the vault from scratch. Store a copy somewhere independent of the server (a password manager or secrets store).
- **Applying configuration changes.** A vault secret added via the console only needs `docker compose restart curia` (Curia re-reads the vault on startup). A changed `.env` value needs `docker compose up -d curia` so the container is recreated with the new environment. If you changed both, `docker compose up -d --force-recreate curia` applies either. See [Initial configuration](/get-started/configuration) for the full breakdown.
- **Postgres listens on loopback only.** The stock `docker-compose.yml` publishes Postgres on `127.0.0.1:5432`. Curia uses the internal compose network, and the installer runs migrations inside the container, so nothing outside the server needs the port. Remote database access is an explicit opt-in: set `POSTGRES_BIND` in `.env` to `0.0.0.0` (IPv4), `::` (IPv4 and IPv6) or an interface address. Prefer an SSH tunnel instead: `ssh -L 15432:127.0.0.1:5432 <server>`, then connect to `localhost:15432`.
- **Port 3000 follows your topology.** For the local and HTTPS options, the installer sets `HTTP_BIND=127.0.0.1`, so port `3000` is reachable only from the server itself (Caddy reaches Curia over the compose network). Re-running `install.sh` on an existing HTTPS install sets it too, so anything that used `<server>:3000` directly, such as an uptime probe, should move to `https://<your-domain>`; set `HTTP_BIND=` (empty) in `.env` to keep `3000` public. For the public IP / own proxy option, `HTTP_BIND` is left empty and `3000` is published on every interface. Docker's published ports bypass host firewalls such as UFW, so in that case allow `3000` only from your proxy in your cloud provider's firewall. Leave 80 and 443 open, plus LiveKit's media ports if you run voice.
- **HTTPS installs sign in over HTTPS only.** With `APP_ORIGIN` set to `https://<your-domain>`, session cookies are marked `Secure` and the API accepts browser requests from that origin alone, so open the console at `https://<your-domain>`, not `http://<server>:3000`. Re-running `install.sh` on an HTTPS install that has no `APP_ORIGIN` (or an empty one) sets it and prints a note; a value you set yourself is never changed.
- **Upgrading.** Re-run `install.sh` to move to a newer image. It detects the completed install, regenerates nothing, re-applies migrations idempotently, and restarts the stack on the new image. Because no secrets rotate, live sessions and the encrypted vault are preserved.

<Warning>
  `install.sh` never overwrites an existing `docker-compose.yml`, so an upgrade keeps your old one, hand-edits included. Compose files from earlier releases publish Postgres on **every** network interface. Edit the postgres `ports:` entry to read `- "${POSTGRES_BIND:-127.0.0.1}:${POSTGRES_PORT:-5432}:5432"`, then re-run `install.sh` (or `docker compose up -d postgres`) so the container is recreated; editing the file alone changes nothing. On an HTTPS install, also change the curia entry to `- "${HTTP_BIND:-}:${HTTP_PORT:-3000}:3000"`.

  `install.sh` checks what Docker actually published. It stops and asks before continuing while Postgres is exposed, and warns when port 3000 ignores `HTTP_BIND`. To check by hand, run `ss -tlnp | grep 5432`: it should show `127.0.0.1:5432`, not `0.0.0.0:5432` or `[::]:5432`.
</Warning>

## The System page

The console's **Settings → System → About** page is a read-only snapshot of the running instance plus one operator control.

It shows the Curia version, the Node runtime, the configured timezone, how long the process has been up, and which concrete model each capability tier currently routes to. Nothing sensitive appears here — no API keys, no database URL, no vault contents — so it is safe to screenshot when asking for help.

### Restarting from the console

**Restart** performs the same graceful shutdown a `docker compose restart` would: Curia stops accepting new work, lets in-flight tasks finish, closes its connections, and exits. Docker's `restart: unless-stopped` brings it back. This is a *process* restart — no Docker socket is mounted, so the console cannot touch containers, images, or the host.

This is the fastest way to apply a vault change, since Curia reads the vault at startup. A changed `.env` value still needs `docker compose up -d curia`, because the container must be recreated to pick up new environment variables.

<Note>
  Restarts are capped at **3 per 5 minutes**. The limit is enforced from the audit log rather than in memory, so it survives the very restarts it is limiting. If Curia cannot read that history or cannot record the restart, it refuses to restart at all rather than proceed unrecorded — every operator restart is auditable and distinguishable from a crash.
</Note>

If the process does not come back, the console gives up waiting after 90 seconds and tells you, rather than spinning indefinitely. Check `docker compose logs curia` at that point.
