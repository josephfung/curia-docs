Curia is single-tenant and self-hosted: one instance per principal, running on infrastructure you control. On a server, the [image-based install](/get-started/installation) is the right path — it needs only Docker and curl, pulls the published container image, and requires no source checkout or toolchain on the box. This page doesn't repeat the install steps; it covers what's specific to running in production.

## Install

The [`install.sh`](/get-started/installation) flow is the same on a server as on a laptop, with one production-relevant choice: when it asks how you'll reach the instance, pick the topology that matches your setup.

- **Public domain + HTTPS** — the installer configures a bundled [Caddy](https://caddyserver.com) reverse proxy that obtains and renews Let's Encrypt certificates automatically. You provide a domain with a DNS A record pointing at the host, and ports 80/443 open. This is the usual choice for an internet-facing instance.
- **Public IP / my own proxy** — Curia serves plain HTTP on `:3000` and you terminate TLS upstream (a load balancer or an existing reverse proxy).

Then add the channels and capabilities you need — email, semantic search, web research, Signal — from the install guide's [full setup](/get-started/installation#full-setup) section.

## Production considerations

<Note>
  The Docker image runs as a non-root `curia` user as part of its security hardening. See the [security overview](/security/overview) for the full container security model.
</Note>

- **The stack restarts automatically.** Both the `postgres` and `curia` services use `restart: unless-stopped`, so the instance comes back after a server reboot or a crash without manual intervention.
- **Secrets live in the encrypted vault.** Application credentials are stored in the [vault](/get-started/secrets-vault), not in `.env`. Only four bootstrap values stay in `.env`: `DB_USER`, `DB_PASSWORD`, `DATABASE_URL`, and `SECRET_ENCRYPTION_KEY`. Treat `.env` as sensitive — back it up securely and keep it out of version control.
- **Back up `SECRET_ENCRYPTION_KEY` separately and keep it safe.** It is the master key that decrypts the vault. If you lose it, every stored secret becomes unrecoverable and you have to re-seed the vault from scratch. Store a copy somewhere independent of the server (a password manager or secrets store).
- **Applying configuration changes.** A vault secret added via the console only needs `docker compose restart curia` (Curia re-reads the vault on startup). A changed `.env` value needs `docker compose up -d curia` so the container is recreated with the new environment. If you changed both, `docker compose up -d --force-recreate curia` applies either. See [Initial configuration](/get-started/configuration) for the full breakdown.
- **Upgrading.** Re-run `install.sh` to move to a newer image. It detects the completed install, regenerates nothing, re-applies migrations idempotently, and restarts the stack on the new image. Because no secrets rotate, live sessions and the encrypted vault are preserved.

## The System page

The console's **System** page is a read-only snapshot of the running instance plus one operator control.

It shows the Curia version, the Node runtime, the configured timezone, how long the process has been up, and which concrete model each capability tier currently routes to. Nothing sensitive appears here — no API keys, no database URL, no vault contents — so it is safe to screenshot when asking for help.

### Restarting from the console

**Restart** performs the same graceful shutdown a `docker compose restart` would: Curia stops accepting new work, lets in-flight tasks finish, closes its connections, and exits. Docker's `restart: unless-stopped` brings it back. This is a *process* restart — no Docker socket is mounted, so the console cannot touch containers, images, or the host.

This is the fastest way to apply a vault change, since Curia reads the vault at startup. A changed `.env` value still needs `docker compose up -d curia`, because the container must be recreated to pick up new environment variables.

<Note>
  Restarts are capped at **3 per 5 minutes**. The limit is enforced from the audit log rather than in memory, so it survives the very restarts it is limiting. If Curia cannot read that history or cannot record the restart, it refuses to restart at all rather than proceed unrecorded — every operator restart is auditable and distinguishable from a crash.
</Note>

If the process does not come back, the console gives up waiting after 90 seconds and tells you, rather than spinning indefinitely. Check `docker compose logs curia` at that point.
