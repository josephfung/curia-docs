---
title: "Skills: how agents take action in the outside world"
description: "Skills connect Curia to the outside world. Each one declares its inputs, outputs, action risk level, and required secrets before the agent can invoke it."
---

Skills are the mechanism through which agents interact with external services and take action in the world. When Curia sends an email, searches the web, creates a calendar event, or looks up a contact, it is invoking a skill. Agents don't call APIs directly — they invoke skills, which handle authentication, validation, and output sanitization on their behalf. The LLM never sees raw credentials.

## Two types of skills

Curia supports two types of skills, and agents work with both using the same interface — they cannot tell the difference at runtime.

<Tabs>
  <Tab title="Local skills">
    Local skills live in the `skills/` directory as a folder containing a manifest and handler:

    ```
    skills/
      email-send/
        skill.json      # manifest: name, inputs, outputs, permissions, sensitivity
        handler.ts      # implementation
        handler.test.ts # tests
    ```

    The manifest declares everything the execution layer needs to validate, authorize, and invoke the skill. The handler implements the actual logic.
  </Tab>
  <Tab title="MCP skills">
    MCP skills connect to external [Model Context Protocol](https://modelcontextprotocol.io) servers over HTTP or stdio. At startup, Curia connects to each configured MCP server, discovers its tools via `tools/list`, and registers them in the skill registry alongside local skills.

    ```yaml
    # config/skills.yaml
    mcp_servers:
      - name: google-workspace
        transport: http
        url: https://mcp-server.example.com/mcp
        headers:
          Authorization: "Bearer <token>"
        action_risk: low
        permissions: ["workspace:read", "workspace:write"]
        secrets:                        # optional — declare vault keys this server needs
          - key: google_oauth_client_id
            label: "Google OAuth Client ID"
            masked: false
          - key: google_oauth_client_secret
            label: "Google OAuth Client Secret"
            masked: true
    ```

    Supported transports are `http` (StreamableHTTP, recommended for hosted servers) and `stdio` (local subprocess).

    **MCP credential management.** When a server declares a `secrets:` block, Curia registers the required keys in the console under **Settings → MCP Skills**. Each key gets a labelled input field (masked or plain text based on `masked`), and the console writes the value to the encrypted vault. The server is only enabled once all declared secrets are present — the same gate used by local skills' `install.requires_secrets`. At spawn time, the vault values are injected into the subprocess environment so the MCP server can read them without Curia hardcoding credentials in the config file.
  </Tab>
</Tabs>

## The skill manifest

Every local skill includes a `skill.json` manifest that the execution layer validates at startup. Here is a real example from the `email-send` skill:

```json
{
  "name": "email-send",
  "description": "Send a new email via the configured email account",
  "version": "1.0.0",
  "sensitivity": "normal",
  "action_risk": "medium",
  "inputs": {
    "to": "string",
    "cc": "string?",
    "subject": "string",
    "body": "string"
  },
  "outputs": {
    "message_id": "string",
    "to": "string",
    "subject": "string"
  },
  "permissions": [],
  "secrets": [],
  "timeout": 30000
}
```

### Manifest fields

| Field | Description |
|---|---|
| `name` | Unique identifier used by agents and the skill registry |
| `description` | Human-readable description — shown to the LLM and in the registry |
| `sensitivity` | `normal` or `elevated` — `elevated` requires a live CEO turn (see below) |
| `action_risk` | Risk level used by the autonomy engine — see below |
| `inputs` | Input schema — validated before the handler is called |
| `outputs` | Output schema — documents what the skill returns |
| `permissions` | Declared capabilities, validated at load time |
| `secrets` | Vault secret keys this skill may request via `ctx.secret()` |
| `timeout` | Per-invocation timeout in milliseconds (default: 30,000) |
| `install.requires_secrets` | Optional. Vault keys that must exist before the skill can be installed or enabled (see [Skill lifecycle](#skill-lifecycle-install-and-enable)) |

## Action risk levels

Every skill declares an `action_risk` value that indicates its potential impact on the world. This field is required — Curia will not start if any skill manifest omits it.

| Level | Min autonomy score | Capability class |
|---|---|---|
| `none` | 0 | Read-only, no external effects (web search, summarization) |
| `low` | 60 | Internal state writes — memory, contacts |
| `medium` | 70 | Outbound communications — sending email or Signal messages |
| `high` | 80 | Calendar writes, commitments made on behalf of the CEO |
| `critical` | 90 | Financial, destructive, or irreversible actions |

The autonomy engine uses these values to determine whether a given skill can run at the current autonomy score. See [Autonomy engine](/core-concepts/autonomy) for the full picture.

## Sensitivity: normal and elevated

The `sensitivity` field controls the elevated-skill gate in the execution layer:

- **`normal`** — no elevated gate. The skill is governed by the autonomy engine via its `action_risk` (and, where set, the list of callers allowed to invoke it).
- **`elevated`** — the skill exercises CEO authority itself, so it only runs during a **live principal turn**: a turn that originated from a fresh inbound from you (the CEO), or a synchronous delegation made inside one. A scheduled job, a woken task, or any task that merely carries your *lineage* can never invoke it.

Elevated is reserved for authority primitives — approving, denying, or dismissing a queued action, changing the autonomy level, and altering a contact's trust tier, role, or permissions. This is what closes the self-approval loophole: Curia acting on its own (woken by a schedule or a reply) can never approve its own pending action or grant itself new permissions. Only you, acting in the moment, can.

This gate is checked on **every** invocation — it is not a one-time "approve once and never ask again." (Consequential but non-authority actions, like sending email or booking calendar events, are `normal` skills governed by `action_risk` and the approval workflow instead.)

## Secrets: credentials the LLM never sees

Skills that need API keys, passwords, or tokens declare them in their `secrets` array. At runtime, the execution layer provides a scoped `ctx.secret()` accessor that resolves the value from the [encrypted vault](/get-started/secrets-vault):

```typescript
// Inside a skill handler
const apiKey = ctx.secret("nylas_api_key");
```

The execution layer validates that the calling skill's manifest declared the requested secret. If a skill tries to access a secret it did not declare, the call fails. Agents and LLMs never see secret values — only the skill handler does, and only through this scoped accessor. Every secret access is audit-logged (which skill, which task, when, and whether the value came from the vault or an env fallback) — but values are never written to the log.

## Skill lifecycle: install and enable

Skills live in a [DB-backed registry](/core-concepts/registry). A skill present on disk is not automatically active — it must be **installed** and **enabled** before agents can call it, and only enabled skills are loaded at startup. This gives you a single place to turn capabilities on and off, and a gate for required credentials.

When a skill declares `install.requires_secrets`, the registry refuses to install or enable it until every listed vault key is present. The bundled `web-search` skill declares `tavily_api_key`, so it stays disabled until you provision a Tavily key. Enable and disable skills from the Settings registry in the console; changes take effect on restart.

## Output sanitization

Every skill result is sanitized before the LLM sees it. This prevents tool outputs from being used as injection vectors:

- XML and HTML tags are stripped — they cannot be interpreted as system instructions
- Outputs longer than 200,000 characters are truncated with a `[truncated]` marker
- Patterns matching known secret formats (API keys, tokens, passwords) are redacted
- Error strings are wrapped in a structured format that prevents them from being read as instructions

Nothing from the outside world reaches the LLM unfiltered.

## Recommended MCP integrations

These MCP servers are not bundled with Curia but are documented as first-class integrations:

| Server | Purpose |
|---|---|
| Google Workspace | Drive, Docs, Sheets, Gmail read/search/write |
| Filesystem | Scoped local file access (read/write/search) |
| GitHub | Repository management, issues, pull requests |
| Brave Search | Additional web search for research agents |
| Fetch | Web fetching with robots.txt compliance |

To connect any MCP server, add it to `config/skills.yaml` using the `mcp_servers` block shown above. Curia will discover and register its tools automatically at startup.
