Signal gives your principal a private, end-to-end encrypted way to message Curia from their phone. Because Signal ties identity to a verified phone number, messages from your principal on Signal carry the highest trust level in Curia's security model. That allows actions that lower-trust channels like email can't authorize.

Two phone numbers are involved. Keep them apart:

- **Curia's number.** A number of its own that you register with signal-cli. Curia sends and receives from it. Your principal messages this number.
- **Your principal's number.** Their own Signal account on their own phone. You link it to your principal's contact in Curia, so Curia knows who's messaging.

<Note>
  Choosing between Signal and SMS? See [3. Reach your principal](/get-started/reach-your-principal).
</Note>

## What you'll need

- **A phone number for Curia** that can receive a text or a voice call for Signal's verification code. Don't use a number that already has Signal on a phone: registering it with signal-cli signs that phone out of Signal.
- **[signal-cli](https://github.com/AsamK/signal-cli), run by you.** It isn't part of Curia's install: the compose files from the installer run Postgres, Curia and LiveKit (plus Caddy for HTTPS), not signal-cli. signal-cli must run on the same host as Curia, because Curia connects to it over a Unix socket.
- **Your principal's Signal number,** in E.164 format (for example `+14165550123`).

**Cost** (checked 2026-11-01): Signal is free. Curia's number costs whatever your carrier charges for it.

## Step 1 — Register Curia's number with signal-cli

Register **Curia's** number, not your principal's. Replace `+12223334444` with it, in [E.164 format](https://www.twilio.com/docs/glossary/what-e164):

```bash
signal-cli -a +12223334444 register
```

Signal sends a verification code to that number by text. To get a voice call instead, add `--voice`. If Signal asks for a captcha, follow signal-cli's registration instructions. Then submit the code:

```bash
signal-cli -a +12223334444 verify <code>
```

Curia uses a number registered this way. It doesn't support linking signal-cli as a secondary device of a phone's Signal account.

## Step 2 — Run signal-cli as a daemon and share its socket

Start signal-cli in daemon mode with a JSON-RPC Unix socket:

```bash
signal-cli -a +12223334444 daemon --socket /var/run/signal-cli/socket
```

Keep it running (for example as a system service or its own container), then make the socket reachable from inside the Curia container:

- **Mount the socket's folder into the `curia` service,** for example through a Compose override file. If your `.env` sets `COMPOSE_FILE` (the HTTPS install does), add your override file to that list, or Compose won't load it.
- **Let Curia write to the socket.** The Curia container runs as user and group `1001`. Connecting to a Unix socket needs write permission on it.

Note the socket's path **as seen from inside the Curia container**. You enter it in the next step.

## Step 3 — Enter Curia's Signal details in the console

In the console, go to **Settings → Channels** and click the **signal** row. Click **Install** if it isn't installed yet. Then, under **Credentials**, save:

| Field | Whose value | Vault key |
|---|---|---|
| **signal-cli socket path** | The socket path inside the Curia container, such as `/var/run/signal-cli/socket` | `channel.signal.socket_path` |
| **Phone number (E.164)** | **Curia's** number from Step 1 | `channel.signal.phone_number` |

Both are required. Click **Enable**, then restart Curia from the folder where you ran the installer:

```bash
docker compose restart curia
```

Saved credentials and enabling both take effect on the next restart.

<Note>
  Older installs may set `SIGNAL_SOCKET_PATH` and `SIGNAL_PHONE_NUMBER` in `.env`. Curia still reads them as fallbacks, and the console shows them as **configured (env)**. A value saved in the console wins.
</Note>

## Step 4 — Link your principal's Signal number

This is the step people miss. Without it, Curia treats messages from your principal's phone as coming from a stranger, and messages Curia sends to your principal can be held back by its outbound filter.

1. In the console, open **Contacts** and select your principal.
2. Under **Channel identities**, choose the channel **signal**.
3. Enter **your principal's** Signal number in E.164 format as the **Identifier**. Add a label if you like.
4. Click **Add identity**.

Numbers you add here are saved as verified and take effect straight away, with no restart. Never enter Curia's own number here.

## Check it works

- **Logs.** After the restart, `docker compose logs curia | grep -i signal` shows the Signal adapter starting. If you see `Signal socket path or phone number not configured`, a value from Step 3 is missing.
- **Health.** `curl https://<your-domain>/api/health` shows `"signal": "ok"`. `"fail"` means Curia can't reach signal-cli over the socket. `"skipped"` means the channel didn't start.
- **Console.** The signal row in **Settings → Channels** shows **enabled**, and your principal's contact lists a verified **signal** identity.
- **A real message.** Send a message to Curia's number from your own Signal account. Curia answers in the same conversation. If you aren't the principal, Curia treats you as an unknown sender and answers with care, and that's expected.

## What your principal will notice

Nothing until Curia messages them. Curia's first message arrives from a number they don't know, so Signal shows it as a message request they need to accept. Give them Curia's number to save as a contact first.

Once it's set up, your principal can use Signal to:

- approve sensitive or financial actions that email can't authorize;
- get urgent notifications when Curia flags something;
- send Curia instructions securely when away from their desk.

<Info>
  Trust levels decide which actions Curia takes on a sender's behalf. Signal carries `high` trust, the same as the console.
</Info>

## Voice notes

Your principal can send Curia a Signal voice note and it's transcribed into an ordinary message. There's no separate setup beyond speech-to-text credentials (the same Deepgram key the [Voice channel](/channels/voice-setup) uses).

- Audio attachments are downloaded through signal-cli and transcribed, then handled exactly like a typed message. The transcript is tagged so you can tell it came from audio.
- In a 1:1 conversation, transcription only runs for **senders Curia already knows**.
- Downloads are capped at **5 MB**. Longer recordings aren't transcribed.
- With no speech-to-text credentials configured, audio-only messages are ignored. Text keeps working.

## Voice calls

People can also **call** Curia's Signal number and hold a live spoken conversation. This is off by default and needs extra infrastructure around signal-cli. See [Signal calls](/channels/voice-setup#signal-calls) on the Voice page.

<Warning>
  By default Curia picks up for strangers too, at unknown trust: calls follow the same `unknown_sender` setting as Signal texts, which ships as `allow`. That's a different exposure from Signal messaging. Read the [policy section](/channels/voice-setup#who-can-call-and-what-they-can-do) before enabling it.
</Warning>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Signal adapter not starting">
    Check that:

    1. Both credentials show **configured** under **Settings → Channels → signal**.
    2. The signal row shows **enabled**, not just **installed**.
    3. You restarted Curia after your last change.
    4. signal-cli is running in daemon mode and the socket exists at the path you entered, inside the Curia container: `docker compose exec curia ls -l /var/run/signal-cli/socket` (use your path).
  </Accordion>

  <Accordion title="Health shows signal as fail">
    Curia started the channel but can't talk to signal-cli. Check that the daemon is running, that the socket's folder is mounted into the Curia container, and that user `1001` can write to the socket. A permission error in `docker compose logs curia` (`EACCES`) points at the last one.
  </Accordion>

  <Accordion title="Messages not delivered">
    Check signal-cli's own logs. If you see connection or authorization errors, the registration may have expired. Repeat Step 1 to re-register Curia's number.
  </Accordion>

  <Accordion title="Curia doesn't recognize my principal">
    Open **Contacts →** your principal and check that **Channel identities** lists a **signal** identity with your principal's number, in E.164 format and marked verified. If it's missing, follow Step 4.
  </Accordion>
</AccordionGroup>
