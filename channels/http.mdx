The HTTP adapter is the Fastify server behind the web console. It is not a chat channel of its own: messages you send through the console arrive on the `web` channel via `/api/chat`. The adapter also serves the console's other API routes and two monitoring endpoints. It is always on and cannot be disabled, so you can never lock yourself out of your instance.

## Endpoints

| Endpoint | Method | Auth | Description |
|---|---|---|---|
| `/api/chat/conversation` | GET | Console session | The shared web thread's id. Every browser and paired phone uses the same one. |
| `/api/chat/messages` | POST | Console session | Send a message to Curia. Returns `202` with the shared `conversationId` right away; the reply arrives on the stream. |
| `/api/chat/stream` | GET | Console session | Subscribe to the shared thread's messages, replies and tool activity via SSE |
| `/api/chat/history` | GET | Console session | Page through the shared thread's history |
| `/api/health` | GET | None | Health check |
| `/api/agents/status` | GET | Bearer token | Agent status information |

For full endpoint documentation, including the console's jobs, tasks, contacts, and registry routes, see the [HTTP API reference](/references/http-api).

<Note>
  The bearer-token message routes, `POST /api/messages` and `GET /api/messages/stream`, were removed (ADR-057). Use `/api/chat` instead.
</Note>

## Authentication

Console routes, including chat, authenticate with the `curia_session` cookie set when you sign in to the console, or with the `x-web-bootstrap-secret` header carrying `web_app_bootstrap_secret` from the [vault](/get-started/secrets-vault).

A console session lasts **90 days from its last use**, and every request you make starts the 90 days again. Sessions are stored in the database, so restarting or updating Curia doesn't sign anyone out. **Settings → System → Devices** lists every signed-in browser and phone, and lets you rename them, sign one out, or sign out all the others. You can also pair a phone from there without typing the access key; see [Use Curia on your phone](/channels/phone-app). To log out, or to switch between light and dark, click your name at the bottom of the sidebar.

Routes that do not authenticate themselves, such as `/api/agents/status`, require a Bearer token in the `Authorization` header:

```
Authorization: Bearer <your-API_TOKEN>
```

The token is the `api_token` value from the vault (generated by `pnpm run setup`). `/api/health` needs no auth.

## Trust level

| Property | Value |
|---|---|
| **Channel** | `web` |
| **Trust level** | High |
| **Reasoning** | The sender is the principal in their own authenticated console session |

Messages from console chat pass through the full dispatch pipeline, including trust scoring.

## Streaming

You have **one conversation with Curia across every device**. The server owns the web thread, so every browser and phone you sign in on shows the same history.

`/api/chat/stream` delivers real-time events for that thread as they occur:

- Your own messages (`user.message`), from any device, so a message sent from your phone appears on your computer
- Agent replies
- Tool invocations and results

The stream is always the shared thread, so there's nothing to filter. The console keeps it open while the page is visible and closes it when the tab is hidden. It reconnects with backoff after a dropped connection, and reloads anything it missed when it comes back. The server sends a `{"type":"ping"}` event every 30 seconds so a client can tell when a connection has died.

<Note>
  A reverse proxy in front of Curia must not compress `/api/chat/stream`, or the events arrive in bursts instead of one by one. With Caddy, exclude the path from `encode`.
</Note>
