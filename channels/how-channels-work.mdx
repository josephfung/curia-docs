Channels are how messages get in and out of Curia. Whether you send a Signal message from your phone, DM it in Slack, text the office number, email it from a colleague, talk to it out loud from the console, or type a command in the terminal, every message travels through a channel adapter that normalizes it into the same internal format. Curia's agents work with that normalized format — they never deal with email headers, Signal protocol specifics, or HTTP request objects directly. Adding a new channel means building one adapter; nothing in the core changes.

<Note>
  Channels are tracked in the [channel registry](/core-concepts/registry): each one is installed and enabled (or not), and its credentials live in the [vault](/get-started/secrets-vault). Email, Signal, Slack, SMS, and voice are toggleable — enable them once their credentials are configured. **HTTP and CLI are always on and cannot be disabled**, so you can never accidentally lock yourself out of your own instance.
</Note>

## The channels

<Tabs>
  <Tab title="Email">
    Email is Curia's primary channel for external communication. It connects via the Nylas API, which abstracts away the differences between Gmail, Outlook, and other providers.

    **Inbound:** Curia polls the Nylas Messages API every 30 seconds (configurable) for new messages. Emails are parsed, attachments extracted, and participants auto-added to your contacts. The adapter persists its high-water mark (the timestamp of the last message it saw) so a restart never re-reads or skips mail, and a watchdog raises an alert if polling stalls for several intervals.

    **Outbound:** Replies and new emails are sent via the Nylas Send API. The Coordinator injects its persona's display name and email signature into every outbound message.

    **CC detection:** The email adapter determines whether Curia is a direct recipient (`to`), copied (`cc`), or blind-copied on each message. When Curia is CC'd, the dispatcher tags the message with the primary recipients so the Coordinator knows who the email was actually addressed to and can respond appropriately — typically by using `email-reply` to the thread rather than composing a new message.

    **Email validation:** Before processing, the email adapter checks SPF, DKIM, and DMARC headers. Messages that fail validation are tagged `sender_verified: false` in their metadata — the Coordinator uses this signal when deciding whether to act on consequential requests.

    **Required secrets (vault):** `nylas_api_key`, `nylas_grant_id`, `nylas_self_email`

    **Trust level:** Low — email From headers are trivially spoofable, and even with SPF/DKIM validation, email is the least trustworthy channel.
  </Tab>
  <Tab title="Signal">
    Signal provides end-to-end encrypted messaging with strong identity guarantees. Curia connects via `signal-cli` running in JSON-RPC mode as a subprocess.

    Signal supports text messages, attachments, and reactions. Conversation IDs are derived from Signal group or 1:1 conversation identifiers, so Curia maintains persistent context within each thread.

    **Required secret (vault):** `channel.signal.phone_number`

    **Trust level:** High — Signal identity is tied to a phone number verified by the Signal protocol. Use Signal for sensitive instructions, financial actions, or anything where you want maximum assurance.
  </Tab>
  <Tab title="Slack">
    Slack lets your team reach Curia the way they'd reach a colleague: DM it, @mention it in a channel, or keep talking in a thread after the first mention. Curia connects as a workspace-owned Slack app over **Socket Mode**, so there's no public webhook to host.

    Slack has native threads, so no context bridging is needed. Reactions are normalized into a channel-agnostic reaction signal. See the [Slack setup guide](/channels/slack-setup) to connect it.

    **Required secrets (vault):** `channel.slack.bot_token` (`xoxb-…`), `channel.slack.app_token` (`xapp-…`)

    **Trust level:** Medium — bot/OAuth tokens authenticate the workspace, but tokens can leak. Trust rides the **sender**: once a Slack user id is linked to a contact, that person's messages carry their contact tier (including principal), the same as on email or Signal.
  </Tab>
  <Tab title="SMS">
    SMS gives the office a dedicated text number (a Telnyx DID) for reaching the principal and third parties and fielding their replies. Inbound texts arrive as a signature-verified Telnyx webhook; outbound sends route through the outbound gateway to the Telnyx Messages API. 1:1 text only in v1 — no MMS or group messaging.

    SMS is non-threaded, so it uses context bridging. Carrier opt-out is enforced by Telnyx (a `STOP` suppresses the number), so Curia keeps no parallel opt-out list. See the [SMS setup guide](/channels/sms-setup) to connect it.

    **Required secrets (vault):** `channel.sms.api_key`, `channel.sms.from_number`, `channel.sms.webhook_public_key`

    **Trust level:** Medium — the Telnyx office DID is not end-to-end encrypted and carrier From headers are spoofable. Trust rides the **sender**: a mobile number linked to a contact carries that person's tier.
  </Tab>
  <Tab title="Voice">
    Voice is a live, two-way spoken conversation from the web console. Curia streams your speech to text (Deepgram), thinks and runs tools exactly as it does in chat, and speaks its reply back (Cartesia), with WebRTC audio carried by a self-hosted LiveKit server. You can interrupt it mid-sentence (barge-in) and it stops to listen.

    Unlike the async text channels, a call is real-time and runs entirely inside an authenticated console session — there is no unknown-sender path. Final transcripts are written to working memory, so the call appears in your console chat history afterward. See the [Voice setup guide](/channels/voice-setup) to connect it.

    **Required secrets (vault):** `channel.voice.livekit_url`, `channel.voice.livekit_api_key`, `channel.voice.livekit_api_secret`, `channel.voice.deepgram_api_key`, `channel.voice.cartesia_api_key`, `channel.voice.cartesia_voice_id`

    **Trust level:** High — the caller is the principal in their own authenticated console session, the same authority as the CLI.
  </Tab>
  <Tab title="CLI">
    The CLI channel is an interactive terminal for local access. It reads from stdin and writes to stdout, making it ideal for setup, testing, and direct executive use when you are on the server.

    Because CLI access requires SSH or physical access to the host machine, it carries the highest trust level. The Coordinator knows when you are on CLI and behaves accordingly — sharing internal details freely, asking clarifying questions without hesitation, and never applying the external-sender communication constraints it uses for email.

    **Trust level:** High — CEO only.
  </Tab>
  <Tab title="HTTP API">
    The HTTP API provides REST endpoints and a Server-Sent Events stream for programmatic access. This is the interface a web dashboard, mobile app, or custom integration uses to communicate with Curia.

    - `POST /api/messages` — send a message and receive a response
    - `GET /api/messages/stream` — SSE stream for real-time response streaming
    - `GET /api/health` — health check for uptime monitors and load balancers

    All HTTP API requests require a Bearer token. Tokens can be leaked, so the HTTP API carries a medium trust level — lower than CLI and Signal, higher than email.

    **Trust level:** Medium.
  </Tab>
</Tabs>

## Channel trust levels

Every inbound message is tagged with the trust level of the channel it arrived on. The Coordinator uses this trust level — along with the sender's individual trust score — to decide what actions it is willing to take on that message.

| Channel | Trust level | Rationale |
|---|---|---|
| CLI | High | Requires SSH or physical access to the host |
| Signal | High | Strong identity via phone number + Signal protocol |
| Voice | High | Live call inside an authenticated console session — the principal |
| Slack | Medium | Workspace bot/OAuth tokens authenticate, but tokens can leak |
| SMS | Medium | Telnyx office DID — carrier From is spoofable and not end-to-end encrypted |
| HTTP API | Medium | Token-authenticated, but tokens can be shared or leaked |
| Email | Low | From headers are spoofable; even SPF/DKIM is not identity verification |

Trust levels gate consequential actions. A request arriving over email to change financial settings, export data, or take irreversible action will be declined or held for verification, even if the sender's name is recognized — the Coordinator asks the sender to confirm through a higher-trust channel.

<Note>
Channel trust is separate from a contact's **capability tier** (`blocked` → `unknown` → `known` → `trusted` → `principal`). Channel trust reflects how much identity assurance the transport provides; the tier reflects how much you trust a specific person. Both feed into the [message trust score](/core-concepts/contacts-trust) and the gates that govern what actions Curia will take.
</Note>

## Unknown sender policy

Each channel can be configured with one of two policies for messages from senders not yet in your contacts:

- **`allow`** (the default) — Curia auto-creates the sender as an `unknown`-tier contact and routes the message to the coordinator under read-only constraints: it may reply or ask a clarifying question, but takes no actions and shares no private context. There's no holding step. As you correspond, the contact elevates to `known` automatically; you can also identify or block them at any time.
- **`ignore`** — messages from unknown senders are silently discarded.

<Note>
Curia no longer queues unknown-sender messages for review (the old `hold_and_notify` policy was removed). Automated senders — noreply addresses, newsletters, bulk mail — are detected and kept out of your way rather than surfaced.
</Note>

## Context bridging on non-threaded channels

Email and Slack have native threading — each reply links to the original conversation, so Curia always knows what it last said. Signal, SMS, CLI, and HTTP have no equivalent concept: each inbound message arrives without a reference to Curia's prior response.

Without bridging, a Signal follow-up like "can you make it 4pm instead?" gives the coordinator no way to know what it's modifying.

**Context bridging** solves this for non-threaded channels. After every outbound response, the dispatch layer writes a compact context memo to working memory. When the user sends a follow-up, the memo is injected as a preamble — giving the coordinator full awareness of what it last said before it reads the new message.

You configure which channels use threading with the `threaded` key in `config/channel-trust.yaml`:

```yaml
channels:
  signal:
    threaded: false   # enables context bridging (default for Signal)
  http:
    threaded: false   # enables context bridging (default for HTTP)
  sms:
    threaded: false   # enables context bridging (default for SMS)
  email:
    threaded: true    # email is natively threaded; no bridging needed
  slack:
    threaded: true    # Slack has native threads; no bridging needed
```

Channels with `threaded: false` get context bridging automatically. Channels with `threaded: true` (email, Slack) use native thread identifiers instead.

<Note>
Context memos are short and structured. They are not the full response — only enough to anchor a follow-up. The coordinator still has access to its full working memory and entity context on every turn.
</Note>

## Channel security

Channel adapters operate within a hard architectural constraint: they can pass inbound messages into the system and receive outbound messages for delivery — and nothing else. They cannot invoke tools, read memory, or trigger agent tasks directly. This is enforced at the framework level, not by policy.

A compromised email adapter could flood inbound messages, but it cannot execute tools, access your data, or impersonate another layer. The boundary is structural.
