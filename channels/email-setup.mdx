Curia's email channel connects **Curia's own mailbox** through [Nylas](https://nylas.com), a unified API for Gmail, Outlook and other providers. With it, Curia receives email at its own address, replies in-thread, sends new email and saves drafts, all signed as Curia.

This channel is for mailboxes that belong to Curia. Access to your principal's own email and calendar is set up separately: see [5. Your principal's email and calendar](/get-started/principal-email-calendar).

<Note>
  Setting up email for the first time? Follow [2. Curia's own email](/get-started/curia-email) for the step-by-step walkthrough. This page is the reference.
</Note>

## Where the values go

Everything is entered in the console under **Settings → Channels → email**. Nothing goes in `.env`.

**Credentials** (one for the whole channel):

| Field | Whose value | Vault key |
|---|---|---|
| **Nylas API key** | Your Nylas application's | `channel.email.nylas_api_key` |

**Email accounts** (one entry per Curia mailbox): an account name, the mailbox address and its Nylas grant ID. Each entry's grant is stored in the vault as `channel.email.<name>.nylas_grant_id`. These entries are the mailboxes Curia reads and sends from.

**Enable** becomes available once the API key is saved and at least one enabled account has a grant. The setup assistant marks email done when the same check passes and the channel is enabled.

**Principal's mailbox** (your principal's own mailbox, not Curia's): its grant ID and address, stored as `ceo_nylas_grant_id` and `ceo_self_email`. Calendar and the inbox tools use it. See [5. Your principal's email and calendar](/get-started/principal-email-calendar).

Saved credentials, enabling the channel and adding or removing accounts all take effect on the next restart:

```bash
docker compose restart curia
```

<Note>
  Older installs may have `NYLAS_API_KEY` in `.env`. Curia still reads it as a fallback, but a value saved in the console wins. `NYLAS_GRANT_ID` and `NYLAS_SELF_EMAIL` are no longer read: add each mailbox under **Email accounts** instead.
</Note>

## More than one mailbox

Curia can work from several mailboxes of its own, for example a general address and a scheduling address. Connect each one to Nylas as its own grant, then add it under **Email accounts** with a different account name. All accounts share the one Nylas API key. Restart Curia after adding one.

Each Nylas grant counts as a connected account on your Nylas plan.

## Email tools

Once the email channel is running, these tools are available to Curia and any agents you configure:

| Tool | What it does |
|---|---|
| `email-list` | List recent messages in any connected account |
| `email-get` | Fetch the full body of a specific message by ID |
| `email-send` | Compose and send a new email |
| `email-reply` | Reply to an existing thread by message ID |
| `email-draft-save` | Save a draft to a specified account for human review |
| `send-draft` | Send a previously saved draft (CEO-authorized) |
| `email-archive` | Archive a message by ID |

All email tools accept an `account` parameter naming one of the email accounts. If it's left out, Curia uses the first enabled account by name.

## File attachments

Outbound email tools (`email-send`, `email-reply`, and their CEO-inbox counterparts) accept an optional list of attachments. Files are referenced by `file://` URLs backed by Curia's temp-file store rather than passed inline, with a cap of **20 MB total across at most 10 attachments** per message. Anything an agent has written to the temp-file store can be attached; the [`drive-download-file`](/tools-and-skills/built-in-tools#email) tool bridges Google Drive by downloading a file (including Google-native exports) into that store and returning a `file://` URL ready to attach. No extra configuration is needed beyond a working Nylas grant: attachments ride the same Send API as the message body.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Email channel not starting">
    Check the startup logs (`docker compose logs curia | grep -i "email channel"`). The message says what's missing:

    - `NYLAS_API_KEY not set — email channel disabled`: save the **Nylas API key** under **Credentials**.
    - `No email accounts resolved — email channel disabled`: add Curia's mailbox under **Email accounts**, with its grant ID.
    - `channel enabled but required credentials missing; not starting`: one of the three **Credentials** fields is empty.

    Also check that the email row shows **enabled**, not just **installed**, and that you restarted Curia after your last change.
  </Accordion>

  <Accordion title="The Enable button is greyed out">
    All three credential fields (Nylas API key, Nylas grant ID, Mailbox address) must show **configured**. Save any that read **missing**.
  </Accordion>

  <Accordion title="Messages not appearing">
    Curia polls Nylas every 30 seconds by default. If messages are slow to appear, check that the mailbox's grant is active in the Nylas dashboard and that the grant ID under **Email accounts** matches the one Nylas shows.

    `/api/health` reports `"email": "fail"` when polling has stopped succeeding.

    You can change the polling interval in `.env` (it isn't a secret):

    ```env
    NYLAS_POLL_INTERVAL_MS=15000
    ```

    Run `docker compose up -d curia` after editing `.env`: a plain restart doesn't pick up changed environment variables.
  </Accordion>

  <Accordion title="Outbound emails going to drafts unexpectedly">
    Outbound sends are governed by the [autonomy engine](/core-concepts/autonomy). If the autonomy score is below 70, `email-send` and `email-reply` are blocked and drafts are saved instead. Ask Curia for its current score ("What is your autonomy score?") and raise it if needed.
  </Accordion>
</AccordionGroup>
