Curia's email channel connects **Curia's own mailbox** through [Nylas](https://nylas.com), a unified API for Gmail, Outlook and other providers. With it, Curia receives email at its own address, replies in-thread, sends new email and saves drafts, all signed as Curia.

This channel is for mailboxes that belong to Curia. Access to your principal's own email and calendar is set up separately: see [5. Your principal's email and calendar](/get-started/principal-email-calendar).

<Note>
  Setting up email for the first time? Follow [2. Curia's own email](/get-started/curia-email) for the step-by-step walkthrough. This page is the reference.
</Note>

## Where the values go

Everything is entered in the console under **Settings → Channels → email**. Nothing goes in `.env`.

**Credentials** (one for the whole channel):

| Field | Whose value | Vault key |
|---|---|---|
| **Nylas API key** | Your Nylas application's | `channel.email.nylas_api_key` |
| **Nylas region** (optional) | `us` or `eu`, the data centre your Nylas application is in. Blank means `us`. | `channel.email.nylas_region` (not secret; `NYLAS_REGION` is the fallback) |

An API key only works in its own region. You can set the region here, or on **Settings → Behaviour → Email & Calendar** with **Detect**, which finds it from the key. After you first save the key or the region, or change either, Curia needs one restart before sign-in works; until then the sign-in setup says **Restart Curia to finish setting up sign-in.** After that, connecting a principal mailbox needs no restart.

**Email accounts** (one entry per Curia mailbox): an account name, the mailbox address and its Nylas grant. Each entry's grant is stored in the vault as `channel.email.<name>.nylas_grant_id`. These entries are the mailboxes Curia reads and sends from.

**Add an account with Connect with Google.** Under **Email accounts**, click **Connect with Google** and sign in as Curia's mailbox. Curia adds the account (named `curia` if that's free), stores the grant and **restarts itself a few seconds later** to start using it. Nothing is copied from the Nylas dashboard. This needs mailbox sign-in set up first, which is covered in [2. Curia's own email](/get-started/curia-email): the Nylas callback and Google connector, an `https://` `APP_ORIGIN`, and a Google Cloud **Web** OAuth client. Only Google accounts work for now; Microsoft 365 isn't supported yet. Signing in again as an address that's already an account refreshes its grant instead of adding a second account. Under **Paste a grant ID instead**, the older route (name, address, grant ID) still works.

**Enable** becomes available once the API key is saved and at least one enabled account has a grant. Signing in a first mailbox gives it one. The setup assistant marks email done when the same check passes and the channel is enabled.

**Your principal's own mailboxes** are not set up here. They have their own page, **Settings → Behaviour → Email & Calendar**, which needs the Nylas API key above. Each grant is stored as `principal.mailbox.<id>.nylas_grant_id`. See [5. Your principal's email and calendar](/get-started/principal-email-calendar).

Saved credentials, enabling the channel and removing accounts take effect on the next restart. Adding an account with **Connect with Google** restarts Curia by itself; adding one by pasting a grant ID does not:

```bash
docker compose restart curia
```

<Note>
  Older installs may have `NYLAS_API_KEY` in `.env`. Curia still reads it as a fallback, but a value saved in the console wins. `NYLAS_GRANT_ID` and `NYLAS_SELF_EMAIL` are no longer read: add each mailbox under **Email accounts** instead.

  Older vault names for these values (`nylas_api_key`, `nylas_grant_id`, `nylas_self_email`) are no longer read either. On upgrade, Curia moves a saved `nylas_api_key` to `channel.email.nylas_api_key`. If email still reports the Nylas key missing after the upgrade, save it again under **Settings → Channels → Email**.
</Note>

## More than one mailbox

Curia can work from several mailboxes of its own, for example a general address and a scheduling address. Add each one under **Email accounts** with **Connect with Google**, signing in as that mailbox. All accounts share the one Nylas API key. Curia restarts itself after each sign-in; if you pasted a grant ID instead, restart it yourself.

Each Nylas grant counts as a connected account on your Nylas plan.

## Email tools

Once the email channel is running, these tools are available to Curia and any agents you configure:

| Tool | What it does |
|---|---|
| `email-list` | List recent messages in any connected account |
| `email-get` | Fetch the full body of a specific message by ID |
| `email-send` | Compose and send a new email |
| `email-reply` | Reply to an existing thread by message ID |
| `email-draft-save` | Save a draft to a specified account for human review |
| `send-draft` | Send a previously saved draft (CEO-authorized) |
| `email-archive` | Archive a message by ID |

All email tools accept an `account` parameter naming one of the email accounts. If it's left out, Curia uses the first enabled account by name.

`email-reply` replies to everyone on the thread by default, keeping every original To recipient, and each email carries a single signature.

## File attachments

Outbound email tools (`email-send`, `email-reply`, and their CEO-inbox counterparts) accept an optional list of attachments. Files are referenced by `file://` URLs backed by Curia's temp-file store rather than passed inline, with a cap of **20 MB total across at most 10 attachments** per message. Anything an agent has written to the temp-file store can be attached; the [`drive-download-file`](/tools-and-skills/built-in-tools#email) tool bridges Google Drive by downloading a file (including Google-native exports) into that store and returning a `file://` URL ready to attach. No extra configuration is needed beyond a working Nylas grant: attachments ride the same Send API as the message body.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Email channel not starting">
    Check the startup logs (`docker compose logs curia | grep -i "email channel"`). The message says what's missing:

    - `NYLAS_API_KEY not set — email channel disabled`: save the **Nylas API key** under **Credentials**.
    - `No email accounts resolved — email channel disabled`: add Curia's mailbox under **Email accounts**, with **Connect with Google** (or a pasted grant ID).
    - `channel enabled but required credentials missing; not starting`: the **Nylas API key** isn't saved.

    Also check that the email row shows **enabled**, not just **installed**, and that you restarted Curia after your last change.
  </Accordion>

  <Accordion title="The Enable button is greyed out">
    The **Nylas API key** must show **configured**, and at least one enabled account under **Email accounts** must have a grant (from **Connect with Google** or a pasted grant ID). Save whichever is missing.
  </Accordion>

  <Accordion title="Connect with Google is greyed out, or a sign-in failed">
    The line under the button says what's missing. The usual causes are no saved API key, a wrong region, a Sandbox application, an `APP_ORIGIN` that isn't `https://`, the callback not registered or no Google connector. The fixes are in the table in [2. Curia's own email](/get-started/curia-email#steps). If a finished sign-in ends on an error page, [that page's troubleshooting table](/get-started/curia-email#troubleshooting) explains each message.

    Links last 60 minutes and work once. A link in an outage email lasts 7 days.
  </Accordion>

  <Accordion title="Messages not appearing">
    Curia polls Nylas every 30 seconds by default. If messages are slow to appear, check that the mailbox's grant is active in the Nylas dashboard. If it isn't, for example after a password change, click **Connect with Google** again for that address.

    `/api/health` reports `"email": "fail"` when polling has stopped succeeding.

    Mail Curia had already fetched isn't lost if it crashes or restarts mid-message: inbound mail is saved first and processed again on the next start.

    You can change the polling interval in `.env` (it isn't a secret):

    ```env
    NYLAS_POLL_INTERVAL_MS=15000
    ```

    Run `docker compose up -d curia` after editing `.env`: a plain restart doesn't pick up changed environment variables.
  </Accordion>

  <Accordion title="Outbound emails going to drafts unexpectedly">
    Outbound sends are governed by the [autonomy engine](/core-concepts/autonomy). If the autonomy score is below 70, `email-send` and `email-reply` are blocked and drafts are saved instead. Ask Curia for its current score ("What is your autonomy score?") and raise it if needed.
  </Accordion>
</AccordionGroup>
