Voice lets you talk to your Curia agent out loud — a live, two-way call instead of typing. Curia streams your speech to text, thinks and runs tools the same way it does in chat, and speaks its reply back sentence by sentence. You can interrupt it mid-sentence (barge-in) and it stops to listen, the way a real conversation works.

There are two ways to place a call, and they share everything above the audio layer:

- **From the web console** — WebRTC through a self-hosted LiveKit server. This is the base setup and the rest of this page walks through it.
- **By Signal call** — anyone can place a native Signal voice call to Curia's Signal number. This is off by default, needs the console path working first, and is covered in [Signal calls](#signal-calls) below.

A console call runs inside an authenticated session, so it carries the same **high** trust as the CLI: the person on the call is you, the principal. A Signal call does not — the caller is whoever dialled, and Curia resolves them like any other Signal contact. See [Who can call, and what they can do](#who-can-call-and-what-they-can-do).

<Warning>
  Enabling voice means **audio and transcripts leave the host** to three third parties: Deepgram (speech-to-text), Cartesia (text-to-speech), and your configured LLM provider. Speech-vendor keys never reach the browser, but treat these vendors' data-processing terms the way you would any external service before turning voice on.

  This applies to **anyone who calls**, not just you. If you enable Signal calls, a caller's speech is transcribed by Deepgram the same way yours is — and Signal's own end-to-end encryption covers the call to Curia, not what Curia does with the audio after that.
</Warning>

## How it works

A call uses three services, wired together by Curia:

- **LiveKit** — a self-hosted WebRTC server that carries the real-time audio between your browser and the host. Curia mints a short-lived (1-hour) join token per call; it never exposes admin credentials to the browser.
- **Deepgram** — streaming speech-to-text: turns your spoken words into transcripts as you talk.
- **Cartesia** — streaming text-to-speech: turns Curia's reply into spoken audio in the voice you choose.

The reply is spoken from within the console session (like principal web chat), while any tools Curia calls still run through the normal execution layer and any external sends still go through the outbound gateway. Final transcripts are written to working memory, so the call shows up in your console chat history afterward.

## Prerequisites

- A Curia host reachable from the browser you run the console in.
- A **LiveKit** server — either the bundled Docker Compose service (below) or your own deployment.
- A **Deepgram** account and API key.
- A **Cartesia** account and API key, plus a **voice id** to speak in.
- Host firewall/NAT access for LiveKit's signaling and media ports.

## Step 1 — Start LiveKit

The root `docker-compose.yml` includes a `livekit` service behind the Compose `voice` profile, so a plain `docker compose up` never starts it — Postgres-only deploys boot normally.

```bash
docker compose --profile voice up -d livekit
```

LiveKit uses three ports. Open them on the host firewall and forward them through NAT if Curia sits behind a router:

| Purpose | Port | Notes |
|---|---|---|
| HTTP/WebSocket signaling | `7880/tcp` | Browser-reachable; can be fronted by a TLS proxy |
| WebRTC TCP fallback | `7881/tcp` | Needs direct exposure |
| WebRTC UDP media | `7882/udp` | Needs direct exposure — cloud firewalls often allow TCP but silently drop UDP |

<Warning>
  For local development the profiled service runs `livekit-server --dev`, which uses the well-known credentials `devkey` / `secret`. **Never expose `--dev` on a public interface** — anyone who can reach the ports could mint LiveKit tokens without Curia's auth. For any reachable deploy, run LiveKit with a real config (copy `docker/livekit.yaml`, replace the placeholder key/secret, and set `LIVEKIT_COMMAND="--config /etc/livekit.yaml"`) and store the same key/secret in the Curia vault.
</Warning>

## Step 2 — Get your provider keys

<Steps>
  <Step title="Deepgram API key">
    Create a Deepgram account and generate an API key. This is `channel.voice.deepgram_api_key`.
  </Step>

  <Step title="Cartesia API key">
    Create a Cartesia account and generate an API key. This is `channel.voice.cartesia_api_key`.
  </Step>

  <Step title="Pick a Cartesia voice">
    Browse voices at [play.cartesia.ai](https://play.cartesia.ai) and copy the **voice id** (a UUID) of the one you want Curia to speak in. This is `channel.voice.cartesia_voice_id`. It is **required** — Cartesia cannot synthesize a reply without it, so the channel stays disabled until it is set.
  </Step>
</Steps>

## Step 3 — Store the values in the vault

In the Curia console, go to **Settings → Channels → Voice** and enter all six values. They are stored in the [vault](/get-started/secrets-vault) and, unlike some channels, have **no environment-variable fallback** — voice credentials must live in the vault.

| Field | Vault key |
|---|---|
| LiveKit WebSocket URL | `channel.voice.livekit_url` |
| LiveKit API key | `channel.voice.livekit_api_key` |
| LiveKit API secret | `channel.voice.livekit_api_secret` |
| Deepgram API key | `channel.voice.deepgram_api_key` |
| Cartesia API key | `channel.voice.cartesia_api_key` |
| Cartesia voice id | `channel.voice.cartesia_voice_id` |

<Note>
  The **LiveKit WebSocket URL** is the *browser-reachable* signaling endpoint, not LiveKit's internal address: `ws://<host>:7880` for private local testing, or `wss://<voice-host>` when you terminate TLS for signaling through a separate proxy. It must match your LiveKit server's key/secret exactly (with `--dev`, that's `devkey` / `secret`).
</Note>

## Step 4 — Enable and restart

Install and enable the Voice channel in the registry, then restart Curia so it reads the vault on startup:

```bash
docker compose restart curia
```

Changing a vault key does not affect a call already in progress — it takes effect on the next call after restart.

## Step 5 — Make a call

Open the console chat. The **Call** button appears once Voice is enabled and the session API can mint LiveKit tokens.

<Steps>
  <Step title="Click Call and allow the microphone">
    Your browser will ask for microphone permission. Microphone access requires a secure origin, so serve the console over **HTTPS** (and use `wss://` for LiveKit) on any non-localhost host.
  </Step>

  <Step title="Talk">
    Speak naturally. Curia replies out loud, and you can interrupt it mid-sentence — it stops to listen.
  </Step>

  <Step title="Mute or hang up">
    Use mute or hang up from the active-call bar. The final transcript is saved to your console chat history.
  </Step>
</Steps>

## What Curia does on a call

<AccordionGroup>
  <Accordion title="It greets you first">
    When an inbound call connects, Curia opens the conversation rather than waiting in silence — a short greeting appropriate to the time of day. If something was sent on another channel just before the call, it acknowledges that in the same breath.
  </Accordion>

  <Accordion title="It knows what just happened on your other channels">
    Spoken turns read the same active outbound context the text channels write to. Call right after Curia emails someone and it already knows what went out; you do not have to re-establish the subject.
  </Accordion>

  <Accordion title="It hands heavy work off instead of stalling the call">
    Some asks take minutes, not seconds — research, a browser session, a multi-step delegation. Rather than leaving dead air while it works, Curia acknowledges the request, dispatches it to the async coordinator, and calls or messages you back when it is done. The call keeps moving.
  </Accordion>

  <Accordion title="It uses the same guardrails as the text agent">
    Voice and the text coordinator compose shared prompt modules rather than maintaining two prompts that drift apart. Date resolution is the first of these: a spoken "next Thursday" is resolved through the same tool the text agent uses, so a call cannot book a meeting on a date chat would have gotten right.
  </Accordion>
</AccordionGroup>

<Note>
  Voice needs a model that genuinely supports **streaming** and **tool calls**, and Curia checks the model registry for both before it will start the channel. A provider exposing a streaming API is not proof — OpenRouter, for instance, exposes one for every model it routes, including models that do neither. If `channels.voice.model` names a model missing either capability (or a model Curia does not know), voice refuses to boot and says which capability is missing.
</Note>

## Signal calls

Curia can answer inbound **native Signal voice calls**, running them through the same speech pipeline as console calls. The feature is **off by default** and needs deploy-side infrastructure beyond the console setup above.

<Note>
  This is newer than the console path. Treat it as experimental.
</Note>

### Prerequisites

Everything from the console setup must already work, plus:

- The **Signal channel** installed, enabled, and connected — see [Signal setup](/channels/signal-setup).
- **signal-cli 0.14.7 or newer**, which answers calls by spawning a `signal-call-tunnel` process per call.
- The **`signal-call-tunnel`** binary available to signal-cli.
- **PulseAudio** running inside the signal-cli container, with its socket shared out to the Curia container.

The published `curia-deploy` Compose stack provides all four. Assembling them by hand is possible but is not a supported path.

### Configuration

These are environment variables in `.env`, not vault keys:

| Variable | Default | What it does |
|---|---|---|
| `SIGNAL_VOICE_CALLS_ENABLED` | `false` | Master switch. |
| `SIGNAL_PULSE_SOCKET_PATH` | — | Path to the shared PulseAudio socket. The `curia-deploy` stack uses `/var/run/pulse-shared/native`. |
| `SIGNAL_VOICE_MAX_CALL_SECONDS` | `600` | Hard per-call duration cap. On expiry the call is hung up — there is no spoken wrap-up first. |

If `SIGNAL_VOICE_CALLS_ENABLED` is set but any prerequisite is missing, Curia logs a warning at startup naming what it could not find and simply does not start the call bridge. It will not half-enable.

### Who can call, and what they can do

The v1 answer policy is **answer everyone**. Curia picks up for known contacts and strangers alike. Two callers are rejected outright:

- A contact you have **blocked**.
- A caller with **no phone number** on the call (Signal permits UUID-only callers). There is nothing stable to resolve or to attach a contact to later, so Curia declines rather than talk to someone untraceable.

Callers are resolved against the **same Signal identity** used for text messages, so your own standing carries over — call from the phone number Curia already knows as yours and it treats you as the principal. A stranger is admitted at **unknown** trust, which means the call is answered but the caller stays outside the elevated-tool and cross-channel-context gates. They can talk to Curia; they cannot use it as a lever on your accounts.

<Warning>
  Answer-everyone means your Signal number is a phone number the public can reach your assistant on. If that is not what you want, leave `SIGNAL_VOICE_CALLS_ENABLED` off — there is no allowlist mode in this version.
</Warning>

Curia handles **one call at a time**. A second caller while a call is in progress gets a busy rejection.

### Checking that the audio path is alive

Signal calls fail in a way messaging does not: the JSON-RPC socket can be perfectly healthy while the audio stack underneath is dead, so Signal texts keep working and calls connect to silence. `/api/health` covers the three paths separately:

| Check | Covers |
|---|---|
| `signal` | Signal **messaging** — the JSON-RPC socket |
| `voice` | **Console** calls — LiveKit reachability |
| `signal_voice` | Signal **calls** — the shared PulseAudio socket |

`signal_voice` reports `skipped` when `SIGNAL_PULSE_SOCKET_PATH` is unset. It proves the audio path by **connecting** to the socket, not by checking that the socket file exists — a dead PulseAudio daemon leaves its socket file behind, and that is exactly how this failure once hid behind a green dashboard for hours. See [Health monitoring](/get-started/health-monitoring).

## Troubleshooting

<AccordionGroup>
  <Accordion title="The Call button doesn't appear">
    Confirm Voice is installed **and** enabled in **Settings → Channels**, that all six vault keys are set (the Cartesia voice id is required), and that Curia was restarted after saving them.
  </Accordion>

  <Accordion title="Token or session creation fails">
    Verify `channel.voice.livekit_url`, `channel.voice.livekit_api_key`, and `channel.voice.livekit_api_secret` match the LiveKit server exactly. A `--dev` server expects `devkey` / `secret`.
  </Accordion>

  <Accordion title="The browser connects but there's no audio">
    Check UDP `7882` first, then TCP `7881`. Cloud firewalls commonly allow TCP while silently dropping UDP, which breaks WebRTC media.
  </Accordion>

  <Accordion title="Works on localhost but fails remotely">
    Run LiveKit with `rtc.use_external_ip: true`, set a browser-reachable LiveKit URL, and confirm NAT forwards the RTC ports (`7881/tcp`, `7882/udp`).
  </Accordion>

  <Accordion title="The browser blocks the microphone or WebSocket">
    Browsers require a secure origin for microphone access. Serve the console over HTTPS and use `wss://` for LiveKit on any public host.
  </Accordion>

  <Accordion title="The assistant is slow to start speaking">
    Voice emits structured latency fields (`voice.ttfa_ms`, `voice.llm_ttft_ms`, `voice.tts_first_byte_ms`) in the logs. Compare them before changing `channels.voice.model` — only switch the model if LLM latency dominates.
  </Accordion>

  <Accordion title="Voice refuses to start and logs a missing capability">
    The model resolved for spoken turns must declare both `streaming` and `tools` in Curia's model registry. Point `channels.voice.model` at a model that does, or clear it to fall back to the fast tier.
  </Accordion>

  <Accordion title="Signal calls never ring Curia">
    Check the startup log first: if a prerequisite was missing, Curia says so and leaves the bridge unstarted. Otherwise confirm `SIGNAL_VOICE_CALLS_ENABLED=true`, that the Signal channel itself is connected (`signal` in `/api/health`), and that signal-cli is 0.14.7 or newer with `signal-call-tunnel` available.
  </Accordion>

  <Accordion title="A Signal call connects but there's silence">
    This is the PulseAudio path, not Signal. Check `signal_voice` in `/api/health` — `fail` means nothing is accepting on the shared socket, usually a PulseAudio daemon that did not start. `skipped` means `SIGNAL_PULSE_SOCKET_PATH` is unset, so the call bridge was never wired up at all.
  </Accordion>

  <Accordion title="A Signal call is rejected immediately">
    Three causes: the caller is a blocked contact, the call carries no phone number (UUID-only callers are declined), or another call is already in progress — Curia handles one at a time.
  </Accordion>

  <Accordion title="Calls cut off after ten minutes">
    That is `SIGNAL_VOICE_MAX_CALL_SECONDS` (default `600`). The cap hangs up hard, with no spoken warning.
  </Accordion>
</AccordionGroup>
