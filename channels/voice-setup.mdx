Voice lets your principal talk to Curia out loud: a live, two-way call instead of typing. Curia streams the caller's speech to text, thinks and runs tools the same way it does in chat, and speaks its reply back sentence by sentence. The caller can interrupt it mid-sentence (barge-in) and it stops to listen, the way a real conversation works.

<Note>
  This page is the reference for the voice channel, written for the operator: whoever installs and runs Curia. To set voice up step by step, follow [4. Voice](/get-started/voice).
</Note>

There are two ways to place a call, and they share everything above the audio layer:

- **From the web console:** WebRTC through a self-hosted LiveKit server. This is the base setup.
- **By Signal call:** anyone can place a native Signal voice call to Curia's Signal number. This is off by default, needs the console path working first, and is covered in [Signal calls](#signal-calls) below.

A console call runs inside an authenticated console session, so it carries the same **high** trust as the CLI. Curia treats whoever is on a console call as the principal: during setup that's you, and after hand-over it's normally your principal. A Signal call does not get that trust automatically. The caller is whoever dialled, and Curia resolves them like any other Signal contact. See [Who can call, and what they can do](#who-can-call-and-what-they-can-do).

<Warning>
  Enabling voice means **audio and transcripts leave the host** to three third parties: Deepgram (speech-to-text), Cartesia (text-to-speech), and your configured LLM provider. Speech-vendor keys never reach the browser, but treat these vendors' data-processing terms the way you would any external service before turning voice on.

  This applies to **anyone who calls**, not just your principal. If you enable Signal calls, a caller's speech is transcribed by Deepgram the same way the principal's is, and Signal's own end-to-end encryption covers the call to Curia, not what Curia does with the audio after that.
</Warning>

## How it works

A call uses three services, wired together by Curia:

- **LiveKit:** a self-hosted WebRTC server that carries the real-time audio between the caller's browser and the host. Curia mints a short-lived (1-hour) join token per call and never exposes admin credentials to the browser.
- **Deepgram:** streaming speech-to-text. It turns the caller's speech into transcripts as they talk.
- **Cartesia:** streaming text-to-speech. It turns Curia's reply into spoken audio in the voice you chose.

The reply is spoken from within the console session (like principal web chat), while any tools Curia calls still run through the normal execution layer and any external sends still go through the outbound gateway. Final transcripts are written to working memory, so the call shows up in the console chat history afterward.

## LiveKit

The install's `docker-compose.yml` includes a `livekit` service behind the Compose `voice` profile. The installer doesn't start it, and neither does a plain `docker compose up`, so installs without voice boot normally. Start it from the install directory:

```bash
docker compose --profile voice up -d livekit
```

To have `docker compose up` (and re-runs of the installer) start LiveKit along with the rest of the stack, add `COMPOSE_PROFILES=voice` to `.env`.

LiveKit uses three ports. Open them on the host firewall and forward them through NAT if Curia sits behind a router:

| Purpose | Port | Notes |
|---|---|---|
| HTTP/WebSocket signaling | `7880/tcp` | Browser-reachable; can be fronted by a TLS proxy |
| WebRTC TCP fallback | `7881/tcp` | Needs direct exposure |
| WebRTC UDP media | `7882/udp` | Needs direct exposure. Cloud firewalls often allow TCP but silently drop UDP |

By default the service runs `livekit-server --dev`, which uses the well-known credentials `devkey` / `secret`. That is fine on a laptop at `localhost`.

<Warning>
  **Never expose `--dev` on a public interface.** Anyone who can reach the ports could mint LiveKit tokens without Curia's auth. On a server, use your own key and secret as below.
</Warning>

### Run LiveKit on a server

The install doesn't configure LiveKit for a server yet, so these steps are by hand. Run them in the install directory.

<Steps>
  <Step title="Create a LiveKit config with your own key">
    Download [`docker/livekit.yaml`](https://github.com/josephfung/curia/blob/main/docker/livekit.yaml) from the Curia repository into a `docker/` folder in the install directory. It isn't part of the install bundle. Generate a key and secret, for example with `openssl rand -hex 16` and `openssl rand -base64 32`, and replace the placeholder line under `keys:` with `<key>: <secret>`. You'll enter the same pair in the console.
  </Step>

  <Step title="Mount the config and point LiveKit at it">
    Create `docker-compose.voice.yml` next to `docker-compose.yml`:

    ```yaml
    services:
      livekit:
        volumes:
          - ./docker/livekit.yaml:/etc/livekit.yaml:ro
    ```

    Then, in `.env`, add the file to `COMPOSE_FILE` and set the LiveKit command:

    ```env
    COMPOSE_FILE=docker-compose.yml:docker-compose.tls.yml:docker-compose.voice.yml
    LIVEKIT_COMMAND=--config /etc/livekit.yaml
    COMPOSE_PROFILES=voice
    ```

    Keep whatever `COMPOSE_FILE` already lists (the domain install adds `docker-compose.tls.yml`) and append the new file. Then run `docker compose up -d`.
  </Step>

  <Step title="Serve signaling over HTTPS">
    A console served over HTTPS can only reach LiveKit over `wss://`. The bundled Caddy proxies only Curia, not LiveKit. One way is to route LiveKit's `/rtc` path on your domain to LiveKit, by adding a `handle` block to `deploy/Caddyfile`:

    ```
    {$DOMAIN} {
    	handle /rtc* {
    		reverse_proxy livekit:7880
    	}
    	handle {
    		reverse_proxy curia:3000
    	}
    }
    ```

    Restart Caddy (`docker compose restart caddy`). The signaling URL is then `wss://<your-domain>`. The installer won't overwrite an existing `Caddyfile` when you re-run it.
  </Step>

  <Step title="Open the media ports">
    Open `7881/tcp` and `7882/udp` to the internet on the host and any cloud firewall. Media can't go through the proxy.
  </Step>
</Steps>

Curia talks to LiveKit's admin API over the Compose network at `channels.voice.livekit_management_url` (default `http://livekit:7880`). Don't point it at the public signaling URL.

## Credentials

Enter these in **Settings → Channels → Voice**. They are stored in the [vault](/get-started/secrets-vault) and have **no environment-variable fallback**: voice credentials must live in the vault.

| Console field | Vault key |
|---|---|
| LiveKit signaling URL | `channel.voice.livekit_url` |
| LiveKit API key | `channel.voice.livekit_api_key` |
| LiveKit API secret | `channel.voice.livekit_api_secret` |
| Deepgram API key | `channel.voice.deepgram_api_key` |
| Cartesia API key | `channel.voice.cartesia_api_key` |
| Cartesia voice ID | `channel.voice.cartesia_voice_id` |

<Note>
  The **LiveKit signaling URL** is the *browser-reachable* signaling endpoint, not LiveKit's internal address: `ws://localhost:7880` for a laptop try-out, or `wss://<your-domain>` behind a TLS proxy. The key and secret must match your LiveKit server's exactly (with `--dev`, that's `devkey` / `secret`).
</Note>

The **Cartesia voice ID** is the voice Curia speaks in: a UUID copied from [play.cartesia.ai](https://play.cartesia.ai). It is required. Cartesia can't synthesize a reply without it, so the channel stays disabled until it's set.

Curia reads these values at startup. After changing any of them, install and enable the Voice channel if you haven't, then restart (from the console's **System** page, or `docker compose restart curia`). A call already in progress keeps the old values.

## Making a call

Open the console chat. A **Voice** button (with a phone icon) appears once voice is enabled. Click it and allow the microphone. Browsers only allow the microphone on a secure origin, so serve the console over **HTTPS** (and use `wss://` for LiveKit) on any host other than `localhost`. Mute or hang up from the call bar. The final transcript is saved to the console chat history.

## What Curia does on a call

<AccordionGroup>
  <Accordion title="It greets the caller first">
    When an inbound call connects, Curia opens the conversation rather than waiting in silence — a short greeting appropriate to the time of day. If something was sent on another channel just before the call, it acknowledges that in the same breath.
  </Accordion>

  <Accordion title="It waits a beat before answering">
    When the caller stops talking, Curia waits briefly before it replies, so a pause mid-thought doesn't get answered as if they had finished. Deepgram first waits for 400 ms of silence, then Curia holds another 350 ms. If they start talking again inside that window, it is all one request. In practice a reply starts about two seconds after their last word.

    If Curia cuts callers off when they pause to think, raise the hold in `config/local.yaml`:

    ```yaml
    channels:
      voice:
        turn_hold_ms: 600
    ```

    It takes a whole number of milliseconds from `0` to `5000`. Curia refuses to start on any other value. A longer hold means fewer interruptions but slower replies.
  </Accordion>

  <Accordion title="It says 'One moment' while it works">
    When a request needs a tool, such as a calendar lookup, Curia says "One moment." once and then goes quiet until it has the answer, even if the work takes several steps. It talks about the work itself ("Let me check your calendar"), not about the assistants or tools doing it behind the scenes.
  </Accordion>

  <Accordion title="The caller can interrupt it">
    When the caller starts talking while Curia is speaking, it stops to listen. Detection takes about a second, because Curia waits for enough of their speech to rule out its own voice or background noise. On console calls, audio already queued is dropped as soon as they're detected. On Signal calls, up to about two seconds of queued audio can still play out before it goes quiet.
  </Accordion>

  <Accordion title="It knows what just happened on other channels">
    Spoken turns read the same active outbound context the text channels write to. Call right after Curia emails someone and it already knows what went out; the caller doesn't have to re-establish the subject.
  </Accordion>

  <Accordion title="It hands heavy work off instead of stalling the call">
    Some asks take minutes, not seconds — research, a browser session, a multi-step delegation. Rather than leaving dead air while it works, Curia acknowledges the request, dispatches it to the async coordinator, and calls or messages the principal back when it is done. The call keeps moving.
  </Accordion>

  <Accordion title="It uses the same guardrails as the text agent">
    Voice and the text coordinator compose shared prompt modules rather than maintaining two prompts that drift apart. Date resolution is the first of these: a spoken "next Thursday" is resolved through the same tool the text agent uses, so a call cannot book a meeting on a date chat would have gotten right.
  </Accordion>
</AccordionGroup>

<Note>
  Voice needs a model that genuinely supports **streaming** and **tool calls**, and Curia checks the model registry for both before it will start the channel. A provider exposing a streaming API is not proof — OpenRouter, for instance, exposes one for every model it routes, including models that do neither. If `channels.voice.model` names a model missing either capability (or a model Curia does not know), voice refuses to boot and says which capability is missing.
</Note>

## Signal calls

Curia can answer inbound **native Signal voice calls**, running them through the same speech pipeline as console calls. The feature is **off by default** and needs deploy-side infrastructure beyond the console setup above. The standard image install doesn't include it.

<Note>
  This is newer than the console path. Treat it as experimental.
</Note>

### Prerequisites

Everything from the console setup must already work, plus:

- The **Signal channel** installed, enabled, and connected — see [Signal setup](/channels/signal-setup).
- **signal-cli 0.14.7 or newer**, which answers calls by spawning a `signal-call-tunnel` process per call.
- The **`signal-call-tunnel`** binary available to signal-cli.
- **PulseAudio** running inside the signal-cli container, with its socket shared out to the Curia container.

The published `curia-deploy` Compose stack provides all four. Assembling them by hand is possible but is not a supported path.

### Configuration

These are environment variables in `.env`, not vault keys:

| Variable | Default | What it does |
|---|---|---|
| `SIGNAL_VOICE_CALLS_ENABLED` | `false` | Master switch. |
| `SIGNAL_PULSE_SOCKET_PATH` | — | Path to the shared PulseAudio socket. The `curia-deploy` stack uses `/var/run/pulse-shared/native`. |
| `SIGNAL_VOICE_MAX_CALL_SECONDS` | `600` | Hard per-call duration cap. On expiry the call is hung up — there is no spoken wrap-up first. |

If `SIGNAL_VOICE_CALLS_ENABLED` is set but any prerequisite is missing, Curia logs a warning at startup naming what it could not find and simply does not start the call bridge. It will not half-enable.

### Who can call, and what they can do

Whether Curia answers a stranger follows the same setting as Signal texts: `channels.signal.unknown_sender` in `config/channel-trust.yaml`. It ships as `allow`, so by default Curia picks up for known contacts and strangers alike. Set it to `ignore` and unknown callers are turned away — but so are unknown senders' Signal **texts**, because one setting governs both. Two callers are always rejected, whatever the setting:

- A contact you have **blocked**.
- A caller with **no phone number** on the call (Signal permits UUID-only callers). There is nothing stable to resolve or to attach a contact to later, so Curia declines rather than talk to someone untraceable.

Callers are resolved against the **same Signal identity** used for text messages, so standing carries over: a call from the Signal number on the principal's contact is treated as the principal. A stranger is admitted at **unknown** trust, which means the call is answered but the caller stays outside the elevated-tool and cross-channel-context gates. They can talk to Curia; they cannot use it as a lever on the principal's accounts.

<Warning>
  With the default `allow`, Curia's Signal number is a phone number the public can reach Curia on. If that is not what you want, either set `channels.signal.unknown_sender: ignore` (accepting that strangers' texts are ignored too) or leave `SIGNAL_VOICE_CALLS_ENABLED` off. There is no calls-only allowlist in this version.
</Warning>

Curia handles **one call at a time**. A second caller while a call is in progress gets a busy rejection.

### Checking that the audio path is alive

Signal calls fail in a way messaging does not: the JSON-RPC socket can be perfectly healthy while the audio stack underneath is dead, so Signal texts keep working and calls connect to silence. `/api/health` covers the three paths separately:

| Check | Covers |
|---|---|
| `signal` | Signal **messaging** — the JSON-RPC socket |
| `voice` | **Console** calls — LiveKit reachability |
| `signal_voice` | Signal **calls** — the shared PulseAudio socket |

`signal_voice` reports `skipped` when `SIGNAL_PULSE_SOCKET_PATH` is unset. It proves the audio path by **connecting** to the socket, not by checking that the socket file exists — a dead PulseAudio daemon leaves its socket file behind, and that is exactly how this failure once hid behind a green dashboard for hours. See [Health monitoring](/get-started/health-monitoring).

## Troubleshooting

<AccordionGroup>
  <Accordion title="The Voice button doesn't appear">
    Confirm Voice is installed **and** enabled in **Settings → Channels**, that all six vault keys are set (the Cartesia voice id is required), and that Curia was restarted after saving them.
  </Accordion>

  <Accordion title="Token or session creation fails">
    Verify `channel.voice.livekit_url`, `channel.voice.livekit_api_key`, and `channel.voice.livekit_api_secret` match the LiveKit server exactly. A `--dev` server expects `devkey` / `secret`.
  </Accordion>

  <Accordion title="The browser connects but there's no audio">
    Check UDP `7882` first, then TCP `7881`. Cloud firewalls commonly allow TCP while silently dropping UDP, which breaks WebRTC media.
  </Accordion>

  <Accordion title="Works on localhost but fails remotely">
    Run LiveKit with `rtc.use_external_ip: true`, set a browser-reachable LiveKit URL, and confirm NAT forwards the RTC ports (`7881/tcp`, `7882/udp`).
  </Accordion>

  <Accordion title="The browser blocks the microphone or WebSocket">
    Browsers require a secure origin for microphone access. Serve the console over HTTPS and use `wss://` for LiveKit on any public host.
  </Accordion>

  <Accordion title="The assistant is slow to start speaking">
    Each reply logs where the time went:

    - `voice.end_of_speech_wait_ms`: your last word until Curia decided you'd finished. This is the silence threshold plus `channels.voice.turn_hold_ms`.
    - `voice.turn_queue_wait_ms`: time the request waited behind a reply that was still running.
    - `voice.ttfa_ms`: from starting the reply to its first audio, which covers the model (`llm_ttft_ms`) and speech synthesis (`voice.tts_first_byte_ms`).
    - `voice.last_word_to_audio_ms`: the whole gap you hear.

    Lower `turn_hold_ms` if the wait dominates. Only switch `channels.voice.model` if model latency dominates.
  </Accordion>

  <Accordion title="Curia cuts me off mid-thought">
    Your pause was longer than the turn hold, so Curia treated it as the end of your request. Raise `channels.voice.turn_hold_ms` (default `350`) in `config/local.yaml` and restart. See [It waits a beat before answering](#what-curia-does-on-a-call).
  </Accordion>

  <Accordion title="Barge-in feels slow, or the audio is choppy">
    Each interruption logs `voice.barge_in_detect_ms` (from when you started speaking to detection) and whether queued audio was dropped (`flushed`). Each spoken sentence logs `voice.tts_starved_ms`: anything above zero means audio arrived slower than real time, which you hear as choppiness. At hang-up, the `voice session audio summary` line totals these for the call and adds event-loop delay, which shows whether the host was too busy to keep audio flowing.
  </Accordion>

  <Accordion title="Voice refuses to start and logs a missing capability">
    The model resolved for spoken turns must declare both `streaming` and `tools` in Curia's model registry. Point `channels.voice.model` at a model that does, or clear it to fall back to the fast tier.
  </Accordion>

  <Accordion title="Signal calls never ring Curia">
    Check the startup log first: if a prerequisite was missing, Curia says so and leaves the bridge unstarted. Otherwise confirm `SIGNAL_VOICE_CALLS_ENABLED=true`, that the Signal channel itself is connected (`signal` in `/api/health`), and that signal-cli is 0.14.7 or newer with `signal-call-tunnel` available.
  </Accordion>

  <Accordion title="A Signal call connects but there's silence">
    This is the PulseAudio path, not Signal. Check `signal_voice` in `/api/health` — `fail` means nothing is accepting on the shared socket, usually a PulseAudio daemon that did not start. `skipped` means `SIGNAL_PULSE_SOCKET_PATH` is unset, so the call bridge was never wired up at all.
  </Accordion>

  <Accordion title="A Signal call is rejected immediately">
    Three causes: the caller is a blocked contact, the call carries no phone number (UUID-only callers are declined), or another call is already in progress — Curia handles one at a time.
  </Accordion>

  <Accordion title="Calls cut off after ten minutes">
    That is `SIGNAL_VOICE_MAX_CALL_SECONDS` (default `600`). The cap hangs up hard, with no spoken warning.
  </Accordion>
</AccordionGroup>
