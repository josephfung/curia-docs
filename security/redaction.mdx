---

Curia's PII redactor sits between agent responses and channel delivery. Before any outbound message reaches a recipient, it scans for sensitive data. The redactor is channel-aware — different channels can allow different types of information through.

What happens to a detected detail depends on `autonomy.gating`:

- **`band` (the default):** nothing is cut out of the message. Each detected detail goes to the send review, which checks who authorized it and then sends the message, holds it for your yes, or sends it back to be rewritten without the detail. No `[REDACTED: …]` token is ever delivered. See [Personal details](/security/autonomy-engine#personal-details).
- **`tier`:** detected details are replaced with labelled tokens like `[REDACTED: CREDIT_CARD]`, as described in the pipeline below.

<Note>
  Redaction is one of two outbound safeguards and handles **pattern-based PII** (emails, phone numbers, card and SSN formats). It is distinct from the outbound content filter and its second-stage [LLM-as-judge](/security/overview), which catch *contextual* leaks — internal reasoning, system details, or principal-private content reaching the wrong audience — that no fixed pattern would match. Both run before a message is delivered.
</Note>

## What's redacted by default

The redactor detects these PII patterns in all outbound messages:

| Pattern | Example | Replacement |
|---|---|---|
| Email addresses | `alice@example.com` | `[REDACTED: EMAIL]` |
| Phone numbers | `+1-555-234-5678` | `[REDACTED: PHONE]` |
| Credit card numbers | `4111 1111 1111 1111` | `[REDACTED: CREDIT_CARD]` |
| US Social Security numbers | `SSN 123-45-6789` | `[REDACTED: SSN]` |
| Canadian Social Insurance Numbers | `130-692-544` | `[REDACTED: SIN_CA]` |
| Custom patterns | Configured per deployment | Configurable replacement |

A Canadian SIN is recognized only when it passes the SIN checksum, and a bare nine-digit number only when "SIN" or "social insurance" comes just before it, so order numbers and reference IDs aren't mistaken for one. A US SSN likewise needs "SSN" or "social security" before it.

You can add custom PII patterns for data types specific to your deployment (employee IDs, national ID numbers, etc.) via `pii.extra_patterns` in `config/local.yaml`. See the [configuration reference](/references/configuration) for details.

## The redaction pipeline

When an outbound message is ready for delivery, the redactor evaluates it in this order. Under `band` gating the first four steps still run, but the review decides what happens to each detail instead of the replacement step.

<Steps>
  <Step title="Kill switch check">
    If `outbound_redaction.enabled` is `false`, the message passes through unmodified. This is an emergency override, not a recommended configuration.
  </Step>
  <Step title="Principal bypass">
    If you, the principal, are the only recipient (matched against your verified identities across every To and CC address), the message passes through unredacted. You always see full content. A message to you with anyone else on To or CC gets no bypass: the third party would see the details too. This is the only bypass — there is no trust-level override; even `trusted` contacts have PII redacted.
  </Step>
  <Step title="PII detection">
    The message content is scanned for all built-in and custom PII patterns.
  </Step>
  <Step title="Channel policy filtering">
    Detected patterns are filtered against the channel's allow list. For example, the email channel policy might allow phone numbers through while redacting credit cards.
  </Step>
  <Step title="Replacement">
    Remaining patterns are replaced with labelled tokens (e.g., `[REDACTED: CREDIT_CARD]`). Replacements are applied end-to-start to preserve character positions.
  </Step>
  <Step title="Audit event">
    An `outbound.pii_redacted` event is published to the audit log recording the pattern label, channel, and replacement token. The original matched value is intentionally **not** stored in the audit event.
  </Step>
</Steps>

## Per-channel policies

Different channels may have different sensitivity requirements. Configure per-channel allow lists to control which PII types pass through unredacted on each channel:

```yaml
# config/local.yaml
outbound_redaction:
  enabled: true
  default: 'block'           # block PII on channels without an explicit policy
  channel_policies:
    email:
      allow: ['email', 'phone']   # email addresses and phone numbers pass through
    signal:
      allow: ['phone']            # only phone numbers pass through
```

With this configuration:
- **Email** — email addresses and phone numbers are allowed; credit cards and SSNs are redacted
- **Signal** — phone numbers are allowed; everything else is redacted
- **CLI** — the principal bypass applies (you always see full content)
- **Any other channel** — all PII is redacted (the `default: 'block'` policy)

## Design principles

**Fail-closed** — the redactor does not swallow errors. If redaction fails, the outbound gateway catches the error and decides whether to block delivery rather than sending unredacted content.

**No original values stored** — the audit event records *what type* of PII was redacted and *what it was replaced with*, but intentionally does not store the original matched value. This prevents the audit log itself from becoming a PII repository.

**Principal identification by verified identity** — the bypass checks every recipient against your verified identities, not a name or a mutable field, so contact management code paths cannot accidentally grant the bypass to another contact.
