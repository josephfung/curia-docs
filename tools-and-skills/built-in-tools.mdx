Curia ships with 140+ tools, grouped into [skills (bundles)](/tools-and-skills/overview) by functional area. Every tool declares an `action_risk` level that determines the minimum [autonomy score](/core-concepts/autonomy) required to invoke it. Tools with `action_risk: none` can always run; higher-risk tools trigger the [approval workflow](/security/approval-workflow) when the score is below their floor. The category headings below map to the built-in skills an agent pins (`email`, `calendar`, `contacts`, `tasks`, `web`, and so on).

Some tools are also **`elevated`**: they exercise CEO authority directly, so they run only during a *live CEO turn* (a fresh inbound from you, or a synchronous delegation within it) and never autonomously or from a scheduled/woken task. These are the autonomy and approval controls (`set-autonomy`, `approve-action`, `deny-action`, `dismiss-action`), the grant-recommendation decisions (`approve-grant-recommendation`, `decline-grant-recommendation`), the authorization-altering contact tools (`contact-set-tier`, `contact-set-role`, `contact-grant-permission`, `contact-revoke-permission`), and `system-secret-capture-request`. See [Sensitivity](/tools-and-skills/how-tools-work#sensitivity-normal-and-elevated).

## Email

Outbound email and console rendering share one sanitized converter: markdown in a draft or reply body becomes HTML with clickable links, bare-URL autolinks, and tables.

**Recipients are people, not addresses.** Every send tool (`email-send`, `email-reply`'s `cc`, `email-draft-save`, `signal-send`, `sms-send`, `slack-send`, `web-send`) takes a contact ID or `principal` — never a typed address or number. The address comes from that person's verified contact record, so a mistyped one can't slip through. Someone new is added with `contact-create` first, then sent to. See [How Curia addresses a message](/core-concepts/contacts-trust#how-curia-addresses-a-message).

| Tool | action_risk | Description |
|---|---|---|
| `email-send` | medium | Send a new email. `to` and `cc` take a contact ID or `principal`; a label hint (`principal#personal`) picks one of that person's labelled addresses. Accepts an optional list of `attachments` (`file://` URLs, 20 MB / 10 files) and an optional `context_bridge` JSON for delegation-aware reply routing. |
| `email-reply` | medium | Reply to an existing email thread. Appends the quoted original message body to the reply (matching standard email-client behaviour). Accepts optional `attachments` and a `context_bridge` JSON. |
| `email-list` | none | List recent messages in an inbox |
| `email-get` | none | Fetch the full body of a specific message |
| `email-get-thread` | none | Fetch every message in a thread, with full bodies, oldest first, in one call |
| `email-draft-save` | low | Save a draft for CEO review, addressed to a contact ID or `principal`. Won't save a draft into the CEO's own mailbox — that goes through the CEO Inbox agent (`ceo-inbox-draft-compose` / `-reply`) |
| `send-draft` | none | Send a previously saved draft |
| `email-archive` | low | Archive a message |
| `email-label` | low | Apply one or more labels to an email message (creates the label if it doesn't exist) |
| `email-mark-read` | low | Mark an email message as read |
| `email-list-folders` | none | List all folders and labels in an email account |
| `email-create-folder` | low | Create a new folder or label in an email account |
| `email-download-attachment` | low | Download an email attachment and return content as base64 (10 MB limit) |
| `drive-download-file` | none | Download a Google Drive file (native or Google-native export) to the temp-file store and return a `file://` URL, so Drive files can be attached to outbound email |

## CEO Inbox

Tools for the CEO Inbox agent to manage the CEO's own mailboxes. These tools are pinned exclusively to the `ceo-inbox` agent — they access the CEO's personal email and should not be called from other agents.

Every CEO Inbox tool takes an optional `mailbox` (a connected mailbox's id). Leave it out unless the CEO named an account, and Curia finds the right one. A new draft (`ceo-inbox-draft-compose`) needs it once several mailboxes are connected.

| Tool | action_risk | Description |
|---|---|---|
| `ceo-inbox-list` | none | List recent unread messages from the CEO's personal inbox |
| `ceo-inbox-read` | none | Read a specific message, returning plain text and HTML body |
| `ceo-inbox-search` | none | Search the CEO's inbox using Gmail-native query syntax. When `unread_only` is set alongside a search query, `is:unread` is embedded into the search string so the filter actually applies. Spam and Trash are left out unless `include_spam_and_trash` is set. |
| `ceo-inbox-draft-compose` | low | Compose a cold-outreach (new, non-reply) draft into the CEO's Gmail Drafts for review. `to`/`cc` take contact IDs; a non-contact's address must be copied from the CEO's mail or the CEO's own message, or nothing is saved |
| `ceo-inbox-draft-reply` | low | Create a reply-all draft for CEO review. Curia sends it only through `ceo-inbox-send-draft`. Refuses to draft a reply to a message in Spam or Trash |
| `ceo-inbox-draft-edit` | low | Update an existing draft's recipients, subject, or body, so a wrong-recipient or stale draft can be fixed without recreating it. `move_to_mailbox` moves a draft saved in the wrong account. Recipients are added or removed one at a time (`add_to` / `add_cc` / `remove`); everyone else stays as they are |
| `ceo-inbox-send-draft` | 80 | Send one existing draft from the CEO's mailbox when the CEO asks, or, in triage, a reply Curia drafted that the mailbox's [sending setting](/core-concepts/inbox-sending) covers. Two or more drafts are read back and sent only after a yes. A refusal leaves the draft in Drafts |
| `ceo-inbox-download-attachment` | low | Download an attachment from the CEO's inbox by its Nylas ID (10 MB limit) |
| `ceo-inbox-archive` | low | Archive a message by removing it from the INBOX folder |
| `ceo-inbox-label` | low | Apply one or more labels to a message, creating labels that don't yet exist |
| `ceo-inbox-mark-read` | low | Mark a message as read to prevent re-processing on the next triage run |
| `ceo-inbox-mark-starred` | low | Star (or unstar) a message in the CEO's inbox. Triage auto-stars anything labelled 🚨 Urgent so it surfaces in the native client. |
| `ceo-inbox-update-folders` | low | Add or remove folders/labels on a message (e.g. star, move between folders). Falls back to the computed folder list when Nylas omits `folders` from the response, guarding against accidental folder wipes. |

**Passive learning.** A background *observe → reflect → remember* loop lets the CEO Inbox agent learn from what actually happens after it drafts — without ever sending or writing anything on its own. These tools run on their own crons (or inline during triage); everything they learn is surfaced to the CEO for approval or undo, never applied silently.

| Tool | action_risk | Description |
|---|---|---|
| `ceo-inbox-sent-observe` | none | Daily pass that reads the CEO's Sent folder since a stored watermark, matches new sends to Curia's draft snapshots and open CEO tasks, and records evidence for the learning loop. Read-only against Nylas — never drafts, archives, or sends. |
| `voice-learn` | medium | Weekly pass that reviews accumulated draft→sent edits, produces an updated free-form writing-voice guide, and queues it as a proposal. You approve or dismiss it; it never rewrites your profile directly and never invents a guide from no data. |
| `task-completion-from-sent` | low | Consumes the sent-mail matches from `ceo-inbox-sent-observe`: auto-completes low-risk, high-confidence CEO tasks with a reversible undo note, and queues confirmations for high-risk or ambiguous matches. |
| `ceo-inbox-shadow-draft` | none | During triage, quietly records what Curia *would* have sent for a message it punted, so a later pass can score that counterfactual toward the autonomy signal. Never creates approvals, notifications, or Gmail drafts. |

## Calendar

Every calendar tool takes an optional `mailbox`: the connected mailbox a calendar belongs to. Once several mailboxes are connected, it's required for a bare `primary` calendar and for writes to the CEO's calendars (`calendar-create-event`, `calendar-create-hold`, `calendar-respond-to-invite`); without it, nothing is written.

| Tool | action_risk | Description |
|---|---|---|
| `calendar-list-calendars` | none | List registered calendars, for one mailbox or every mailbox |
| `calendar-register` | high | Register a new calendar |
| `calendar-list-events` | none | List events in a date range. A meeting on calendars of two accounts is listed once, and each event carries `icalUid`, `organizerEmail` and a `meetingKey` that is the same on every calendar. `partial` and `removed` say when a calendar couldn't be read |
| `calendar-create-event` | high | Create a new calendar event. `recurrence` takes one `RRULE` line plus optional `EXDATE` lines for a repeating event |
| `calendar-update-event` | high | Update an existing event, or a series' `RRULE` (cancel one occurrence with `calendar-delete-event`) |
| `calendar-delete-event` | high | Delete a calendar event |
| `calendar-find-free-time` | none | Find available time slots across at most 20 calendars (treats `free`-status events as available). `treat_as_free` names blocking events the CEO's preferences say don't count. `partial` and `removed` list calendars that couldn't be read; their time is never reported as free |
| `calendar-check-conflicts` | none | Check for scheduling conflicts across at most 20 calendars (`free`-status events do not count). `clear` is false whenever a calendar couldn't be read |
| `calendar-create-hold` | medium | Place a tentative `HOLD (TBC)` event on an offered slot so it is not re-offered while scheduling is in flight |
| `calendar-holds-sweep` | low | Remove expired tentative holds (runs daily on a schedule) |
| `calendar-respond-to-invite` | medium | Send an RSVP (accept / decline / tentative) to a formal calendar invite via Nylas, and release any matching hold. `mailbox` (formerly `account`) is the mailbox the invite arrived in; the RSVP is never sent from another account |

## Tasks

Track deferred, multi-step, and waiting work in the unified [tasks backlog](/core-concepts/scheduling#tasks-and-the-backlog). These tools ship together in the **`tasks`** skill — pin that skill (`pinned_skills: [tasks]`) to give an agent the whole set and make it heartbeat-eligible, rather than pinning the tools individually. See [choosing built-in skills](/agents/building-custom-agents#choosing-built-in-skills).

| Tool | action_risk | Description |
|---|---|---|
| `task-create` | low | Create a task with an owner (you / the CEO / external), priority, optional due date, and an optional `wake_at` that schedules a future nudge |
| `task-list` | none | List tasks filtered by status, owner, or tag — the source for "what's open?", "what's waiting on me?" |
| `task-update` | low | Update a task's status, priority, owner, or wake time; append a progress note |
| `task-complete` | low | Mark a task done (cancels any pending wake-up) |
| `plan` | low | Draft or revise a task's decomposition into subtasks before committing them |
| `checkpoint` | low | Record durable progress on a long-running task so a later wake resumes where it left off |

## Documents (working memory)

An `ls` / `grep` / `read` / `write` interface over the agent's OKF document workspace — durable, document-like working memory for notes, plans, and drafts that outlive a single turn. These ship as the **`documents`** skill; pin it alongside `tasks` (`pinned_skills: [tasks, documents]`) for resumable project work. See [choosing built-in skills](/agents/building-custom-agents#choosing-built-in-skills).

| Tool | action_risk | Description |
|---|---|---|
| `doc-list` | none | List a directory in the document workspace, like `ls` on a path prefix. Returns the directory manifest of direct child documents with titles and types; use `doc-read` for content |
| `doc-read` | none | Read a document by path. Optionally read just one heading's section to keep context cost down; returns a not-found flag rather than erroring when the path is missing |
| `doc-search` | none | Case-sensitive substring search across the workspace, optionally scoped to a path prefix. Returns matching paths, line numbers, and line text; use `doc-read` to pull full context |
| `doc-place` | none | Recommend where a new project document belongs before writing it — extend an existing document, add to an existing `/projects/<name>/` folder, or start a new one. Doesn't write anything itself |
| `doc-write` | low | Create, append, replace, section-edit, or section-delete a document (section-delete removes one `##` section and its heading, and fails if the section isn't there). Every write is logged, and version conflicts return the latest versions so the agent can re-read and retry. Project documents are durable; scratch documents are ephemeral. Shared (`/shared/`) documents are durable and writable only by agents that declare them in [`pinned_context`](/agents/how-agents-work#pinned-context) |

**Readable placement.** Project documents land in human-readable `/projects/` folders (`/projects/board-offsite/`, not a task ID), with agents checking `doc-place` before starting a new folder so related work stays together.

## Google Workspace

Google Workspace connects as an [MCP server](/tools-and-skills/building#connect-an-mcp-server) (`google-workspace`) and covers **Drive, Docs, and Sheets** only. Calendar is never reached through it — your calendar always goes through the [Calendar specialist](/agents/built-in-agents#calendar-specialist). The Coordinator doesn't carry these tools on every turn; it activates them when you mention a Google file. When Curia shares a Drive file, you always get edit access, and other people get a role that fits the content.
