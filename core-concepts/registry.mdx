Curia ships with a large library of skills, several agents, and a handful of channels, but not all of them are active by default. What actually runs is governed by a **registry** — a database record of which skills, agents, and channels are installed and enabled. Only enabled items are loaded at startup. This gives you one place to turn capabilities on and off, and a gate that keeps a capability from running before its prerequisites (like an API key) are in place.

## Installed vs. enabled

The registry tracks two independent states for each item:

- **Installed** — the item is registered with the system. Installing records it and runs any install-time checks.
- **Enabled** — the item is active. Only enabled skills, agents, and channels are loaded and usable.

An item present on disk is not automatically active. A new skill you add, for example, is registered but starts disabled — you enable it before an agent can call it.

<Note>
  Registry changes are **restart-based**. Enabling or disabling an item updates its state in the database; the change takes effect when the instance reloads. Restart Curia after a change: `docker compose restart curia`. Curia re-reads the registry on startup, so a plain restart is enough here.
</Note>

## Required-secret gates

A tool or channel can declare credentials it cannot run without. The registry refuses to install or enable it until those secrets are present in the [vault](/get-started/secrets-vault):

- **Tools** declare `install.requires_secrets` in their manifest. The bundled `web-search` tool declares `tavily_api_key`, so it stays disabled until you provision a Tavily key.
- **Channels** declare required credential fields in the catalog. Email and Signal cannot be enabled until their vault keys (`channel.email.*`, `channel.signal.*`) resolve.

This means a half-configured capability fails closed — it cannot be switched on until it would actually work.

## Channels: always-on vs. toggleable

Channels behave like skills and agents, with one safeguard: the **HTTP and CLI channels are always on and cannot be disabled or uninstalled**. They are how you reach your own instance, so locking them off would lock you out. Email, Signal, Slack, SMS, and Voice are toggleable — install and enable them from the Channels page once their credentials are in the vault.

## Managing from the console

- **Tools, skills, and agents** — the **Tools** page lists everything registered, with its installed/enabled state. Required-secret gates are surfaced inline so you can see what a disabled item is waiting on.
- **Channels** — the Channels page lists each channel, its credential fields, and its enabled state. Enter credentials there (they are written to the vault) and enable the channel.

### Bundles and their tools

A **skill** is a bundle of tools. On the Tools page a bundle appears as a parent row with its member tools nested underneath; a tool that belongs to no bundle sits at the top level on its own.

Enabling or disabling a bundle applies to the bundle **and every tool in it, in one atomic change**. There is no state where the bundle is on and half its tools are off — that partial configuration is precisely what the grouped view exists to prevent, so if any part of the change fails, none of it is applied.

<Warning>
  **Watch for unresolved pins.** An agent can pin a bundle it needs. If that bundle is not enabled but the agent is, the agent silently loses every tool in it — and the only other symptom is a line in the startup log. The Tools page flags this case explicitly: an unenabled bundle pinned by an enabled agent is marked as unresolved, and names the agent affected. If an agent has mysteriously stopped being able to do something, check here first.
</Warning>

The same operations are available over the HTTP API under `/api/registry/*` for skills and agents and `/api/vault/*` for credentials — see the [HTTP API reference](/references/http-api).
