title: "Channel configuration schema"
description: "Reference for Curia channel configuration — the channel registry, credential vault keys, channel trust policy, and email accounts."

Channels have three configuration surfaces:

1. **The channel registry** — a DB-backed record of which channels are installed and enabled, plus their credentials in the vault. Managed from the Channels page in the console, not from YAML. See [Managing skills, agents, and channels](/core-concepts/registry).
2. **`config/channel-trust.yaml`** — per-channel trust level, unknown-sender policy, and threading. This is where a channel's security posture is set, not the vault or the adapter.
3. **Email accounts** — the mailboxes Curia itself reads and sends from, added in the console. See [Email accounts](#email-accounts).

## The channel registry

Each channel is described by a catalog entry and tracked by a row in the `channel_registry` table (`enabled`, `is_toggleable`, install/enable provenance). A channel implements a small interface:

```typescript
interface Channel {
  readonly name: string;          // 'email' | 'signal' | 'slack' | 'sms' | 'voice' | 'http' | 'cli'
  readonly isToggleable: boolean; // false for http and cli — see below
  start(): Promise<void>;         // connect / begin listening
  stop(): Promise<void>;          // graceful, idempotent teardown
}
```

Outbound delivery does not go through this interface — all sends are routed through the outbound gateway.

<Note>
  **HTTP and CLI are always on.** They have `isToggleable: false` and cannot be disabled or uninstalled — this is an operator-lockout safeguard, so you can never accidentally cut off your own access to the instance. Email, Signal, Slack, SMS, and voice are toggleable: install/enable them from the Channels page once their credentials are in the vault.
</Note>

### Credential fields and vault keys

Each channel declares its credential fields in the catalog. Every field is stored in the vault under a namespaced key following the convention `channel.<name>.<field>`:

| Channel | Vault keys |
|---|---|
| `email` | `channel.email.nylas_api_key`. Each mailbox's grant is stored per email account as `channel.email.<name>.nylas_grant_id`, and **Enable** also needs one enabled account with a grant. |
| `signal` | `channel.signal.socket_path`, `channel.signal.phone_number` |
| `slack` | `channel.slack.bot_token`, `channel.slack.app_token` |
| `sms` | `channel.sms.api_key`, `channel.sms.from_number`, `channel.sms.webhook_public_key` (vault-only — no env fallback) |
| `voice` | `channel.voice.livekit_url`, `channel.voice.livekit_api_key`, `channel.voice.livekit_api_secret`, `channel.voice.deepgram_api_key`, `channel.voice.cartesia_api_key`, `channel.voice.cartesia_voice_id` (vault-only — no env fallback) |

A field marked required must resolve before the channel can be enabled — the registry blocks enabling a channel whose required credentials are missing, the same way [`install.requires_secrets`](/references/tool-manifest-schema#install) gates tools.

## Channel trust and policy (`config/channel-trust.yaml`)

A channel's **security posture** is set here, not in the vault or the adapter. Each channel gets a block with three keys:

```yaml
channels:
  slack:
    trust: medium          # high | medium | low — max sensitivity of actions via this channel
    unknown_sender: allow  # allow | ignore
    threaded: true         # true = native threads; false = enable context bridging
```

| Key | Values | Meaning |
|---|---|---|
| `trust` | `high`, `medium`, `low` | Caps the sensitivity of actions this channel can drive. The dispatcher combines it with the sender's contact confidence and injection-risk score to compute the message trust score. Defaults to `low` when unset. |
| `unknown_sender` | `allow`, `ignore` | `allow` routes messages from unrecognized senders to the coordinator in low-trust mode (auto-created as a `tier=unknown` contact); `ignore` silently drops them (no rejection notice). |
| `threaded` | `true`, `false` | `true` when the platform has native threads (email, Slack). `false` enables [context bridging](/channels/how-channels-work#context-bridging-on-non-threaded-channels) for channels without a thread reference (Signal, SMS, CLI, HTTP). Voice is a live call rather than a store-and-forward channel, so bridging does not apply. |

Current defaults: CLI, Signal, and voice are `high`; HTTP, Slack, and SMS are `medium`; email is `low`. HTTP and voice use `unknown_sender: ignore` (voice is principal-only in the console); the rest `allow`.

## Email accounts

Curia's own mailboxes are managed in the console under **Settings → Channels → Email → Email accounts**, not in YAML. The old `channel_accounts.email` block in `config/local.yaml` is no longer read.

Each account has:

| Field | Meaning |
|---|---|
| Account name | Lowercase letters, digits, `-` and `_`, starting with a letter or digit (e.g. `curia`, `scheduling`). Email tools take it as their `account` parameter. |
| Address | The address this mailbox reads from and sends as. |
| Grant ID | The mailbox's Nylas grant, stored in the vault as `channel.email.<name>.nylas_grant_id`. |

All accounts share the one Nylas API key, `channel.email.nylas_api_key`. An account whose grant is missing is skipped at startup, and the others still start. Restart Curia after adding an account.

<Note>
The legacy vault keys `nylas_api_key`, `nylas_grant_id`, `nylas_self_email`, `ceo_nylas_grant_id` and `ceo_self_email` are no longer read. Curia migrates existing keys at boot. If email reports the Nylas key missing, re-save it in **Settings → Channels → Email**.
</Note>

The principal's own mailboxes are separate: they're managed under **Settings → Behaviour → Email & Calendar**. See [Your principal's email and calendar](/get-started/principal-email-calendar).
