---
title: "Agent manifest schema"
description: "Complete YAML schema reference for Curia agent definitions — all fields, types, defaults, and configuration options."
---

Agent definitions live in `agents/<name>.yaml`. Each file defines an agent's identity, model configuration, system prompt, and skill access.

<Note>
  Like skills and channels, agents are tracked in a [DB-backed registry](/core-concepts/registry). An agent on disk must be installed and enabled before it loads; only enabled agents run. Enable or disable agents from the Settings registry in the console — changes take effect on restart.
</Note>

## Schema reference

```yaml
# agents/<name>.yaml

# Required — unique identifier for this agent
name: string

# Required — "coordinator" or "specialist"
role: coordinator | specialist

# Required — human-readable description of the agent's purpose
description: string

# Required — LLM capability tier
model:
  tier: fast | standard | powerful   # maps to a concrete model via config/local.yaml

# Required — the system prompt injected on every task
# Supports ${variable} interpolation for runtime values
system_prompt: |
  Multi-line system prompt text...

# Required — tools and skills this agent can always invoke
# Items not in this list are only available if allow_discovery is true
pinned_skills:
  - skill-name-1
  - skill-name-2

# Optional — whether the agent can discover and invoke tools and skills not in pinned_skills
# Default: false
allow_discovery: boolean

# Optional — shared documents and config-store keys shown to the agent on every turn
# Each of docs / configs is a single string or a list; an item is a string or
# a mapping with path (docs) / key (configs) and an optional description
pinned_context:
  docs:
    - /shared/<folder>/<name>.md
    - path: /shared/<folder>/<name>.md
      description: string            # one line, 300 characters max
  configs:
    - <namespace>/<key>
    - key: <namespace>/<key>
      description: string

# Optional — inject the list of available specialist agents into the system prompt
# Used by the coordinator to know which specialists it can delegate to
# Default: false
inject_specialists: boolean

# Optional — custom handler for agent-specific logic
# Path relative to the agent YAML file
handler: ./custom-handler.ts
```

## Field details

### `name`

Unique identifier used for routing, delegation, and logging. Must be unique across all agent definitions. Convention: lowercase kebab-case.

### `role`

| Value | Meaning |
|---|---|
| `coordinator` | Receives all inbound messages. Only one coordinator should exist. |
| `specialist` | Receives tasks only via delegation from the coordinator or other agents. |

### `model`

The capability tier used to select the LLM for this agent. Tiers are mapped to concrete models by the operator in `config/local.yaml` under `model_routing.tiers` — see the [configuration reference](/references/configuration).

| Tier | Default model | Typical use |
|---|---|---|
| `fast` | Claude Haiku | High-frequency structured agents (calendar, contacts) |
| `standard` | Claude Sonnet | General-purpose agents (coordinator, inbox) |
| `powerful` | Claude Opus | Agents requiring maximum reasoning depth |

### `system_prompt`

The prompt injected at the start of every task. Supports runtime variable interpolation using `${variable}` syntax:

| Variable | Value |
|---|---|
| `${office_identity_block}` | Agent persona (name, title, signature) from office identity config |
| `${executive_voice_block}` | CEO's writing voice profile |
| `${agent_contact_id}` | The agent's own contact UUID |
| `${principal_contact_id}` | The principal's contact UUID (the CEO / operator the deployment serves). Resolved once at bootstrap. Pass it to `entity-context` to discover the principal's verified email addresses, Signal number, calendar IDs, and timezone — do not hardcode addresses or call `contact-lookup`-by-role for the principal. |
| `${available_specialists}` | List of specialist agents available for delegation |

Both `${agent_contact_id}` and `${principal_contact_id}` are opt-in — only agents that reference the placeholder pay the prompt-bytes cost. Both are guarded by a UUID-format check; if the underlying contact can't be resolved, the placeholder expands to an empty string and a one-time warning is logged at boot.

### `pinned_skills`

Array of tool and skill names this agent can always invoke. Each entry must be registered in the registry. If a name in this list doesn't exist at startup, a warning is logged but the agent still starts.

### `allow_discovery`

When `true`, the agent can use the `tool-registry` tool to search for and invoke tools and skills not in its `pinned_skills` list. The coordinator typically has this enabled; specialists typically do not (they operate with a fixed, auditable skill set).

### `pinned_context`

Shared documents and settings that are part of how the agent works. On every turn, Curia reads each one and adds a **Pinned context** section to the agent's instructions with its current contents. See [Pinned context](/agents/how-agents-work#pinned-context) for how each item is shown.

| Key | Accepts | Rules |
|---|---|---|
| `docs` | A path, or a list of paths or `{ path, description }` mappings | Each path must be a `.md` document under `/shared/`. Not `index.md` or `log.md` |
| `configs` | A key, or a list of keys or `{ key, description }` mappings | Each key is `<namespace>/<key>` with exactly one `/`. Whole namespaces are not supported |

`description` is optional. It must be one line of 300 characters or fewer.

Declaring a document is also what lets the agent write it: `doc-write` refuses a `/shared/` path that the calling agent doesn't declare. Config keys are shown only, and the agent still changes them with `config-store`.

The agent fails to load, with an error naming the agent and the entry, on any of these:
- a malformed entry or an unknown key
- a document outside `/shared/` or not ending in `.md`
- a config key without exactly one `/`
- a blank or over-long description
- a duplicate entry

### Memory access

Agents do not declare memory scopes. Every agent reads and writes a single shared knowledge graph; there is no per-agent memory isolation. What an agent can touch is governed by which memory tools it is granted (capability gating), the sensitivity ceiling on knowledge-graph reads, and source attribution on writes — not by agent identity.
