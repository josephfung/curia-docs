The Curia HTTP server is the process behind the web console. It serves the console's API — chat, jobs, tasks, contacts, the knowledge graph, and the registry — plus two operational endpoints for monitoring: `GET /api/health` and `GET /api/agents/status`.

<Note>
  `POST /api/messages` and `GET /api/messages/stream` were removed (ADR-057). Requests to them no longer reach an agent. To talk to Curia over HTTP, use [console chat](#console-chat) on `/api/chat`.
</Note>

## Base URL

The API listens on port `3000` by default. You can change this by setting `HTTP_PORT` in your `.env` file.

```
http://localhost:3000
```

For production deployments behind a reverse proxy, replace `localhost:3000` with your domain or internal service address.

## Authentication

There are two auth schemes, depending on the route.

**Bearer token.** The API token (`api_token`) lives in the [vault](/get-started/secrets-vault) and is generated automatically by `pnpm run setup`. It guards every route that does not authenticate itself, including `GET /api/agents/status`. Send it in the `Authorization` header:

```
Authorization: Bearer <your-token>
```

`GET /api/health` needs no token.

**Console session.** The console routes — chat, jobs, tasks, contacts, the knowledge graph, the registry, and the vault — authenticate with the `curia_session` cookie set by the `/auth` exchange, or with the `x-web-bootstrap-secret` header carrying `web_app_bootstrap_secret` from the vault.

### Example authenticated request

```bash
curl http://localhost:3000/api/agents/status \
  -H "Authorization: Bearer your-token-here"
```

If the token is missing or incorrect, the API returns:

```json
{ "error": "Unauthorized — provide a valid Bearer token" }
```

### Console chat

Console chat is how you send Curia a message over HTTP. It runs on the `web` channel, where the sender is the principal in their own authenticated session, so it carries **high trust**.

| Endpoint | Description |
|---|---|
| `POST /api/chat/messages` | Send a message. Body: `{ "message": "...", "conversationId": "..." }` (`conversationId` optional). Returns `202 { "conversationId": "..." }`; the reply arrives on the stream. |
| `GET /api/chat/stream` | Server-Sent Events stream of agent replies and tool activity. Filter with `?conversationId=...`. |
| `GET /api/chat/history` | Page through a conversation. Query: `conversationId` (required), `before` (ISO timestamp cursor), `limit` (default 25, max 50). |

Open the stream for the conversation, post the message, then read the reply from the stream:

```bash
# Terminal 1 — watch the conversation
curl -N -H "x-web-bootstrap-secret: $SECRET" \
  "http://localhost:3000/api/chat/stream?conversationId=my-conv-id"

# Terminal 2 — send a message
curl -X POST http://localhost:3000/api/chat/messages \
  -H "x-web-bootstrap-secret: $SECRET" \
  -H "Content-Type: application/json" \
  -d '{"message": "What is on my calendar today?", "conversationId": "my-conv-id"}'
```

### Other console endpoints

The following endpoints are used by the built-in web console. They use console session auth (see [Authentication](#authentication)), not the Bearer token.

| Endpoint | Description |
|---|---|
| `GET /api/jobs` | List scheduled jobs, with optional `status` and `agent_id` filters |
| `GET /api/jobs/:id` | Get a single scheduled job by ID |
| `POST /api/jobs` | Create a new scheduled job |
| `PATCH /api/jobs/:id` | Update or unsuspend a scheduled job |
| `DELETE /api/jobs/:id` | Cancel (soft-delete) a scheduled job |
| `GET/POST /api/kg/*` | Knowledge graph browser — nodes, graph, search, and node merge |
| `GET/POST /api/tasks`, `PATCH/DELETE /api/tasks/:id` | List, create, update, and delete tasks |
| `GET/POST /api/contacts`, `PATCH/DELETE /api/contacts/:id` | List, create, update, and delete contacts; sub-routes manage identities, permission overrides, and merges |
| `GET /api/grant-recommendations` | Pending capability-grant recommendations |
| `GET /api/autonomy` | Current autonomy score, band, trend direction, `lastSetBy`, and scored action count |
| `PUT /api/autonomy` | Set the autonomy score (body: `{ "score": 85, "reason": "..." }`) |
| `GET /api/autonomy/history` | Paginated autonomy score change history (query: `limit`, `offset`) |
| `GET /api/registry/tools` | List registered tools with installed/enabled state |
| `GET /api/registry/skills` | List registered skills (bundles) with installed/enabled state |
| `GET /api/registry/agents` | List registered agents with installed/enabled state |
| `POST /api/registry/:kind/:name/install` | Install a tool, skill, or agent (`kind` is `tools`, `skills`, or `agents`) |
| `POST /api/registry/:kind/:name/enable` | Enable an installed tool, skill, or agent |
| `POST /api/registry/:kind/:name/install-enable` | Install and enable in one call |
| `POST /api/registry/:kind/:name/disable` | Disable a tool, skill, or agent |
| `DELETE /api/registry/:kind/:name` | Uninstall a tool, skill, or agent |
| `GET /api/vault/*` | Manage vault secrets and channel credentials (names only; values are never returned) |

See [Managing skills, agents, and channels](/core-concepts/registry) for how the registry and required-secret gates work.

## Rate limiting

The API enforces a global limit of **200 requests per minute**. Stricter per-route limits apply to authentication endpoints to prevent brute-force attacks. When you exceed the limit, the API returns `429 Too Many Requests`.

## Error responses

All errors follow the same JSON format:

```json
{ "error": "A human-readable description of the problem." }
```

| Status | Meaning |
|---|---|
| `200` | Success |
| `400` | Bad request — a required field is missing or invalid |
| `401` | Unauthorized — token missing or incorrect |
| `413` | Payload too large — request body exceeds the 64 KiB limit |
| `429` | Rate limited — slow down and retry |
| `500` | Internal server error — check your Curia logs |
| `503` | Service degraded — typically a database connectivity issue |
