`GET /api/health` reports whether your Curia instance is healthy. It probes every dependency in real time — database, message bus, each configured channel, browser automation, MCP servers, and the task scheduler — and returns a single `status` field that summarises the result. No authentication is required, so you can point any uptime monitor or load balancer probe directly at this endpoint.

Unconfigured services report `"skipped"`, so the exact set of keys in `checks` depends on what you have enabled.

## Request

```
GET /api/health
```

No `Authorization` header is needed. The endpoint is intentionally open so monitoring infrastructure can reach it without credentials.

```bash
curl https://your-curia-instance.example.com/api/health
```

Rate-limited to 60 requests per minute.

## Response

### Status values

| `status` | HTTP | Meaning |
|---|---|---|
| `ok` | `200` | All enabled checks pass |
| `degraded` | `200` | A non-critical service is down — anything other than the database or bus |
| `down` | `503` | A critical service is unreachable (database or bus) — Curia cannot function |

Both `ok` and `degraded` return `200`. Your uptime monitor should watch for `503` to detect outages, and optionally check the response body for `"status":"degraded"` to catch softer failures.

### Response fields

<ResponseField name="status" type="string" required>
  Overall health of the instance: `"ok"`, `"degraded"`, or `"down"`. See the table above for semantics.
</ResponseField>

<ResponseField name="uptime_s" type="number" required>
  Seconds since the HTTP server started. Resets to `0` on each restart.
</ResponseField>

<ResponseField name="checks" type="object" required>
  Per-service check results. Each value is `"ok"`, `"fail"`, or `"skipped"`. A `"skipped"` result means the service is not configured and is excluded from the overall status calculation.

  <Expandable title="checks fields">
    <ResponseField name="checks.db" type="string" required>
      Database connectivity. `"fail"` causes `status: "down"` and a `503` response.
    </ResponseField>

    <ResponseField name="checks.bus" type="string" required>
      Internal message bus. `"fail"` causes `status: "down"` and a `503` response.
    </ResponseField>

    <ResponseField name="checks.email" type="string" required>
      Email adapter (Nylas). `"skipped"` when email is not configured.
    </ResponseField>

    <ResponseField name="checks.signal" type="string" required>
      Signal-cli socket. `"skipped"` when Signal is not configured.
    </ResponseField>

    <ResponseField name="checks.browser" type="string" required>
      Patchright browser context. `"skipped"` when browser automation is not configured.
    </ResponseField>

    <ResponseField name="checks.mcp" type="object" required>
      MCP server checks, keyed by server name. Each value is `"ok"`, `"fail"`, or `"skipped"`.

      ```json
      "mcp": { "google_workspace": "ok" }
      ```
    </ResponseField>

    <ResponseField name="checks.nylas_calendar" type="string" required>
      The principal's calendar grant, probed separately from email — a calendar grant can fail while the mailbox grant is fine. `"skipped"` when calendar is not configured.
    </ResponseField>

    <ResponseField name="checks.slack" type="string" required>
      Slack Socket Mode connection state, with a short grace period at boot. `"skipped"` when Slack is not configured.
    </ResponseField>

    <ResponseField name="checks.sms" type="string" required>
      Whether the Telnyx webhook handler is installed. `"skipped"` when SMS is not configured.
    </ResponseField>

    <ResponseField name="checks.voice" type="string" required>
      LiveKit reachability for console voice calls, probed via its management API. `"skipped"` when voice is not configured.
    </ResponseField>

    <ResponseField name="checks.signal_voice" type="string" required>
      The shared PulseAudio socket that carries Signal call audio. Probed by **connecting**, not by checking that the socket file exists — a dead audio daemon leaves its socket behind. `"skipped"` when `SIGNAL_PULSE_SOCKET_PATH` is unset.
    </ResponseField>

    <ResponseField name="checks.scheduler" type="string" required>
      Task scheduler heartbeat. `"fail"` if the scheduler has not ticked within its expected window.
    </ResponseField>
  </Expandable>
</ResponseField>

### Healthy response (200)

```json
{
  "status": "ok",
  "uptime_s": 3812,
  "checks": {
    "db":             "ok",
    "bus":            "ok",
    "signal":         "skipped",
    "email":          "ok",
    "browser":        "ok",
    "mcp":            { "google_workspace": "ok" },
    "nylas_calendar": "ok",
    "slack":          "skipped",
    "sms":            "skipped",
    "voice":          "skipped",
    "signal_voice":   "skipped",
    "scheduler":      "ok"
  }
}
```

### Degraded response (200)

A non-critical service is down. The instance is still operational — other services continue to work.

The example below is a real failure shape worth recognising: `signal` and `voice` are both `ok`, but `signal_voice` is `fail`. Signal messaging works and console calls work; only the audio path behind Signal *calls* is dead. Checks that look related fail independently.

```json
{
  "status": "degraded",
  "uptime_s": 7200,
  "checks": {
    "db":             "ok",
    "bus":            "ok",
    "signal":         "ok",
    "email":          "ok",
    "browser":        "skipped",
    "mcp":            { "google_workspace": "skipped" },
    "nylas_calendar": "ok",
    "slack":          "skipped",
    "sms":            "skipped",
    "voice":          "ok",
    "signal_voice":   "fail",
    "scheduler":      "ok"
  }
}
```

### Down response (503)

A critical service (database or bus) is unreachable. Curia cannot process agent requests.

```json
{
  "status": "down",
  "uptime_s": 120,
  "checks": {
    "db":             "fail",
    "bus":            "ok",
    "signal":         "skipped",
    "email":          "skipped",
    "browser":        "skipped",
    "mcp":            {},
    "nylas_calendar": "skipped",
    "slack":          "skipped",
    "sms":            "skipped",
    "voice":          "skipped",
    "signal_voice":   "skipped",
    "scheduler":      "fail"
  }
}
```

<Warning>
  A `503` response does not mean Curia has crashed — the HTTP server is still running and returning this response. It means the database or message bus is unreachable, which prevents agent actions from completing. Restore connectivity and the endpoint will return `200` on the next probe.
</Warning>

## HTTP status codes

| Status | Meaning |
|---|---|
| `200` | Instance is healthy or degraded — critical services are up |
| `503` | Instance is down — database or bus is unreachable |

## Which checks are critical vs. non-critical

**Critical (down on failure, 503):** `db`, `bus`

**Non-critical (degraded on failure, 200):** `email`, `signal`, `browser`, `mcp.*`, `nylas_calendar`, `slack`, `sms`, `voice`, `signal_voice`, `scheduler`

The rationale: a crashed Signal socket or a stale scheduler should raise a warning, not page as a full outage when email and the database are healthy.

## How deep each probe goes

Most checks make a real round-trip rather than asserting that an object exists. `browser` does a bounded call into the Chrome process; `signal_voice` opens a connection to the audio socket; `mcp` sends a `ping`. The reason is that holding a handle to something running in another process proves nothing about whether it is alive — a socket file outlives the daemon that made it, and a wedged browser still reports itself as connected.

Two checks are deliberately shallower. `slack` reads cached connection state, and `sms` only confirms the webhook handler is installed — neither proves inbound reachability. Proving that would put a third-party API call on an unauthenticated endpoint probed every 30 seconds, so it belongs in the daily canary instead. Treat those two as "configured and plausibly working", not as delivery guarantees.

## Use cases

<CardGroup cols={2}>
  <Card title="Uptime monitoring" icon="chart-line">
    Point Better Stack, Uptime Robot, or any HTTP monitor at this endpoint. Alert on `503` for outages. Add a keyword check on `"status":"degraded"` for a softer warning.
  </Card>
  <Card title="Load balancer health probe" icon="server">
    Configure your load balancer (AWS ALB, nginx, HAProxy) to probe `GET /api/health` every 10–30 seconds. Route traffic only to instances returning `200`.
  </Card>
  <Card title="Deployment verification" icon="circle-check">
    After deploying a new version, poll the health endpoint until it returns `200` before switching traffic.
  </Card>
  <Card title="Kubernetes readiness probe" icon="hourglass">
    Use this endpoint as a readiness probe. Curia is ready to serve traffic once `status` is `"ok"` or `"degraded"` (i.e., the HTTP response code is `200`).
  </Card>
</CardGroup>
