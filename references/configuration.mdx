This page documents the configurable settings in `config/local.yaml` that you are most likely to tune. A few internal defaults (health-check thresholds, document-workspace TTLs, bulk-export gates, and the autonomy bypass ladder) are omitted — `config/default.yaml` in the repo is the exhaustive source of truth, and `src/config.ts` holds the validation schema. For initial setup and environment variables, see [Initial configuration](/get-started/configuration).

## Secrets and the vault

Secrets are not configured in YAML or `.env`. They live in an [encrypted vault](/get-started/secrets-vault) (AES-256-GCM, stored in Postgres) and are resolved at runtime through a scoped accessor. Only four bootstrap values stay in `.env`: `DB_USER`, `DB_PASSWORD`, `DATABASE_URL`, and `SECRET_ENCRYPTION_KEY` (the base64 master key that decrypts the vault).

**Add or update vault secrets** via the Curia console (Settings → Channels for channel credentials) or through the initial `pnpm run setup` flow. See [Secrets vault](/get-started/secrets-vault) for vault key names and channel-by-channel guidance.

**Rotate the master key** by supplying the old and new keys; every stored secret is re-encrypted under the new key:

```bash
SECRET_ENCRYPTION_KEY_OLD=<old-base64> \
SECRET_ENCRYPTION_KEY_NEW=<new-base64> \
DATABASE_URL=<url> \
pnpm exec tsx scripts/rotate-secret-key.ts
```

After rotation, replace `SECRET_ENCRYPTION_KEY` in `.env` with the new key and recreate the container. See [Secrets vault](/get-started/secrets-vault) for the full workflow, the canonical key names, and backup guidance.

## Channels

Top-level channel settings. Per-channel credentials live in the vault (see above); this block controls channel-wide behavior. Signal activation is driven by vault credentials, not this file.

```yaml
# config/local.yaml
channels:
  cli:
    enabled: true          # the local CLI channel (always-on, not toggleable at runtime)
  max_message_bytes: 102400 # 100 KB — inbound messages larger than this are rejected before routing
```

`max_message_bytes` is the hard cap on a single inbound message across all channels; oversized messages are dropped before they reach an agent.

## Rate limiting

Curia enforces two independent rate limits in the dispatch layer to protect against message flooding from malfunctioning channels, abusive senders, or compromised integrations.

- **Global limit** — total messages per window across all senders, enforced before any policy-gate processing
- **Per-sender limit** — messages per sender per window, enforced after policy gates

Excess messages are dropped silently. Violations are audit-logged as `message.rejected` events with reason `global_rate_limited` or `sender_rate_limited`.

```yaml
# config/local.yaml
dispatch:
  rate_limit:
    window_ms: 60000       # 1-minute fixed window
    max_per_sender: 15     # messages per sender per window
    max_global: 100        # total messages per window across all senders
```

## Working memory summarization

When a conversation grows long, Curia automatically condenses older turns into a summary to prevent silent context-window overflow. You can tune when summarization triggers and how much recent context is preserved.

```yaml
# config/local.yaml
workingMemory:
  ttlDays: 30       # working-memory turns are purged this many days after they are written
  summarization:
    threshold: 20   # number of turns that triggers a summarization pass
    keepWindow: 10  # most-recent turns to retain as active after summarization
```

Constraints: `threshold` must be 2 or greater, `keepWindow` must be 1 or greater, and `keepWindow` must be less than `threshold`.

`ttlDays` (default `30`) is the retention window for individual working-memory turns. The dream engine's nightly purge deletes turns whose `expires_at` has passed, so 30 days means re-opening a conversation up to a month later still has full context. Lower it for high-volume deployments where week-old context isn't worth retaining. Must be a positive integer no greater than `36500` (100 years).

## Conversation checkpoint debounce

After the last agent response in a conversation, Curia waits for a quiet period before firing a `conversation.checkpoint` event, which kicks off background memory extraction (`extract-relationships` and related passes). Debouncing means a burst of rapid turns produces one extraction pass at the end rather than one per turn.

```yaml
# config/local.yaml
dispatch:
  conversationCheckpointDebounceMs: 600000   # 10 minutes of inactivity before extraction fires
```

Lower it to extract memory sooner after a conversation goes quiet; raise it to batch more turns into a single extraction pass. Must be a positive integer; a non-numeric or non-positive value is a hard startup failure.

## Skill output length

All skill results are sanitized and truncated before being fed to the LLM. Raise this limit if you routinely hit it on large-payload skills (search results, page crawls, long calendar lists). Lower it to reduce LLM context pressure on installations with many concurrent agents.

```yaml
# config/local.yaml
skillOutput:
  maxLength: 200000   # characters (~50k tokens at 4 chars/token)
```

## Web browser

Controls the headless browser the `web-browser` skill drives (Patchright, a stealth-hardened Playwright fork). Sessions are pooled and swept on a timer so logins can persist across calls without leaking idle browser processes.

```yaml
# config/local.yaml
browser:
  sessionTtlMs: 600000     # how long a session stays alive after its last action (10 min)
  sweepIntervalMs: 120000  # how often expired sessions are swept (2 min)
  profileDir: ""           # persistent profile dir; empty → ${HOME}/.curia/browser-profile
  channel: ""              # "chrome" for real Chrome (must be in the image); empty → bundled Patchright Chromium
  locale: "en-US"          # context locale (BCP 47)
```

Mount `profileDir` on a volume in production so browser logins survive container restarts.

## Security rules

<AccordionGroup>
  <Accordion title="Extra injection patterns">
    Curia checks all inbound messages against a set of built-in prompt injection patterns. You can add your own patterns without changing any code.

    Built-in patterns include: "ignore previous instructions", "you are now", "system:", "act as", and others.

    ```yaml
    # config/local.yaml
    security:
      extra_injection_patterns:
        - regex: "forget everything above"
          label: "forget everything above"
        - regex: "new\\s+persona"
          label: "new persona"
    ```

    <Warning>
      Avoid patterns with unbounded nested quantifiers such as `(a+)+` or `(.+)+`. These can cause catastrophic backtracking on adversarial input and may freeze the Node.js event loop. Prefer simple bounded patterns. These patterns run on every inbound message.
    </Warning>
  </Accordion>

  <Accordion title="Trust score weights">
    Each inbound message receives a trust score based on the channel it arrived on, the confidence of the sender's contact record, and any detected injection risk. You can adjust the relative weights of these factors.

    ```yaml
    # config/local.yaml
    security:
      trust_score:
        channel_weight: 0.4       # weight of channel trust level
        contact_weight: 0.4       # weight of sender contact confidence
        max_risk_penalty: 0.2     # maximum penalty for detected injection risk
    ```

    Channel trust levels normalize as: `high = 1.0`, `medium = 0.6`, `low = 0.3`. A contact's capability is governed separately by its ordered tier: `blocked` < `unknown` < `known` < `trusted` < `principal`. See [Contacts and trust](/core-concepts/contacts-trust) for details.
  </Accordion>

  <Accordion title="Action trust thresholds">
    The coordinator checks a sender's `messageTrustScore` against these thresholds before taking action on their behalf. All values must be between 0.0 and 1.0. **This block is required** — startup fails if it is missing or malformed.

    ```yaml
    # config/local.yaml
    security:
      trust_thresholds:
        information_query: 0.2   # answering questions, summaries
        scheduling: 0.5           # calendar changes, meeting requests
        data_export: 0.8          # sharing files, forwarding records
        financial: 0.8            # payments, financial commitments
    ```

    These thresholds are compiled into the coordinator's system prompt at startup. Changes take effect on restart. See [Contacts and trust](/core-concepts/contacts-trust#action-thresholds) for how these thresholds are enforced.

    <Note>
      This replaces the previous top-level `trust_policy` config key, which was dead config (typed but never read by the runtime). If you had overrides under `trust_policy`, move them to `security.trust_thresholds`.
    </Note>
  </Accordion>

  <Accordion title="Custom PII patterns">
    Curia redacts common PII from LLM-facing error messages by default: email addresses, phone numbers, credit card numbers, and US Social Security numbers. Add custom patterns for PII types specific to your deployment.

    ```yaml
    # config/local.yaml
    pii:
      extra_patterns:
        - regex: "EMP-\\d{6}"
          replacement: "[EMPLOYEE_ID]"
        - regex: "\\b\\d{3}[-\\s]?\\d{3}[-\\s]?\\d{3}\\b"
          replacement: "[CA_SIN]"
    ```

    <Warning>
      Avoid patterns with unbounded nested quantifiers. These patterns run on every LLM-facing error message.
    </Warning>
  </Accordion>

  <Accordion title="Outbound PII redaction">
    Distinct from `pii.extra_patterns` (which scrubs LLM-facing error strings), this policy governs which detected PII is allowed to leave in **outbound channel messages** (email, Signal). Detection uses the same library as the log scrubber; this block controls only the policy — which detected labels pass through on which channel. Anything not on a channel's allow list is redacted. The principal is exempt structurally (a UUID match on the CEO contact ID), so their own messages are never redacted.

    ```yaml
    # config/local.yaml
    pii:
      outbound_redaction:
        enabled: true          # kill switch for the whole outbound-redaction pass
        default: block         # action for label/channel combos not explicitly allowed (block | allow)
        channel_policies:
          email:
            allow: [email]     # email addresses pass through on email replies
          signal:
            allow: []          # nothing allowed on Signal (except the principal)
    ```

    Each key under `channel_policies` is a channel name; its `allow` list holds the lowercase pattern labels permitted on that channel. With `default: block`, omitting a channel means everything is redacted for it.
  </Accordion>
</AccordionGroup>

## Knowledge graph sensitivity rules

Every knowledge-graph node is classified into a sensitivity level — `public`, `internal`, `confidential`, or `restricted` — based on its content. These rules drive bulk-export gating: `restricted` nodes are blocked from bulk export entirely, and `confidential` nodes require CEO approval. `sensitivity_rules` is a top-level list; each entry is a category with a sensitivity level and a set of lowercase patterns.

```yaml
# config/default.yaml — this block is read ONLY from default.yaml (see warning below)
sensitivity_rules:
  - category: credentials        # human-readable label, used for logging and category hints
    sensitivity: restricted      # public | internal | confidential | restricted
    patterns:                    # lowercase substrings matched case-insensitively
      - password
      - api key
      - secret key
  - category: financial
    sensitivity: confidential
    patterns:
      - salary
      - invoice
      - bank account
```

<Warning>
  Unlike every other block on this page, `sensitivity_rules` is loaded directly from `config/default.yaml` at startup — the classifier reads that file by an absolute path, **not** the merged `local.yaml`. Rules placed in `config/local.yaml` are silently ignored. To customize sensitivity classification you must edit `config/default.yaml` in the repo. ([Configuration merge behavior](/get-started/configuration) covers how every other block is layered from `local.yaml`.)
</Warning>

Rules are evaluated highest-sensitivity-first, so the most protective match always wins — a node matching both a `restricted` and a `confidential` pattern is classified `restricted`. Matching is a case-insensitive substring search across the node's label and all of its string property values, so write patterns in lowercase. The full shipped rule set (credentials, board materials, litigation, strategy, financial, contracts, HR, and personal identifiers) lives in `config/default.yaml`; edit it there to add categories or patterns. See [Contacts and trust](/core-concepts/contacts-trust) for how sensitivity interacts with export controls.

## Outbound content filter (LLM judge)

Stage 2 of the outbound content filter is a single-purpose LLM judge that blocks messages leaking internal monologue, system/agent status, or side-channel notes to a mixed audience. Stage 1 (deterministic rules) always runs and has no config. The judge is skipped entirely when the principal is the sole recipient. Use a different model family than your agent tiers for diversity — an attack tuned for the coordinator should not also fool the reviewer.

```yaml
# config/local.yaml
filter:
  llmJudge:
    enabled: true
    model: claude-haiku-4-5
    timeout_ms: 5000
    failMode: split   # split (default) | open | closed
```

`failMode` controls what happens on judge timeout or error: `split` sends to principal-only recipients but blocks mixed-audience sends, `open` sends anyway, `closed` blocks.

## Escalation policy judge

A separate LLM judge classifies outbound disclosures and proposed actions, then maps trust tier × class to allow or escalate. It is fail-closed: on timeout or error the action escalates. As with the content filter, prefer a different model family than the coordinator.

```yaml
# config/local.yaml
escalation:
  judge:
    enabled: true
    model: claude-haiku-4-5
    timeout_ms: 5000
```

## Contact creation limits

When Curia processes email, it auto-creates `unknown`-tier contacts for unrecognized participants. These limits protect against spam campaigns that flood your contacts database.

```yaml
# config/local.yaml
contact_creation_limits:
  max_per_message: 10    # max new contacts from a single email's participant list
  max_per_hour: 100      # max new contacts per hour, per email account
```

When a limit is hit, remaining participants are skipped and the CEO is notified (at most once per limit type per hour). Skipped participants will be auto-created if they email directly in the future. See [Contacts and trust](/core-concepts/contacts-trust#automatic-contact-creation-from-email) for full details.

## Knowledge graph decay

Curia's dream engine runs a nightly background pass that reduces the confidence of facts in the knowledge graph based on their decay class. When a fact's confidence falls below the archive threshold, it is soft-deleted — it no longer appears in queries but is retained in the audit log.

```yaml
# config/local.yaml
dreaming:
  decay:
    intervalMs: 86400000       # how often the decay pass runs (default: daily)
    archiveThreshold: 0.05     # confidence below which facts are archived
    halfLifeDays:
      permanent: null          # permanent facts are never touched by the decay pass
      slow_decay: 180          # employer, residence — reliable for months
      fast_decay: 21           # coffee preference, current focus — unreliable after weeks
    # Decay-warning knobs: warn "important" nodes before archiving them.
    edgeCountPercentile: 0.95  # a node in the top 5% by edge count counts as important
    edgeCountFloor: 5          # minimum edge count to be important regardless of percentile
    warnHoldBackDays: 7        # days to hold a warned node before archiving it anyway
```

Before archiving a node, the decay pass checks whether it is **important** — either high-sensitivity (confidential or restricted) or highly connected (edge count at or above the `edgeCountPercentile` of all nodes, with `edgeCountFloor` as a hard minimum). Important nodes are warned rather than silently archived, and held back for `warnHoldBackDays` before archiving proceeds. `edgeCountPercentile` is a fraction between 0 and 1; `edgeCountFloor` and `warnHoldBackDays` are non-negative integers.

## Autonomy auto-scoring

A second dream-engine pass runs daily alongside decay. It scores recently completed actions on three dimensions (Competence, Commitment, Compatibility) with an LLM judge, then nudges the [autonomy score](/core-concepts/autonomy) up or down by a small delta. This is how the score drifts on its own between explicit CEO adjustments.

```yaml
# config/local.yaml
dreaming:
  autonomy_scoring:
    intervalMs: 86400000      # how often the pass runs (default: daily, same cadence as decay)
    model_tier: fast          # tier for the scoring judge, resolved via ModelRouter
    batchSize: 50             # max actions scored per pass
    minScoredActions: 30      # minimum scored actions before any adjustment fires
    halfLifeDays: 30          # time-decay half-life for weighting recent vs. older actions
    weakExpiredWeight: 0.3    # reduced weight for an 'expired' compatibility signal
    ceoCooldownDays: 7        # days after a manual CEO set-autonomy before auto-adjust resumes
    errorRateThreshold: 0.20  # competence error rate above which score increases are blocked
```

`model_tier` is a tier name (`fast` / `standard` / `powerful`), not a raw model string — set the concrete model under [model routing](#model-routing). The older `model` key is rejected at startup; use `model_tier`. `ceoCooldownDays` prevents the background pass from immediately undoing a score the CEO just set by hand. `weakExpiredWeight` and `errorRateThreshold` are fractions between 0 and 1; the interval, batch, and count knobs are positive integers.

## Intent drift detection

For long-running scheduled tasks, Curia periodically compares the agent's current progress against the original task description. If the agent has drifted significantly from its goal, the task is paused and you are notified. In unattended mode, drift detection blocks — it does not just advise.

```yaml
# config/local.yaml
intentDrift:
  enabled: true
  checkEveryNBursts: 1          # check on every burst (raise to reduce LLM call frequency)
  minConfidenceToPause: high    # high | medium | low
```

**Confidence thresholds:**

| Value | Behaviour |
|---|---|
| `high` | Pause only on egregious, unambiguous deviations. Fewest false positives. (Default) |
| `medium` | Pause on probable deviations. Some false positives expected. |
| `low` | Pause whenever any drift is detected, regardless of LLM confidence. |

## Model routing

Agents declare a capability tier rather than a specific model. The `model_routing` config maps each tier to a concrete model. The provider is inferred automatically from a centralized **model registry** based on the model name prefix (e.g., `claude-*` resolves to Anthropic, `google/gemini-*` resolves to OpenRouter).

```yaml
# config/local.yaml
model_routing:
  tiers:
    fast:
      model: claude-haiku-4-5
    standard:
      model: claude-sonnet-4-6
    powerful:
      model: claude-sonnet-4-6
  default_tier: standard   # tier used when a caller requests a model without naming a tier
```

`default_tier` (default `standard`) is the tier the `ModelRouter` falls back to when a caller resolves a model without specifying a tier. It must be one of `fast`, `standard`, or `powerful`; any other value is a hard startup failure.

To route a tier through OpenRouter (requires `openrouter_api_key` in the vault), set the model to an OpenRouter model ID:

```yaml
model_routing:
  tiers:
    fast:
      model: google/gemini-2.5-flash    # routed through OpenRouter
    standard:
      model: claude-sonnet-4-6           # routed through Anthropic
    powerful:
      model: claude-sonnet-4-6
```

The `ModelRouter` validates at startup that every configured model exists in the model registry. Unknown models cause a startup failure with a clear error message.

<Note>
  The `provider` field was removed from tier config. The model registry infers the provider from the model name — you only need to specify the `model`.
</Note>

## Delegation and scheduler timeouts

Two related timeouts can be tuned per deployment based on your model's latency profile.

```yaml
delegate:
  defaultTimeoutMs: 90000   # how long the coordinator waits for a delegated specialist's reply (90 s default)

scheduler:
  defaultExpectedDurationSeconds: 600   # fallback expected duration for scheduled jobs that don't declare one (10 min default)
```

Raise `delegate.defaultTimeoutMs` if specialist agents are timing out under standard-tier models that run more slowly than the defaults assume. `scheduler.defaultExpectedDurationSeconds` is what the watchdog uses to compute the recovery timeout for a job — increase it if you run long jobs without an explicit `expectedDurationSeconds` hint. Both values are validated at startup; non-numeric or non-positive values cause a hard startup failure.

## Outbound context bridge

Controls TTL for the registry that lets the coordinator link incoming replies to messages it previously sent. See [Architecture › Outbound context bridge](/core-concepts/architecture#outbound-context-bridge) for the conceptual model.

```yaml
contextBridge:
  defaultExpiryHours: 6      # auto-registered entries (proactive sends without explicit context_bridge metadata)
  explicitExpiryHours: 24    # entries with explicit context_bridge JSON
```

Every outbound message auto-registers an entry. Callers can pass a `context_bridge` input with `expires_in_hours` to override per-entry; that value wins over both defaults.

## Meeting debrief

Configures the meeting-debrief specialist agent. The agent itself is defined in `agents/meeting-debrief.yaml`; this block controls runtime knobs.

```yaml
debrief:
  channel: signal               # channel for debrief prompts (signal | email)
  reminderDelayMinutes: 120     # minutes before a reminder is sent for unanswered debriefs
  contextBridgeTtlHours: 48     # how long replies to a debrief prompt remain routable back to the agent
```

`contextBridgeTtlHours` overrides the global `contextBridge.explicitExpiryHours` for the outbound-context entry the agent registers when it sends a debrief prompt — giving the CEO a longer window to reply before the entry expires.

## Task management

Tunes the [task backlog and heartbeat](/core-concepts/scheduling#tasks-and-the-backlog). The heartbeat is the deterministic loop that wakes idle or stale tasks so open work doesn't linger.

```yaml
tasks:
  heartbeatIntervalMinutes: 60   # how often the heartbeat ticks
  heartbeatMaxWakesPerTick: 5    # global cap on agents woken per tick (per-agent cap is always 1)
  idleThresholdHours: 4          # an open/in-progress Curia-owned task is "idle" after this long untouched
  staleWaitThresholdHours: 48    # a waiting/blocked task with no pending wake is "stale" after this long
```

Whether an agent participates in the task system (auto-pinned `task-*` skills, the executor-discipline prompt block, and heartbeat eligibility) is set per agent with `enable_task_management: true` in `agents/<name>.yaml` — not in this file. The coordinator and ceo-inbox ship with it enabled.

## Autonomy engine

The autonomy score is stored in Postgres and controlled via natural-language commands or the CLI — you do not set it in a config file. Ask Curia directly:

- *"What is your current autonomy score?"*
- *"Set your autonomy score to 85."*

The score defaults to **75 (Approval Required)** on first deployment. Changes take effect immediately without a restart. See [Autonomy](/core-concepts/autonomy) for the full band reference and [Autonomy engine](/security/autonomy-engine) for the governance mechanics.
